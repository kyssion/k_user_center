# 全局持久化与事务规范

## 1. 单条命令执行骨架

所有改变权威事实的同步命令按以下顺序实现：

1. 在事务外完成语法、长度、协议格式和不需要权威状态的输入校验。
2. 解析调用者、主体、Tenant、Client、Business Line 和安全 Profile。
3. 完成认证强度、授权、风险、审批和限流判断；需要稳定快照的版本 ID 随命令写入。
4. 开启数据库事务并登记 `idempotency_records`。相同作用域和键、不同 `request_hash` 返回冲突。
5. 读取权威聚合及其 `row_version`；读取存在不代表状态、作用域或权限有效。
6. 执行业务前置条件和状态转换判断。
7. 使用 `WHERE id = @id AND row_version = @expected` 更新；成功时显式递增 `row_version`。`updated_at` 由数据库技术 Trigger 自动刷新。
8. 在同一事务写入权威事实、Outbox、Audit 和最终幂等结果；任何一项失败都回滚。
9. 提交后再执行非事务外部调用；需要可靠恢复的调用由 Outbox 或 `operations + operation_steps` 驱动。

禁止在数据库 Trigger、Function 或 Stored Procedure 中实现第 2、3、6、8 步的业务判断。

## 2. 数据库约束与代码校验

| 数据库拒绝项 | 代码仍需处理 |
|---|---|
| Primary Key、Unique、NOT NULL、基础 Check | 将约束名稳定映射为领域错误，不暴露占用主体或敏感值 |
| `RESTRICT` Foreign Key | 目标类型、Tenant/Business Line、目标状态、授权和生命周期 |
| `row_version >= 0` | expected version、重读、冲突响应和有限重试 |
| 时间先后、非负数、字段互斥 | TTL、冷静期、保护期、最大尝试策略和业务日历 |
| 列级 UPDATE 权限 | 状态转换是否合法、字段变化是否允许、操作者是否有权 |
| `updated_at` 技术 Trigger | 业务发生时间、签发时间、生效时间和完成时间 |

Foreign Key 错误只能说明引用不存在，不得替代状态、租户或授权判断。多态、数组和外部引用必须在代码中显式解析并测试未知类型及跨作用域引用。

## 3. 字段可变性

字段分为四类：

1. 永久不可变：内部主键、公开稳定 ID、唯一业务键、请求/内容摘要、创建/签发/记录时间、不可变版本载荷。
2. 追加式事实：Audit、认证尝试、授权决策、风险评估、审批动作、投递尝试和迁移变更日志，只允许 INSERT。
3. 生命周期元数据：状态、原因、消费/撤销/退役时间、重试计数、当前指针、`updated_at` 和 `row_version`，只允许列级 UPDATE。
4. 可版本化内容：策略、配置、模板、Schema、密钥发布和 Subject 分配通过新增版本表达，不原地改写已发布内容。

代码仓储不得使用“更新整个实体”的通用接口；每个命令必须声明允许更新的字段集合，并与 `825_column_update_permissions.sql` 对齐。

## 4. 并发与单次消费

- 聚合更新使用 `row_version` CAS；受影响行数为 0 时返回 `412 VERSION_MISMATCH`，不得盲目覆盖。
- 唯一占用、当前占位、幂等键、Token 摘要和全局事件 ID 由数据库最终裁决并发竞争。
- Challenge、恢复码、授权码和 Refresh Token 使用条件更新完成单次消费，例如同时匹配 `state`、未过期和 expected version。
- 网络重试不得创建第二条 Token 轮换分支、第二个当前 Membership 或第二个当前 Subject。
- 可安全自动重试的只有序列化失败、死锁和明确无外部副作用的 CAS 重读；业务冲突不自动重试。

## 5. Outbox、Audit 与 Operation

- 同步命令：权威事实、Outbox、Audit 和幂等结果同事务提交。
- 跨系统长流程：事务内创建 `operations`、初始 `operation_steps` 和 Outbox，事务外由 Worker 推进。
- `operations.request_digest/request_payload`、Actor、Subject、能力编号和策略版本是创建时快照，不得在重试中改写。
- Worker 只能更新状态、检查点、尝试次数、结果、错误和下一次重试时间。
- 越过不可逆边界前必须完成审批、幂等和补偿能力检查，并写入 `irreversible_at`。

## 6. 统一错误映射

| 场景 | API/领域结果 |
|---|---|
| 唯一键被占用 | `409 CONFLICT`；使用稳定领域错误码，不回显占用者 |
| 同幂等键不同请求摘要 | `409 IDEMPOTENCY_KEY_REUSED` |
| expected version 不一致 | `412 VERSION_MISMATCH` |
| 引用不存在 | `404` 或 `422 INVALID_REFERENCE`，由资源暴露策略决定 |
| 引用存在但跨租户/无权访问 | 对外按防枚举策略返回 `404` 或 `403` |
| 基础 Check 失败 | `422 INVALID_ARGUMENT`；日志记录约束名，不回显敏感值 |
| 状态转换不合法 | `409 INVALID_STATE_TRANSITION` |
| 需要 Step-up/审批 | `403 STEP_UP_REQUIRED` 或 `202` + `operation_id` |
| 数据库不可用且安全敏感 | 失败关闭，不使用陈旧授权或风险结果继续写入 |

## 7. 查询与索引契约

每个 Repository 查询必须登记：

```text
query_id
owner_domain
table
where_predicate
order_by
expected_cardinality
required_index
tenant_guard
freshness_requirement
```

队列领取必须使用状态、可执行时间和稳定顺序；Subject/Identifier/Token/公开请求 ID 必须走唯一或前缀索引；Tenant 查询不得省略 Tenant 守卫。索引门禁检查名称和结构，PostgreSQL 实跑阶段再使用代表性数据量验证 `EXPLAIN`。
