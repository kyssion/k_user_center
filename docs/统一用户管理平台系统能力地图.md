# 统一用户管理平台系统能力地图

> **文档定位**：本文档是统一用户管理平台的唯一权威施工蓝图，目标是「多个前台系统 + 多个后台系统、统一账号、单点登录」。能力编号 `CAP-{域码}-{序号}` 全文唯一，供验收清单与工单引用。

## 1. 平台定位

统一用户管理平台是公司所有前台系统与后台系统共同依赖的身份基础设施，不是一张公共用户表，也不只是登录注册服务。

### 1.1 业务对象

| 对象 | 说明 |
|---|---|
| 外部用户 | 使用统一登录注册授权能力的前台系统用户 |
| 业务方 | 不自建登录认证，接入平台的前台系统与后台系统 |
| 内部系统管理员 | 管理平台自身，拥有全部管理域权限，受职责分离与操作审计约束 |
| 业务方管理员 | 管理本业务系统的账号与权限 |
| 业务子账号 | 由业务方管理员创建并授予有限权限的账号 |

### 1.2 平台职责

- 统一身份认证（面向外部用户与前台系统）：注册、登录、单点登录、令牌签发与会话管理。
- 用户与权限管理（面向内部与后台系统）：用户档案、账号处置、后台管理员账号与权限管理。
- 统一登录页：平台提供默认登录页，业务方也可按平台接口规范自建页面接入。

职责细目见 §5 能力清单。

### 1.3 平台不负责

- 订单、资产、会员等级、积分、内容、客户标签等业务数据，不把业务数据集中到用户中心。
- 会员系统、CRM、组织人事系统或业务后台的业务功能。
- 业务系统不得直接读写用户中心数据库。

## 2. 建设原则

### 2.1 数据库设计

（1）数据库只负责存储与查询；业务逻辑、人员权限与数据权限全部在代码中实现。
（2）通用能力（如更新时间自动记录）使用数据库自身能力；表与字段注释完整，命名清晰。
（3）预留扩展字段，必要时允许适度冗余；敏感数据不得明文存储。
（4）表结构保持简单清晰，不做过度设计，参考最佳实践。

### 2.2 技术实现

（1）优先选用经过审计与社区验证的成熟组件；协议层（OAuth/OIDC 端点、Token 签发与校验、密码哈希）禁止自研，必须复用成熟开源实现，.NET 技术栈优先评估 OpenIddict 与 Duende IdentityServer（阶段 0 冻结选型，见 §14）；平台只实现用户、会话与权限的业务语义层。
（2）分层架构，依赖方向自上而下（Controller → Service → Repository），禁止反向依赖与跨层调用；模块边界通过命名空间与架构测试保障。
（3）功能模块化，高内聚、低耦合。
（4）安全纵深防御：在协议层、代码边界、数据库权限与运行时环境分别设防；敏感数据（密码、Token、验证码）禁止明文出现在数据库、日志与审计中。
（5）优先使用 OpenID Connect、OAuth 2.0 等标准协议。

### 2.3 业务核心原则

（1）身份与业务解耦：全局用户只表达「是谁」，业务成员关系表达「在哪个业务中是什么状态」；各业务系统以统一标识关联自己的成员与业务数据。
（2）认证与授权分离：认证解决「是谁」，授权解决「能做什么、能访问哪些数据」。
（3）标识与登录名分离：手机号、邮箱会变化，不能作为主键（见 §4.2）。
（4）公共资料与业务资料分离：业务私有信息（会员等级、积分、偏好等）由业务系统负责。
（5）全局状态与业务状态分离：安全冻结全局生效，业务封禁只影响指定业务系统。
（6）权限分级：外部用户、平台管理员、业务管理员、业务子账号权限不同；**前台用户账号与后台管理员账号分属两个独立账号空间，互不互通**。
（7）全程可审计：身份、凭证、权限与管理操作必须留痕。
（8）配置与数据面分离：配置、策略与应用接入变更可版本化、可回滚，生产变更留有记录。

## 4. 核心领域模型

### 4.1 核心对象

| 对象 | 定义 | 关键要求 |
|---|---|---|
| Global User | 平台内唯一的前台用户主体 | UID 永久、不可变、无业务含义、不可复用 |
| Identity | 用户可用于登录的身份 | 手机、邮箱、用户名、微信账号；一个用户可有多个 |
| Credential | 证明身份的凭证 | 密码哈希等，与用户资料隔离存储 |
| Application | 接入平台的前台或后台系统 | 登记类型、负责人、状态、接入策略 |
| Client | 应用在协议层的 OAuth 客户端 | Client ID、密钥、回调地址、scope、环境 |
| Admin User | 后台管理员（员工）账号 | 独立于前台用户的账号空间，见 §2.3（6） |
| Role / Permission | 后台角色与权限模型 | 按后台系统划分作用域，支持角色继承与互斥 |
| Membership | 用户与某业务系统的成员关系 | 记录该系统内的业务状态（正常、停用、封禁） |
| Profile | 公共用户资料 | 平台统一管理；业务私有资料由业务系统负责 |
| Session | 一次持续登录关系 | 关联应用、过期时间、撤销状态 |
| Audit Event | 操作审计记录 | 操作者、对象、动作、时间、来源、前后值 |
| External Account Mapping | 存量系统账号映射 | 旧系统 ID ↔ UID，仅用于迁移与对账 |

### 4.2 ID 体系

| 标识 | 用途 |
|---|---|
| Global User ID（UID） | 平台内部统一标识，永久稳定，仅平台内部与受信任系统使用 |
| Subject ID | 通过 OIDC 发布给应用的用户标识（`sub`）；公司内部系统默认共享同一 Subject，是否按应用隔离可配置（§14 决策 4） |
| External ID | 存量系统旧用户 ID，仅作迁移映射键 |

- UID 不包含手机号、注册时间等可推断信息；内部主键可用有序 ID（如 UUIDv7）保证索引效率。
- 手机号和邮箱只是可变登录标识，不得作为主键；旧系统 ID 只作映射，禁止继续作为跨系统主键。
- UID、Subject ID 不得被重新分配给其他用户。

### 4.3 数据权威边界

| 数据 | 权威系统 |
|---|---|
| 全局 UID、账号状态、登录身份、凭证 | 用户中心 |
| 公共头像、昵称、已验证手机号和邮箱 | 用户中心 |
| 后台管理员账号、跨后台的角色与权限 | 用户中心 |
| 用户在某业务系统中的会员等级、积分、订单、偏好 | 业务系统 |
| 业务系统内部的菜单、按钮级细粒度权限 | 业务系统（首期） |
| 各业务系统的员工与组织人事数据 | 各业务系统或人事系统 |

### 4.4 账号状态机与不变量

账号状态使用正交维度，禁止用一个字段同时表达生命周期、安全处置和业务状态：

- 用户生命周期：`PROVISIONAL → ACTIVE`；注销 `ACTIVE → DELETING（冷静期）→ DELETED`，冷静期内可撤回；`DELETED` 为终态，保留 UID 墓碑。
- 认证锁定：`ENABLED ⇄ LOCKED`，多次失败自动锁定，可自动或人工解锁。
- 全局冻结：`CLEAR ⇄ FROZEN`，人工处置，全局生效，阻止一切登录与会话刷新。
- 应用成员状态：`ACTIVE ⇄ SUSPENDED → BANNED`，仅影响该业务系统的 Membership。
- 标识状态：`PENDING → VERIFIED → UNBOUND`，解绑后进入隔离期，期满释放；保留历史归属记录防回收号码接管。
- 会话状态：`ACTIVE → EXPIRED / REVOKED`。
- 管理员账号状态：`ACTIVE ⇄ LOCKED / DISABLED`，与前台用户状态互不影响。

全局不变量：

1. UID 与 Subject ID 一经签发不得变更、复用或重新分配。
2. 同一唯一性作用域内，一个有效手机号/邮箱最多绑定一个有效用户。
3. 冻结用户不得登录、刷新会话或换绑；改密与冻结后存量会话按 §10.4 时效失效。
4. 应用禁用后不得签发新 Token。
5. 注销不可恢复，旧 UID 仅作为墓碑与映射存在。
6. 批量账号合并只发生在受控迁移流程中并全程留审计；日常登录不得自动合并账号（防回收号码接管旧账号）。
7. 前台用户账号与管理员账号不得互相转换或混用。
8. 所有管理操作必须留审计。

## 5. 详细能力清单

优先级定义：

- **P0**：首个统一登录上线必备，未交付不得对外切换流量。
- **P1**：规模化或增强能力，按小节登记的启用触发排期。

实现策略取值：**自建**（语义与状态机由平台拥有）、**复用**（采用成熟开源组件，平台负责选型与配置）、**集成**（依赖外部服务，平台保留断言与降级策略）。

本档共 53 项能力：自建 43、复用 8、集成 2；协议端点、Token 签发校验、密码哈希等协议与密码学内容**零自建**，全部由开源授权服务器或成熟库承载。本档不含 P2 项，更远期能力见归档参考架构。

- 前端权限只用于界面展示，后端必须再次校验。
- 平台管到「谁能进哪个后台、是什么角色」；各后台内部的菜单、按钮级细粒度权限首期由各后台自行维护。
- `CAP-AUTHZ-008` 启用触发：出现外包/临时人员需要限时后台权限的场景。

## 6. 关键业务流程

本章只描述编排顺序与关键判定点；能力定义见 §5，时限数值见 §10.4。

### 6.1 新用户注册与首次登录

主责能力：`CAP-AUTH-001/002/007`、`CAP-ID-001/003`、`CAP-SSO-001/002/003`。

~~~mermaid
sequenceDiagram
    participant U as 用户
    participant A as 前台应用
    participant I as 用户中心
    participant M as 消息通道

    U->>A: 发起注册/登录
    A->>I: 跳转统一登录页（携带 Client 与回调）
    I->>M: 发送短信验证码
    M-->>U: 验证码
    U->>I: 提交手机号与验证码
    I->>I: 校验频控与验证码
    I->>I: 创建 Global User 与 Identity
    I-->>A: 返回授权码
    A->>I: 授权码换取 Token
    A-->>U: 完成登录
~~~

- 注册与登录运行在服务端登录会话上，「已验证」状态不得由客户端参数声明。
- 已注册用户走同一入口直接登录，不区分注册/登录两个页面。

### 6.2 单点登录（已有会话）

主责能力：`CAP-SSO-005/007`。

1. 用户在应用 B 点击登录，跳转授权端点；平台校验 Client 与回调，发现已有有效统一登录会话。
2. 按应用声明的认证新鲜度要求决定：直接免密发码，或要求重新认证（后台类应用可要求每次输密码）。
3. 返回授权码，应用 B 换取 Token，全程无需再次输入凭证。

### 6.3 退出登录

主责能力：`CAP-SSO-006/008`。

1. 应用内退出：撤销该应用的 Token 与本地会话，统一登录会话保留（下次静默登录）。
2. 全局退出：撤销统一登录会话与该用户全部应用 Token，下次进入任何应用均需重新认证。
3. 短期 Access Token 通过撤销表或等待自然过期失效，最大残留时效见 §10.4。

### 6.4 找回密码

主责能力：`CAP-AUTH-005/008/009`、`CAP-SSO-008`。

通过手机验证码（或邮箱）验证身份，全程受频控与图形验证码约束；重置后撤销该用户全部会话与 Token；发送改密通知并记录审计。

### 6.5 换绑手机号

主责能力：`CAP-ID-005/006`、`CAP-AUTH-008`。

验证当前登录态与原手机号（原手机不可用时进入找回流程）→ 验证新手机号并检查占用与黑名单 → 执行换绑并通知新旧手机号；旧号码进入隔离期并记录历史归属。

### 6.6 冻结与应用封禁

主责能力：`CAP-ID-007`、`CAP-OPS-002/003`、`CAP-SSO-008`。

- 全局冻结：平台执行，阻止一切应用登录并吊销全部会话，用于安全事件。
- 应用封禁：仅修改该应用的 Membership 状态，其他应用不受影响。
- 管理员账号停用：独立执行，立即终止后台会话。

### 6.7 注销

主责能力：`CAP-ID-008`、`CAP-OPS-002`。

1. 强身份验证与影响提示（各业务系统的未完成事项由业务系统返回）。
2. 进入冷静期（时长见 §10.4），期内可撤回。
3. 执行：全局登出、标识解绑、UID 墓碑登记，通知各业务系统删除其数据副本。
4. 各业务系统返回处理结果，平台留存完成记录；注销后不可恢复。

### 6.8 存量账号迁移与合并

主责能力：`CAP-ACCESS-005`、`CAP-ID-009`，完整规则见 §11。要点：按手机号匹配建立映射，无匹配创建新用户，冲突进人工队列不自动合并；密码旧哈希兼容验证、登录时透明升级；双轨运行、灰度切量、持续对账。

### 6.9 后台管理员登录与鉴权

主责能力：`CAP-AUTHZ-001~007`、`CAP-SSO-007`。

管理员在独立入口认证，获取短时效后台会话；每次操作经 RBAC 校验（角色 × 后台作用域），默认拒绝；业务子账号由业务管理员创建并授予有限权限，全程审计；管理后台上线后启用 MFA（§10.1）。

### 6.10 新应用接入

主责能力：`CAP-ACCESS-001/002`。

登记 Application 与 Client（回调地址、scope、环境）→ 测试环境联调走通登录、Token 校验、退出 → 上线审批后发放生产凭证；接入文档与示例随 Client 提供。

## 7. 系统交互边界

~~~mermaid
flowchart TB
    FE["前台系统 Web / App / 小程序"] --> G["统一认证 OIDC 端点"]
    BE["各后台系统"] --> G
    G --> SESSION["会话与 Token"]
    SESSION --> USER["用户、身份与资料"]
    G --> AUTHZ["后台权限"]
    ADMIN["平台/业务管理后台"] --> M["用户与权限管理"]
    M --> USER
    M --> AUTHZ
    USER --> EVENT["用户变更事件"] --> BIZ["各业务系统"]
~~~

业务系统接入约束（本节为唯一口径）：

- 只通过标准协议（OIDC/OAuth 2.0）与管理 API 接入；禁止直接读写用户中心数据库。
- 人类用户客户端一律使用授权码模式 + PKCE S256；禁止 Implicit 与密码模式（ROPC）；回调地址精确匹配；浏览器、移动端、小程序不得保存客户端密钥。
- ID Token 只用于确认认证结果，不得作为 API Access Token 使用。
- 业务后端必须校验 issuer、audience、签名、有效期与 scope；用户中心不在 Token 中放入不必要的个人敏感信息。
- 统一使用平台错误契约，不得把收敛后的错误改写为可枚举的具体原因。
- 业务本地保存的用户资料副本必须明确用途、字段和同步机制。
- 事件消费必须幂等，并支持按数据版本拒绝旧事件覆盖新数据。

## 8. 数据一致性与缓存策略

| 数据类型 | 一致性要求 | 原因 |
|---|---|---|
| 密码、身份绑定 | 强一致 | 防止旧凭证继续生效 |
| 全局冻结、Token 吊销 | 接近实时 | 属于安全控制面 |
| 后台角色与权限 | 实时或短缓存（带版本失效） | 防止权限变更延迟放行 |
| 普通资料 | 最终一致（事件同步） | 可用性优先 |
| Membership（业务成员状态） | 平台写入、事件同步 | 避免跨系统双写 |
| 审计日志 | 仅追加 | 不允许覆盖 |

业务系统（下游）需具备：基于事件 ID 的幂等消费、失败重试、定期对账、事件丢失后的主动补拉能力。

## 9. 管理角色

| 角色 | 管理范围 |
|---|---|
| 平台管理员 | 平台自身：应用接入、Client、全局策略、账号处置、权限授予 |
| 业务管理员 | 本业务系统的用户成员、业务角色与业务配置 |
| 业务子账号 | 被授予的有限操作权限 |
| 审计查看（可由平台管理员兼任） | 只读查看审计记录 |

高权限账号不得多人共享；管理后台上线后强制 MFA（见 §10.1）；全部管理操作留审计。

## 10. 核心非功能要求

### 10.1 安全

- 密码采用现代自适应哈希（由所选组件默认提供），参数可升级。
- 验证码、Token、密码哈希不得出现在日志、审计与错误信息中。
- 手机号、邮箱在管理后台按角色脱敏展示。
- 管理后台上线后强制 MFA；上线前以强密码策略 + 登录频控 + IP 限制过渡。
- 前台用户库与管理员账号库分库或分安全域存储。

### 10.2 可用性

- 认证链路避免依赖非核心服务。
- 已签发 Token 可由业务本地短期校验，降低平台故障影响面；本地校验窗口即吊销时效上限。
- 短信通道故障时启用备用供应商或降级登录方式（密码/邮箱），降级方向预先登记。
- 平台多实例部署，数据库主从与备份。

### 10.3 性能与容量

- 按日活用户、并发登录峰值、验证码量、Token 签发量估算容量。
- Token 只携带必要声明，不塞完整资料与权限列表。

### 10.4 服务等级基线

以下为建议基线，阶段 0 与各业务方确认后作为验收依据：

| 指标 | 建议基线 |
|---|---|
| 认证与 Token 端点可用性 | ≥ 99.9%（月度） |
| Token 签发延迟 P95 | ≤ 300ms |
| 冻结/改密后存量会话失效 | ≤ 5 分钟 |
| 短信验证码送达率 | ≥ 98% |
| 管理后台可用性 | ≥ 99.5% |
| 注销冷静期 | 7 天（可配置） |

## 11. 存量系统迁移

迁移不是一次性脚本，而是一组受控能力：

| 能力 | 说明 |
|---|---|
| 旧 ID 映射 | 保存旧系统用户 ID 与 UID 的映射，迁移后对账用 |
| 数据清洗 | 手机、邮箱规范化，异常值与重复值识别 |
| 账号匹配规则 | 以手机号（其次邮箱）为匹配键；冲突一律进人工队列 |
| 密码迁移 | 旧哈希兼容验证、登录时透明升级，不可迁移的强制重置 |
| 双轨运行 | 新旧认证有限期并行，登记例外与退役时间 |
| 灰度切换 | 按系统、按用户比例逐步切量，随时可回滚 |
| 差异对账 | 比对用户、身份、状态差异，差异清零或已处置才算完成 |
| 用户沟通 | 需要改密、重新绑定时明确通知 |

### 11.1 推荐迁移顺序

1. 盘点各前台系统的用户表、登录方式、ID、资料与状态；确定接入顺序：先小系统试点，后核心系统。
2. 先接统一认证协议（新注册走平台），再迁移存量账号。
3. 按手机号匹配建立映射，冲突人工处理。
4. 双轨运行，灰度切量，持续对账。
5. 单个系统切换完成后停用其本地注册能力；全部系统迁移完成后下线旧认证，双轨例外清零。

### 11.2 后台账号收编

- 各后台系统的存量管理员账号统一收编到管理员账号体系，按后台系统建立作用域。
- 员工名单以人事或部门指定名单为准，逐账号确认归属与角色后迁移。
- 收编完成后，各后台本地账号停用，仅保留平台账号入口。

## 12. 分期建设路线

### 阶段 0：选型与骨架（决策冻结）

- 完成 §14 全部决策并记录；冻结授权服务器选型：OpenIddict / Duende IdentityServer / Keycloak 逐项比选（许可、能力、团队栈、运维形态）。
- 工程骨架：健康检查、配置加载、结构化日志、错误契约中间件；数据库迁移工具链与可回滚的初始 Schema。
- 最小链路打通：授权码登录 → 签发 Token → 受保护接口校验 → 退出，全部走选定组件。
- 出口条件：最小链路在测试环境跑通；决策记录、Schema、骨架入版本库。

### 阶段 1：前台统一登录上线

- §5.1/§5.2/§5.3 的全部 P0：注册、验证码与密码登录、统一登录页、OIDC 端点、JWT 与 JWKS、单点登录与退出、改密冻结吊销、注销流程。
- 公共资料与头像；管理后台最小版（用户查询、处置、审计）；验证码消息通道（含频控与送达监控）；基础监控告警。
- 第一个前台系统完成接入；存量迁移工具就绪并启动首个迁移。
- 出口条件：一个真实前台系统全量走统一登录；协议一致性测试通过；改密/冻结后 Token 失效达到 §10.4 时效。

### 阶段 2：后台统一与多系统接入

- §5.4 全部 P0：管理员账号体系、RBAC、后台作用域、管理员分级、权限目录与审计。
- 其余前台系统接入与存量迁移推进；基础监控完善。
- 出口条件：全部后台系统使用统一管理员认证；两个以上前台系统完成迁移。

### 阶段 3：增强与收尾

- 第三方登录（微信）、邮箱登录、多端会话管理与互踢、安全通知；用户变更事件 Webhook、业务扩展字段、临时授权、资料变更历史。
- 旧系统认证全部退场，双轨结束。
- 出口条件：旧账号体系下线，迁移对账差异清零。

## 13. 验收要点

验收项必须可判定：引用能力编号、给出验证方法与证据形式。

| 能力编号 | 验收项 | 验证方法 | 证据形式 |
|---|---|---|---|
| `CAP-ID-001` | UID 唯一、稳定、不可修改、不可复用 | 自动化：创建/注销后 ID 复用负向用例 | 测试报告 |
| `CAP-ID-002` | 并发绑定同一手机号仅一个成功，规范化跨服务一致 | 自动化：并发与属性用例 | 并发测试报告 |
| `CAP-ID-008` | 注销冷静期可撤回；终态不可恢复；墓碑防复用 | 自动化：状态机用例 | 状态机测试报告 |
| `CAP-ID-009` | 合并冲突进人工队列并留审计，不静默合并 | 自动化：冲突负向用例 + 审计记录抽查 | 负向测试 + 审计样本 |
| `CAP-AUTH-008` | 错误账号、错误密码、冻结账号响应无可利用枚举差异 | 自动化：负向用例 + 响应时差对比 | 负向测试报告 |
| `CAP-SSO-002/003` | 授权码 + PKCE 流程符合 OIDC 规范，禁用弱流程 | 一致性测试套件 + 负向用例（改回调、重放授权码） | 门禁报告 |

## 14. 待决策问题

以下问题必须在阶段 0 结束前形成结论并记录（建议以 ADR 形式入版本库）：

1. 授权服务器选型：OpenIddict、Duende IdentityServer 还是 Keycloak？比选维度：许可成本、协议能力、.NET 栈匹配、运维形态。
2. 前台用户与管理员账号是否分库存储，还是同库分安全域？
3. 手机号唯一性作用域：全局唯一？（多前台系统共用同一手机号体系的前提）
4. Subject 策略：公司内部系统默认共享全局 Subject，还是按应用隔离？未来是否需要防跨应用关联？
5. 各前台系统存量账号合并规则：手机号匹配的优先级、无手机号账号如何处理、冲突人工流程由谁负责？
6. 确认会员等级、积分、订单等业务数据留在业务系统，不进用户中心。
7. 第三方登录范围：哪些微信 AppID 需要接入？是否绑定开放平台使用 unionid 做跨应用识别？
8. Token 校验模式：业务后端本地校验（JWT）为主，哪些应用需要内省？
9. 短信/邮件供应商选型与备援策略？发送频控阈值？
10. 部署形态与可用性目标：单实例可接受还是必须多实例高可用？数据库主从方案？
11. 密码策略（长度、复杂度、历史口令）与登录频控阈值。
12. 各后台系统存量管理员账号的员工名单来源与收编节奏。

## 15. 参考标准与术语

### 15.1 参考标准

- OpenID Connect Core / Discovery：统一身份认证与用户身份声明。
- OAuth 2.0、RFC 9700（OAuth Security BCP）：应用访问授权与安全基线。
- RFC 8725：JWT 算法、类型与密钥使用基线。
- RFC 7636（PKCE）：授权码拦截防护，仅允许 S256。
- RFC 7009 / RFC 7662：Token 撤销与内省。
- RFC 8414：Authorization Server Metadata。
- JWT / JWK：令牌声明与签名密钥发布。

暂不建设、保留演进方向（见归档参考架构）：WebAuthn/Passkey、SCIM、SAML、FAPI、多租户。

### 15.2 术语表

| 术语 | 定义 |
|---|---|
| SSO（单点登录） | 一次认证后在多个应用间复用登录态 |
| 单点退出 | 撤销统一登录会话及全部应用 Token 的全局退出 |
| RBAC | 基于角色的访问控制：管理员—角色—权限—资源 |
| 后台作用域 | 权限的作用边界，每个后台系统一个独立权限空间 |
| 墓碑（tombstone） | 标识或账号被释放、注销后保留的最小不可逆记录，防止历史被继承 |
| 双轨运行 | 迁移期新旧认证并行的阶段，需明确权威侧与退役时间 |
| 灰度切量 | 按系统、按用户比例逐步把流量切到新认证的过程 |

其余领域术语（UID、Subject ID、External ID、Membership 等）见 §4。
