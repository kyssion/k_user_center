# 统一身份与访问平台数据库设计总纲

> 文档状态：候选设计基线；算法与密码合规开放项关闭并完成 PostgreSQL 实跑后最终冻结
> 数据库基线：PostgreSQL  
> 规范来源：[能力地图](./能力地图.md)、[统一身份与访问平台建设与验收蓝图](./统一身份与访问平台建设与验收蓝图.md)  
> 核心边界：数据库负责数据存储、关系标识、基础约束、唯一性、原子并发、技术时间和部署身份的粗粒度访问控制；最终用户、管理员、租户、数据范围、领域 Owner、业务状态机、风险、审批与流程编排属于用户中心代码职责。
> 关系策略：数据库不创建 Foreign Key；所有逻辑关系必须在字段 Comment、本文档和逻辑关系清单中明确，目标有效性和作用域校验在 `docs/implementation` 中展开。
> 文档范围：本文档及 `docs/database` 只定义业务模型、持久化事实、逻辑关系、数据库硬边界和数据库验收，不定义代码结构、接口、Handler、Repository 或框架用法；命令、事务、权限和校验契约见 `docs/implementation`。

## 1. 设计结论

1. 使用单一业务 Schema：`iam`。
2. 最终目标态共规划 113 张表，不按建设阶段拆减，不按一个 `CAP-*` 建一张表。
3. 不创建数据库 Foreign Key、业务 Trigger、业务 Function、Stored Procedure、PostgreSQL Enum 或表达业务语义的 View。
4. 数据库保留 Primary Key、Unique、必要的基础 Check、索引、分区、默认值、Comment 和面向部署身份的粗粒度技术权限。
5. 所有 `*_id` 只是逻辑引用；数据库只保存关系标识和查询索引，目标存在、租户一致、状态允许、权限满足和并发处理属于后续实施职责。
6. 配置类能力统一存入版本化 `configuration_versions`，使用 `config_type + schema_version + payload jsonb` 承载，避免为每一种策略单独建表。
7. 跨事务流程统一使用 `operations + operation_steps`；不为注销、合并、换绑、恢复等流程分别建设数据库工作流引擎。
8. 所有领域状态使用 `varchar` 保存；数据库不维护状态全集、初态、转换边和终态，这些内容在 `docs/implementation` 和自动化验收中定义。
9. `created_at`、`recorded_at` 等技术时间由数据库生成；`updated_at` 在应用更新 SQL 中使用数据库时间刷新，不使用更新时间 Trigger。
10. 聚合根和跨系统引用 ID 由应用生成；纯内部高频从属记录可以使用数据库 Identity。
11. 每张逻辑表必须映射到一个主要业务模型和一个权威持久化域；多域引用同一表不代表多方都可直接维护其生命周期，具体共享边界以 `业务模型与持久化边界清单.md` 为准。
12. 权威事实、Outbox、Audit 和幂等结果的共同提交属于数据库持久化原子性契约；数据库不负责流程编排，但后续实现不得拆散已确认的原子边界。
13. 数据库账号和角色只区分 Owner、Migration、普通运行时、只读、敏感数据、审计和 Worker 等技术身份；不映射最终用户、管理员角色、租户、业务权限或逐行 Owner。
14. 业务授权、租户隔离、领域写入权和不可变/追加语义以用户中心的 PEP、应用服务、仓储和命令接口为权威实现；基线不依赖 RLS、数据库 Policy、`SECURITY DEFINER`、按租户建账号/Schema 或存储过程承载业务授权。审计、敏感存储和选定的高价值追加证据表可以额外使用粗粒度 Grant 防御纵深，但必须保留代码契约、可迁移实现和独立测试，不得成为业务正确性的唯一来源。

## 2. 数据库持久化边界与非数据库职责

| 内容 | 数据库职责 | 非数据库职责；后续实施必须关注 |
|---|---|---|
| 数据类型和长度 | 定义并拒绝非法结构 | 提供符合契约的数据 |
| 主键和唯一性 | PK、Unique、唯一索引 | 生成 ID、处理冲突错误 |
| 逻辑关系 | 保存 `*_id`、建立查询索引、写 Comment | 校验引用存在、类型正确、租户一致 |
| 状态 | 保存状态字符串及变更时间 | 定义状态全集、合法转换和前置条件 |
| 并发 | 保存 `row_version`，执行条件更新 | 传入 expected version、处理冲突和重试 |
| 安全水位 | 保存 epoch/watermark | 决定何时递增、传播和失败关闭 |
| 时间 | 生成创建、记录和数据库更新时间 | 计算业务有效期、冷静期和保护期 |
| 敏感数据 | 保存密文、摘要、盲索引和 Key 引用 | 规范化、加解密、HMAC、脱敏和密钥调用 |
| 幂等 | 唯一保存调用方、幂等键和请求摘要 | 判定相同请求、返回原结果或冲突 |
| Outbox/Audit | 与领域数据同事务持久化 | 生成事件、审计内容和投递语义 |
| 共享表权威 | 保存统一模型、版本、并发边界和必要的技术隔离 | 由代码中的唯一权威域或实例 Owner 控制读写，不建立影子状态和未声明双写 |
| 业务权限与风险 | 保存策略版本、决策和证据；数据库角色只隔离技术身份 | 执行最终用户/管理员授权、PDP/PEP、租户与数据范围校验、风险计算和审批判断 |
| 删除与保留 | 保存状态、证明和保留信息 | 编排下游删除、匿名化、Legal Hold 和对账 |

## 3. 无 Foreign Key 的关系规则

### 3.1 非数据库写入前校验责任

每个包含逻辑引用的写命令必须在同一应用事务上下文中完成：

1. 查询目标记录是否存在。
2. 校验目标对象类型与作用域。
3. 校验 `business_line_id`、`tenant_id`、`organization_id` 是否一致。
4. 校验目标状态是否允许建立关系。
5. 校验操作者权限、保证等级、风险和审批。
6. 使用目标和聚合根 `row_version` 执行并发保护。
7. 写入领域数据、幂等结果、Outbox 和 Audit Outbox。

### 3.2 删除与终态处理

- 不依赖级联删除。
- 主体、标识、认证器、Grant、Consent、审计和事件优先使用终态、解绑、匿名化或墓碑，而不是直接删除。
- 纯技术从属记录由代码按明确顺序清理。
- 历史、审计、Outbox、撤销、迁移映射和删除证明可在主对象清除后继续保存逻辑引用。
- 定期执行孤儿关系扫描，并将结果作为发布和运行门禁证据。

### 3.3 逻辑关系登记

数据库基线必须维护机器可读取的逻辑关系索引，至少包含：

```text
source_table
source_column
target_table
target_column
relation_type
column_comment
```

`required`、`tenant_guard`、`delete_behavior`、锁定策略和校验 Owner 属于 `docs/implementation`；数据库文档只负责声明稳定的来源、目标和关系类型，不虚构尚未完成的应用设计。

数据库字段 Comment 必须写明逻辑目标，例如：

```sql
COMMENT ON COLUMN iam.sessions.user_id IS
'逻辑引用 iam.global_users.id；数据库不创建外键。写入前由 SESSION 领域服务校验用户存在、生命周期、安全冻结和租户上下文。';
```

## 4. Schema、角色和数据库对象

### 4.1 Schema

```text
iam       # 113 张业务表及其索引、约束和分区
iam_meta  # Migration 技术账本；不属于业务模型和 113 张业务表
```

首期和目标态均使用单一业务 Schema `iam`；`iam_meta` 仅用于记录已提交 Migration 的版本、脚本名、SHA-256、时间和执行登录身份。敏感表、审计表与选定的高价值追加证据表可通过独立数据库角色、表级或列级 Grant 形成技术防御纵深；这些 Grant 不承载最终用户、租户、领域 Owner 或业务状态的授权判断。只有明确出现独立备份、独立密钥域或独立实例要求时再拆分业务 Schema 或实例。

所有运行时技术角色均不得拥有 `DELETE`。业务删除、匿名化、终态和保留期由代码编排；物理清理、分区退役和依法保留后的删除只允许通过单独审批的版本化 Migration 或维护流程执行。该限制是部署身份的粗粒度安全边界，不把业务权限或删除状态机下沉到数据库。

### 4.2 数据库角色

| 角色 | 用途 |
|---|---|
| `iam_owner` | Schema 和数据库对象所有者，禁止应用运行时使用 |
| `iam_migrator` | 供部署登录身份继承的版本化迁移组角色；自身禁止登录 |
| `iam_app_rw` | 普通运行时持久化读写；不表达终端用户、租户或领域业务权限 |
| `iam_app_ro` | 技术只读查询；业务数据可见性仍由代码判定 |
| `iam_sensitive_rw` | 读取或写入凭证密文、机器凭证等敏感数据 |
| `iam_audit_writer` | 仅追加审计数据 |
| `iam_audit_reader` | 受控审计查询，不可修改 |
| `iam_ops` | Outbox、Webhook、消息投递、目录同步和迁移等技术 Worker 持久化；具体可操作的实例和状态由代码限制，分区 DDL 由版本化 Migration 执行 |

运行时登录身份可以按最小技术职责组合上述组角色，但必须在部署清单中显式登记。例如消息或 Webhook Worker 使用 `iam_ops`，确需读取目标密文时再叠加 `iam_sensitive_rw`；普通服务不得因为少数敏感操作而整体获得敏感读取能力。任何运行时身份均不得继承 `iam_owner` 或 `iam_migrator`。

数据库角色组合只是部署和存储安全边界，不是用户中心的业务授权模型。代码必须在进入仓储前校验 Actor、Subject、Tenant、数据范围、领域 Owner、状态、保证等级、风险和审批，并默认拒绝。不为每个最终用户、管理员角色、租户或领域创建数据库账号或动态 Grant。

运行时身份的最小组合契约：

| 运行时身份类型 | 必须继承 | 权限目的 |
|---|---|---|
| 普通领域写入方 | `iam_app_rw` + `iam_audit_writer` | 写入领域事实、Outbox 和仅追加审计；不读取凭证、验证码或 Token 摘要 |
| AUTH/OAP 敏感事务写入方 | `iam_app_rw` + `iam_sensitive_rw` + `iam_audit_writer` | 对 Challenge、恢复码、授权码、Refresh/Access Token 元数据执行受控读取与 INSERT/UPDATE 闭环 |
| 凭证与机器凭证管理方 | `iam_sensitive_rw` + `iam_app_rw` + `iam_audit_writer` | 维护凭证材料，并写入相关认证器、主体和审计事实 |
| 队列、投递与迁移 Worker | `iam_ops`；确需读取密文时叠加 `iam_sensitive_rw` | 只处理已登记运行队列、投递、同步和迁移状态 |
| 审计查询方 | `iam_audit_reader`；需要普通业务上下文时叠加 `iam_app_ro` | 只读审计与受控业务查询，不得修改历史证据 |

`iam_app_rw` 与 `iam_sensitive_rw` 对 `recovery_codes`、`auth_challenges`、`authorization_codes`、`refresh_token_instances`、`access_token_records` 采用拆分授权：前者可写不可读敏感摘要，后者可读但不可单独改写。这是敏感存储的技术隔离，不代替业务授权、租户校验或状态机。部署身份必须按上表组合，`verification/007_permissions_check.sql` 只验证数据库技术身份的正向可用性和负向隔离。

平台接入方业务系统不得直接获得数据库账号或访问 `iam` Schema；只有用户中心内部部署身份按上述技术职责连接。

### 4.3 明确不创建的对象

- Foreign Key。
- 业务 Trigger。
- 自动更新时间 Trigger。
- 业务 Function 和 Stored Procedure。
- PostgreSQL Enum。
- 状态字典表。
- 表达“有效用户”“有效授权”等业务含义的 View 或 Materialized View。
- 在数据库内部执行加密、风险计算、权限决策或流程编排的例程。
- 为最终用户、管理员角色、租户或业务领域动态创建的数据库账号、Schema 或 Grant 体系。
- 以 RLS、数据库 Policy、`SECURITY DEFINER` 或存储过程作为业务权限、租户隔离、领域 Owner 或状态转换规则的权威或唯一实现。

## 5. ID、时间、版本和公共字段

### 5.1 ID 生成

| 类型 | 推荐方式 |
|---|---|
| 聚合根内部 ID | 应用生成 UUIDv7，数据库类型 `uuid` |
| Global User ID、Subject ID 等公开 ID | 应用生成随机、不可推断的独立标识 |
| Event、Operation、Session、Grant ID | 应用生成，保证事务提交前可引用 |
| 纯内部从属或追加记录 | 可使用 `bigint GENERATED ALWAYS AS IDENTITY` |
| 外部 ID | 保留外部原始值或加密值，只作为映射键 |

内部有序 ID 不得出现在对外 API、Token、URL、Webhook 和业务日志中。

### 5.2 技术时间

```sql
created_at  timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,
updated_at  timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,
recorded_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP
```

- `created_at`：数据库插入时间。
- `updated_at`：插入时数据库生成；更新 SQL 显式执行 `updated_at = CURRENT_TIMESTAMP`。
- `occurred_at`：业务事件实际发生时间，由代码传入。
- `recorded_at`：事件或审计实际落库时间，由数据库生成。
- 业务有效期、Token TTL、冷静期、保护期、等待期由代码计算后写入。

### 5.3 乐观锁和安全水位

```sql
row_version          bigint NOT NULL DEFAULT 0,
user_security_epoch  bigint NOT NULL DEFAULT 0,
client_security_epoch bigint NOT NULL DEFAULT 0
```

更新示例：

```sql
UPDATE iam.global_users
SET lifecycle_state = @new_state,
    row_version = row_version + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE id = @id
  AND row_version = @expected_version;
```

数据库只执行原子条件更新；是否允许转换由代码决定。

### 5.4 聚合根公共字段

聚合根按需要包含：

```text
id
public_id
state
state_reason
state_changed_at
row_version
created_at
updated_at
```

不机械要求每张表都包含全部公共字段。不可变历史、关联表、追加日志和分区记录只保留其实际需要的列。

## 6. 敏感数据存储

### 6.1 标准字段

```text
value_ciphertext
blind_index
normalization_version
encryption_algorithm
encryption_version
key_id
value_fingerprint
```

### 6.2 存储要求

- 手机、邮箱等可等值检索标识：随机化密文 + HMAC 盲索引。
- 密码：现代自适应哈希及算法参数，不保存可解密密码。
- TOTP、第三方 Token 等秘密：应用加密后保存密文和 KMS Key ID。
- Passkey：保存 Credential ID 摘要、公钥和认证器元数据。
- Access Token、Refresh Token、授权码、验证码、恢复码：只保存摘要或必要元数据。
- 私钥：只保存 KMS/HSM 引用，不保存私钥明文或可导出副本。
- 日志、事件、审计和追踪禁止出现密码、验证码、完整 Token 和私钥。

## 7. 最终表目录

### 7.1 通用技术设施：6 张

| 表 | 核心数据 | 说明 |
|---|---|---|
| `idempotency_records` | caller、idempotency key、request hash、Operation、结果、过期时间 | 保证同键同请求结果稳定，同键不同请求由代码判定冲突 |
| `operations` | operation type/state、调用作用域、幂等键、请求摘要、能力、Saga、策略版本、Subject、Actor、Tenant、当前步骤、不可逆边界、结果 | 通用异步和跨域流程载体；创建快照不可被步骤改写 |
| `operation_steps` | step code/state、attempt、checkpoint、输入输出摘要、错误 | Operation 从属步骤；无 FK，由代码校验 Operation |
| `outbox_events` | event id/type/schema、Producer、Subject/Actor 标识类型、业务线、发生时间、数据版本、Trace/因果、敏感级别、payload、publish state | 与领域数据同事务写入；核心事件信封使用独立字段 |
| `inbox_messages` | consumer、event id、处理状态、结果 | 消费幂等和乱序保护 |
| `audit_events` | Actor、Subject、Tenant、Action、Object、前后摘要、审批、Trace | 追加写入，逻辑引用不建 FK |

### 7.2 身份主体与标识：7 张

| 表 | 核心数据 | 说明 |
|---|---|---|
| `global_users` | internal ID、Global User ID、正式/Guest 类型、生命周期、独立认证锁定、独立安全冻结、Guest 到期、security epoch | 全局用户主体，不保存业务会员状态 |
| `user_subjects` | user、client/audience、pairwise subject、生成版本、退役时间、当前占位、CAS | 追加式对外 Subject 映射，保留轮换历史 |
| `identifiers` | type、scope、ciphertext、blind index、normalization version、验证信息 | 手机、邮箱、用户名等标识数据 |
| `identifier_claims` | scope、type、blind index、identifier、owner | 当前唯一性占用；Unique 约束保证单一占用 |
| `identifier_bindings` | identifier、user、绑定解绑时间、来源、原因 | 保存历史归属和墓碑关系 |
| `user_identities` | user、identity type、identifier/provider、external stable key、state | 本地、社交和企业登录身份 |
| `user_aliases` | alias type/value、canonical user、来源、状态 | 合并账号、旧 UID 和历史主体映射 |

### 7.3 认证器与认证：10 张

| 表 | 核心数据 | 说明 |
|---|---|---|
| `authenticators` | user、type、state、assurance metadata、登记/替换信息 | 认证器生命周期由代码控制 |
| `credential_materials` | authenticator、material type、hash/ciphertext/public material、algorithm、key | 凭证安全数据 |
| `password_history` | user/authenticator、password hash、algorithm、created time | 历史口令事实 |
| `recovery_code_batches` | user、batch version、state、created/expired time | 恢复码批次 |
| `recovery_codes` | batch、code hash、used time、state | 单次恢复码 |
| `auth_challenges` | purpose、client、subject/target、token hash、attempt、expiry、state | 短信、邮件、Magic Link 等 Challenge |
| `login_transactions` | request context、client、subject、risk snapshot、state、expiry | 服务端权威登录事务 |
| `login_transaction_steps` | transaction、factor/consent step、evidence、state | 已完成步骤和证据摘要 |
| `authentication_contexts` | IAL/AAL/FAL、acr、amr、auth time、risk、mapping version | 一次认证保证上下文 |
| `authentication_attempts` | client、subject hint、device、network、result、reason、occurred time | 高容量认证尝试记录 |

### 7.4 业务线、应用、租户和组织：14 张

| 表 | 核心数据 | 说明 |
|---|---|---|

## 8. 索引、唯一性和基础 Check

### 8.1 必须的唯一性

- `global_users.global_user_id`。
- `user_subjects(client_id, subject_id)` 的历史 Subject 唯一，以及 User/Client 最多一个当前占位。
- `identifier_claims(scope, identifier_type, blind_index)`。
- 外部身份源稳定键摘要。
- `oauth_clients.client_id`。
- `api_resources.audience`。
- `oauth_scopes.scope_code`。
- Membership 作用域内最多一个当前占位；终态后重新加入创建新记录。
- Challenge、授权码、Refresh Token、恢复码摘要。
- `idempotency_records(caller_scope, idempotency_key)`。
- `outbox_events.event_id`。
- `inbox_messages(consumer_id, event_id)`。
- Policy、Configuration、Event Schema 的 `(code/type, scope, version)`。
- `legacy_id_mappings(system_id, external_type, external_id_digest)`。

### 8.2 查询索引

- 每个逻辑引用 `*_id` 根据实际查询路径建立单列或组合索引。
- 优先建立组合索引，例如 `(user_id, state, expires_at)`，而非机械为所有 `*_id` 建单列索引。
- Tenant 作用域查询必须将 `tenant_id` 放入高选择性索引前缀或紧邻主查询字段。
- Outbox、Webhook、消息、Operation 建立 `(state, next_attempt_at)` 类工作队列索引。
- Audit、认证尝试、风险信号按主体、时间和事件类型建立分区内索引。
- JSONB 只对明确存在的查询路径建立 GIN 或表达式索引。

### 8.3 基础 Check

只保留不表达业务流程的稳定检查：

```text
row_version >= 0
security_epoch >= 0
attempt_count >= 0
expires_at IS NULL OR expires_at > created_at
数量和配额非负
摘要和 ID 长度合法
必要的字段互斥或至少一个存在
```

不使用 Check 表达状态转换、权限、风险、审批和租户业务规则。

## 9. 分区和容量

以下表按月使用 Range Partition：

- `audit_events`
- `authentication_attempts`
- `access_token_records`
- `authorization_decisions`
- `risk_signals`
- `workload_attestations`
- `webhook_deliveries`
- `webhook_delivery_attempts`
- `message_requests`
- `message_delivery_attempts`
- `migration_change_logs`

以下表使用 8 路 Hash Partition：

- `outbox_events`：分区键 `event_id`，以维持数据库级 `event_id` 全局唯一。
- `inbox_messages`：分区键 `(consumer_id, event_id)`，以维持数据库级消费幂等唯一。

技术原因：PostgreSQL Range 分区表的 Unique/Primary Key 必须包含时间分区键，无法同时维持跨月 `event_id` 全局唯一。Outbox/Inbox 优先保证正确性和幂等，时间保留通过时间索引与运维归档完成。

要求：

- 分区键统一使用 `created_at`、`recorded_at` 或 `occurred_at` 中明确选定的一列。
- 默认提前创建未来分区，禁止依赖运行时 Trigger 自动建分区。
- 活跃队列和历史归档使用不同索引策略。
- 删除旧分区前由代码或运维任务校验保留策略、Legal Hold 和审计要求。

## 10. Comment 规范

必须为 Schema、表、字段、关键索引、唯一约束和分区补充中文 Comment。

字段 Comment 至少说明：

1. 数据含义。
2. 权威域。
3. 是否为逻辑引用以及目标表字段。
4. 数据敏感级别和加密形态。
5. 空值含义。
6. 是否对外暴露。
7. 状态或业务规则属于哪个非数据库业务领域。

示例：

```sql
COMMENT ON TABLE iam.identifier_claims IS
'当前标识唯一性占用记录。数据库通过唯一索引维持同一作用域、类型和盲索引只有一个占用；占用创建、释放和隔离期判断由 ID 领域代码负责。';

COMMENT ON COLUMN iam.identifier_claims.identifier_id IS
'逻辑引用 iam.identifiers.id；数据库不创建外键。写入前由 ID 领域服务校验标识存在、规范化版本和当前状态。';
```

## 11. 初始化数据

Seed 只初始化稳定系统目录和待审批控制面候选版本：

- SP1、SP1-D、SP2、SP3、SP4、SP5 安全 Profile DRAFT 配置版本。
- 标准 OAuth Scope。
- 48 项稳定系统权限目录。
- 算法 Allowlist DRAFT。
- 完整 `SLO-*`、`TTL-*`、`TERM-*` DRAFT 基线。
- 默认数据分类和依赖失败策略 DRAFT；未批准的 Retention 数值不进入 Seed。
- 13 个核心安全通知模板 DRAFT。
- 28 个核心事件 JSON Schema DRAFT，并由 Seed 契约校验蓝图要求的核心事件名称。

控制面 Seed 不直接激活；后续实施完成审批和发布后才进入运行时有效集合。Seed 重复执行时同业务键内容摘要不一致必须失败，不允许 `DO NOTHING` 静默漂移。

禁止通过 Seed 创建：

- 用户和 Membership。
- 业务线和租户。
- 生产 Client。
- 管理员和 Break-glass 账号。
- 私钥、Client Secret 和机器凭证。

这些对象必须通过安全引导、控制面审批或运行期 API 创建。

## 12. 文件组织逻辑

### 12.1 总体原则

- SQL 按数据库执行依赖和存储领域组织。
- 业务规则 Markdown 按能力地图的 21 个域码组织。
- SQL Comment 是表字段说明的唯一权威来源。
- 数据库文档只保存业务模型与持久化边界；状态机和业务规则的执行设计由 `docs/implementation` 单独维护。
- 已执行的 Migration 不修改，只追加新 Migration。
- Migration 使用唯一 `NNN_name.sql` 版本且不得自行控制事务；Runner 将每个脚本的 SHA-256 和执行身份登记在独立技术 Schema，脚本与登记必须同事务提交，已登记脚本被修改、改名或移除时必须失败。
- 已有无迁移账本环境只能通过单独评审的基线登记接管，不得根据现存对象自动推断或静默认领历史。
- 生成的数据字典和检查报告不手工维护。

```text
            ├── 表字段索引清单.md
            └── 数据库对象检查报告.md
```

### 12.3 Migration 内部顺序

每个领域 SQL 文件固定使用以下顺序：

```text
1. 文件说明、依赖和对应能力域
2. CREATE TABLE
3. COMMENT ON TABLE
4. COMMENT ON COLUMN
5. Primary Key、Unique 和基础 Check
6. 本领域查询索引
7. 权限说明
```

不存在 Foreign Key 阶段。跨领域逻辑关系只进入 Comment、关系清单和孤儿扫描；具体有效性校验以 `docs/implementation` 为准。

### 12.4 SQL 与业务文档的映射

- SQL 文件按存储依赖组织，一张表只在一个 Migration 文件中定义。
- 业务规则按能力域组织，一个领域文档可以引用多个 SQL 文件中的表。
- `业务模型与持久化边界清单.md` 记录每个核心业务模型必须保存的事实、数据库硬边界和明确不属于数据库的职责。
- `逻辑关系与非数据库校验清单.md` 替代数据库 Foreign Key，记录数据库可识别的逻辑引用；`docs/implementation` 补充租户守卫、删除行为、锁和校验 Owner。
- `查询与索引契约.md` 登记安全关键和高频查询的完整过滤、所需索引与代码守卫；索引不表达业务授权或引用有效性。
- `需求编号与数据库持久化覆盖索引.md` 是需求编号到数据库持久化边界的覆盖索引，不是代码实施或验收矩阵，也不声明 Owner、Phase 或逐条自动化测试绑定。

## 13. 验证门禁

数据库验证脚本必须检查：

1. 113 张目标表全部存在。
2. 不存在 Foreign Key。
3. 不存在业务 Trigger、业务 Routine、PostgreSQL Enum、View 和 Materialized View。
4. 表和字段 Comment 完整。
5. 主键、唯一索引、工作队列索引和分区存在。
6. 敏感数据字段未设计为明文。
7. 运行时技术角色没有 DDL、物理 DELETE、越权读取或审计修改权限，且 AUTH/OAP 等组合身份具备完成受控持久化所需的正向技术权限；该门禁不证明业务授权正确。
8. 逻辑关系孤儿扫描无未登记异常。
9. 高容量表的未来分区已创建。
10. Migration 与 Seed 可在空数据库重复构建出一致 Schema；迁移账本中的版本、脚本名和 SHA-256 一致，已登记脚本发生漂移时必须失败。
11. Security Profile、SLO/时长、权限、模板和核心事件 Seed 满足蓝图基线且未静默漂移。
12. 113 张逻辑表均映射到业务模型和至少一个领域持久化范围；多领域复用表写入权威无冲突。

后续实施验收必须检查；具体测试设计不在数据库文档中定义：

1. 所有逻辑引用写入前均校验存在性和作用域。
2. 删除、匿名化、合并和迁移不会制造未处理孤儿记录。
3. 并发写入使用 `row_version` 或技术对象的原子 CAS。
4. 权威数据、Outbox、Audit 和幂等结果同事务提交。
5. 状态转换、不变量、租户隔离、撤销和恢复路径符合蓝图。
6. 业务授权、数据范围、领域 Owner 和追加/不可变写入契约通过代码负向测试、跨租户测试、越权命令测试和历史篡改测试验证，不以数据库 Grant 报告代替。

## 14. 后续实施约束

- 本文档是数据库总体设计的确认基线。
- 实际 DDL 必须以本文档的表目录、无 Foreign Key 原则和职责边界为依据。
- 新增表前必须证明其保存的是独立、稳定、需要查询或审计的数据事实，而不是把某个代码流程固化为表。
- 数据库领域文档中的“业务模型要求”和“后续关注”用于证明当前持久化模型能够支撑需求，不构成代码设计；代码实施遵守 `docs/implementation`。
- 后续实施文档可以决定类、接口、事务编排和外部组件，但不得改变已确认的权威事实、唯一性、CAS、追加写和敏感数据边界。
- 新增配置类型优先扩展 `configuration_versions`，只有存在独立唯一性、高频查询或固定法规证据结构时才新增专用表。
- 所有重要设计变更必须同步更新本文档、SQL Comment、逻辑关系清单和追踪矩阵。
