# 统一身份与访问平台数据库设计总纲

> 文档状态：设计确认稿  
> 数据库基线：PostgreSQL  
> 规范来源：[能力地图](./能力地图.md)、[统一身份与访问平台建设与验收蓝图](./统一身份与访问平台建设与验收蓝图.md)  
> 核心边界：数据库负责数据存储、关系标识、基础约束、唯一性、原子并发和技术时间；业务状态机、关联有效性、权限、风险、审批与流程编排由 .NET 代码负责。  
> 关系策略：数据库不创建 Foreign Key；所有逻辑关系必须在字段 Comment、本文档和代码仓储/领域服务中明确。

## 1. 设计结论

1. 使用单一业务 Schema：`iam`。
2. 最终目标态共规划 113 张表，不按建设阶段拆减，不按一个 `CAP-*` 建一张表。
3. 不创建数据库 Foreign Key、业务 Trigger、业务 Function、Stored Procedure、PostgreSQL Enum 或表达业务语义的 View。
4. 数据库保留 Primary Key、Unique、必要的基础 Check、索引、分区、默认值、权限和 Comment。
5. 所有 `*_id` 只是逻辑引用；代码必须校验目标存在、租户一致、状态允许、权限满足和并发版本正确。
6. 配置类能力统一存入版本化 `configuration_versions`，使用 `config_type + schema_version + payload jsonb` 承载，避免为每一种策略单独建表。
7. 跨事务流程统一使用 `operations + operation_steps`；不为注销、合并、换绑、恢复等流程分别建设数据库工作流引擎。
8. 所有领域状态使用 `varchar` 保存，合法状态、初态、转换边和终态由 C# Enum、领域服务和自动化测试维护。
9. `created_at`、`recorded_at` 等技术时间由数据库生成；`updated_at` 在应用更新 SQL 中使用数据库时间刷新，不使用更新时间 Trigger。
10. 聚合根和跨系统引用 ID 由应用生成；纯内部高频从属记录可以使用数据库 Identity。

## 2. 数据库与代码职责

| 内容 | 数据库职责 | .NET 代码职责 |
|---|---|---|
| 数据类型和长度 | 定义并拒绝非法结构 | 提供符合契约的数据 |
| 主键和唯一性 | PK、Unique、唯一索引 | 生成 ID、处理冲突错误 |
| 逻辑关系 | 保存 `*_id`、建立查询索引、写 Comment | 校验引用存在、类型正确、租户一致 |
| 状态 | 保存状态字符串及变更时间 | 定义状态全集、合法转换和前置条件 |
| 并发 | 保存 `row_version`，执行条件更新 | 传入 expected version、处理冲突和重试 |
| 安全水位 | 保存 epoch/watermark | 决定何时递增、传播和失败关闭 |
| 时间 | 生成创建、记录和数据库更新时间 | 计算业务有效期、冷静期和保护期 |
| 敏感数据 | 保存密文、摘要、盲索引和 Key 引用 | 规范化、加解密、HMAC、脱敏和密钥调用 |
| 幂等 | 唯一保存调用方、幂等键和请求摘要 | 判定相同请求、返回原结果或冲突 |
| Outbox/Audit | 与领域数据同事务持久化 | 生成事件、审计内容和投递语义 |
| 权限与风险 | 保存策略版本、决策和证据 | 执行 PDP/PEP、风险计算和审批判断 |
| 删除与保留 | 保存状态、证明和保留信息 | 编排下游删除、匿名化、Legal Hold 和对账 |

## 3. 无 Foreign Key 的关系规则

### 3.1 代码写入前校验

每个包含逻辑引用的写命令必须在同一应用事务上下文中完成：

1. 查询目标记录是否存在。
2. 校验目标对象类型与作用域。
3. 校验 `business_line_id`、`tenant_id`、`organization_id` 是否一致。
4. 校验目标状态是否允许建立关系。
5. 校验操作者权限、保证等级、风险和审批。
6. 使用目标和聚合根 `row_version` 执行并发保护。
7. 写入领域数据、幂等结果、Outbox 和 Audit Outbox。

### 3.2 删除与终态处理

- 不依赖级联删除。
- 主体、标识、认证器、Grant、Consent、审计和事件优先使用终态、解绑、匿名化或墓碑，而不是直接删除。
- 纯技术从属记录由代码按明确顺序清理。
- 历史、审计、Outbox、撤销、迁移映射和删除证明可在主对象清除后继续保存逻辑引用。
- 定期执行孤儿关系扫描，并将结果作为发布和运行门禁证据。

### 3.3 代码关系清单

后续代码实现必须维护机器可读取的关系元数据，至少包含：

```text
source_table
source_column
target_table
target_column
relation_type
required
tenant_guard
delete_behavior
validation_owner
```

数据库字段 Comment 必须写明逻辑目标，例如：

```sql
COMMENT ON COLUMN iam.sessions.user_id IS
'逻辑引用 iam.global_users.id；数据库不创建外键。写入前由 SESSION 领域服务校验用户存在、生命周期、安全冻结和租户上下文。';
```

## 4. Schema、角色和数据库对象

### 4.1 Schema

```text
iam
```

首期和目标态均使用单一 Schema。敏感表与审计表通过独立数据库角色、表级或列级 Grant 隔离；只有明确出现独立备份、独立密钥域或独立实例要求时再物理拆分。

### 4.2 数据库角色

| 角色 | 用途 |
|---|---|
| `iam_owner` | Schema 和数据库对象所有者，禁止应用运行时使用 |
| `iam_migrator` | 执行版本化迁移和初始化数据 |
| `iam_app_rw` | 普通领域表读写 |
| `iam_app_ro` | 受控只读查询 |
| `iam_sensitive_rw` | 读取或写入凭证密文、机器凭证等敏感数据 |
| `iam_audit_writer` | 仅追加审计数据 |
| `iam_audit_reader` | 受控审计查询，不可修改 |
| `iam_ops` | Outbox、Webhook、消息投递、分区和迁移运维 |

业务系统不得直接获得数据库账号或访问 `iam` Schema。

### 4.3 明确不创建的对象

- Foreign Key。
- 业务 Trigger。
- 自动更新时间 Trigger。
- 业务 Function 和 Stored Procedure。
- PostgreSQL Enum。
- 状态字典表。
- 表达“有效用户”“有效授权”等业务含义的 View 或 Materialized View。
- 在数据库内部执行加密、风险计算、权限决策或流程编排的例程。

## 5. ID、时间、版本和公共字段

### 5.1 ID 生成

| 类型 | 推荐方式 |
|---|---|
| 聚合根内部 ID | 应用生成 UUIDv7，数据库类型 `uuid` |
| Global User ID、Subject ID 等公开 ID | 应用生成随机、不可推断的独立标识 |
| Event、Operation、Session、Grant ID | 应用生成，保证事务提交前可引用 |
| 纯内部从属或追加记录 | 可使用 `bigint GENERATED ALWAYS AS IDENTITY` |
| 外部 ID | 保留外部原始值或加密值，只作为映射键 |

内部有序 ID 不得出现在对外 API、Token、URL、Webhook 和业务日志中。

### 5.2 技术时间

```sql
created_at  timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,
updated_at  timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,
recorded_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP
```

- `created_at`：数据库插入时间。
- `updated_at`：插入时数据库生成；更新 SQL 显式执行 `updated_at = CURRENT_TIMESTAMP`。
- `occurred_at`：业务事件实际发生时间，由代码传入。
- `recorded_at`：事件或审计实际落库时间，由数据库生成。
- 业务有效期、Token TTL、冷静期、保护期、等待期由代码计算后写入。

### 5.3 乐观锁和安全水位

```sql
row_version          bigint NOT NULL DEFAULT 0,
user_security_epoch  bigint NOT NULL DEFAULT 0,
client_security_epoch bigint NOT NULL DEFAULT 0
```

更新示例：

```sql
UPDATE iam.global_users
SET lifecycle_state = @new_state,
    row_version = row_version + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE id = @id
  AND row_version = @expected_version;
```

数据库只执行原子条件更新；是否允许转换由代码决定。

### 5.4 聚合根公共字段

聚合根按需要包含：

```text
id
public_id
state
state_reason
state_changed_at
row_version
created_at
updated_at
```

不机械要求每张表都包含全部公共字段。不可变历史、关联表、追加日志和分区记录只保留其实际需要的列。

## 6. 敏感数据存储

### 6.1 标准字段

```text
value_ciphertext
blind_index
normalization_version
encryption_algorithm
encryption_version
key_id
value_fingerprint
```

### 6.2 存储要求

- 手机、邮箱等可等值检索标识：随机化密文 + HMAC 盲索引。
- 密码：现代自适应哈希及算法参数，不保存可解密密码。
- TOTP、第三方 Token 等秘密：应用加密后保存密文和 KMS Key ID。
- Passkey：保存 Credential ID 摘要、公钥和认证器元数据。
- Access Token、Refresh Token、授权码、验证码、恢复码：只保存摘要或必要元数据。
- 私钥：只保存 KMS/HSM 引用，不保存私钥明文或可导出副本。
- 日志、事件、审计和追踪禁止出现密码、验证码、完整 Token 和私钥。

## 8. 索引、唯一性和基础 Check

### 8.1 必须的唯一性

- `global_users.global_user_id`。
- `user_subjects(client_id, subject_id)` 和用户到 Client 的唯一映射。
- `identifier_claims(scope, identifier_type, blind_index)`。
- 外部身份源稳定键摘要。
- `oauth_clients.client_id`。
- `api_resources.audience`。
- `oauth_scopes.scope_code`。
- Membership 作用域内的唯一关系。
- Challenge、授权码、Refresh Token、恢复码摘要。
- `idempotency_records(caller_scope, idempotency_key)`。
- `outbox_events.event_id`。
- `inbox_messages(consumer_id, event_id)`。
- Policy、Configuration、Event Schema 的 `(code/type, scope, version)`。
- `legacy_id_mappings(system_id, external_type, external_id_digest)`。

### 8.2 查询索引

- 每个逻辑引用 `*_id` 根据实际查询路径建立单列或组合索引。
- 优先建立组合索引，例如 `(user_id, state, expires_at)`，而非机械为所有 `*_id` 建单列索引。
- Tenant 作用域查询必须将 `tenant_id` 放入高选择性索引前缀或紧邻主查询字段。
- Outbox、Webhook、消息、Operation 建立 `(state, next_attempt_at)` 类工作队列索引。
- Audit、认证尝试、风险信号按主体、时间和事件类型建立分区内索引。
- JSONB 只对明确存在的查询路径建立 GIN 或表达式索引。

### 8.3 基础 Check

只保留不表达业务流程的稳定检查：

```text
row_version >= 0
security_epoch >= 0
attempt_count >= 0
expires_at IS NULL OR expires_at > created_at
数量和配额非负
摘要和 ID 长度合法
必要的字段互斥或至少一个存在
```

不使用 Check 表达状态转换、权限、风险、审批和租户业务规则。

## 9. 分区和容量

以下表按月使用 Range Partition：

- `audit_events`
- `authentication_attempts`
- `access_token_records`
- `authorization_decisions`
- `risk_signals`
- `workload_attestations`
- `webhook_deliveries`
- `webhook_delivery_attempts`
- `message_requests`
- `message_delivery_attempts`
- `migration_change_logs`

以下表使用 8 路 Hash Partition：

- `outbox_events`：分区键 `event_id`，以维持数据库级 `event_id` 全局唯一。
- `inbox_messages`：分区键 `(consumer_id, event_id)`，以维持数据库级消费幂等唯一。

技术原因：PostgreSQL Range 分区表的 Unique/Primary Key 必须包含时间分区键，无法同时维持跨月 `event_id` 全局唯一。Outbox/Inbox 优先保证正确性和幂等，时间保留通过时间索引与运维归档完成。

要求：

- 分区键统一使用 `created_at`、`recorded_at` 或 `occurred_at` 中明确选定的一列。
- 默认提前创建未来分区，禁止依赖运行时 Trigger 自动建分区。
- 活跃队列和历史归档使用不同索引策略。
- 删除旧分区前由代码或运维任务校验保留策略、Legal Hold 和审计要求。

## 10. Comment 规范

必须为 Schema、表、字段、关键索引、唯一约束和分区补充中文 Comment。

字段 Comment 至少说明：

1. 数据含义。
2. 权威域。
3. 是否为逻辑引用以及目标表字段。
4. 数据敏感级别和加密形态。
5. 空值含义。
6. 是否对外暴露。
7. 状态或业务规则由哪个 .NET 领域负责。

示例：

```sql
COMMENT ON TABLE iam.identifier_claims IS
'当前标识唯一性占用记录。数据库通过唯一索引维持同一作用域、类型和盲索引只有一个占用；占用创建、释放和隔离期判断由 ID 领域代码负责。';

COMMENT ON COLUMN iam.identifier_claims.identifier_id IS
'逻辑引用 iam.identifiers.id；数据库不创建外键。写入前由 ID 领域服务校验标识存在、规范化版本和当前状态。';
```

### 12.3 Migration 内部顺序

每个领域 SQL 文件固定使用以下顺序：


不存在 Foreign Key 阶段。跨领域的逻辑关系只进入 Comment、关系清单、代码校验和孤儿扫描。

### 12.4 SQL 与业务文档的映射

- SQL 文件按存储依赖组织，一张表只在一个 Migration 文件中定义。
- 业务规则按能力域组织，一个领域文档可以引用多个 SQL 文件中的表。
- `.NET业务规则与状态机实现清单.md` 作为代码实现总索引，记录命令、聚合根、读写表、前置条件、CAS、事件、错误码和测试。
- `逻辑关系与代码校验清单.md` 替代数据库 Foreign Key，记录每个逻辑引用的校验和删除策略。
- `需求能力表测试追踪矩阵.md` 维护 `CAP/REQ/INV/API/EVT/AT/SLO` 到表、代码模块和证据的映射。

## 13. 验证门禁

数据库验证脚本必须检查：

1. 113 张目标表全部存在。
2. 不存在 Foreign Key。
3. 不存在业务 Trigger、业务 Routine 和 PostgreSQL Enum。
4. 表和字段 Comment 完整。
5. 主键、唯一索引、工作队列索引和分区存在。
6. 敏感数据字段未设计为明文。
7. 运行时角色没有 DDL、越权读取或审计修改权限。
8. 逻辑关系孤儿扫描无未登记异常。
9. 高容量表的未来分区已创建。
10. Migration 与 Seed 可在空数据库重复构建出一致 Schema。

业务测试必须检查：

1. 所有逻辑引用写入前均校验存在性和作用域。
2. 删除、匿名化、合并和迁移不会制造未处理孤儿记录。
3. 并发写入使用 `row_version` 或技术对象的原子 CAS。
4. 权威数据、Outbox、Audit 和幂等结果同事务提交。
5. 状态转换、不变量、租户隔离、撤销和恢复路径符合蓝图。

## 14. 后续实施约束

- 本文档是数据库总体设计的确认基线。
- 实际 DDL 必须以本文档的表目录、无 Foreign Key 原则和职责边界为依据。
- 新增表前必须证明其保存的是独立、稳定、需要查询或审计的数据事实，而不是把某个代码流程固化为表。
- 新增配置类型优先扩展 `configuration_versions`，只有存在独立唯一性、高频查询或固定法规证据结构时才新增专用表。
- 所有重要设计变更必须同步更新本文档、SQL Comment、逻辑关系清单和追踪矩阵。
