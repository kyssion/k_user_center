# 统一身份与访问平台数据库设计总纲

> 文档状态：候选设计基线；算法与密码合规开放项关闭并完成 PostgreSQL 实跑后最终冻结
> 数据库基线：PostgreSQL  
> 规范来源：[能力地图](./能力地图.md)、[统一身份与访问平台建设与验收蓝图](./统一身份与访问平台建设与验收蓝图.md)  
> 核心边界：数据库负责数据存储、关系标识、基础约束、唯一性、原子并发、技术时间和数据库对象访问控制；业务状态机、关联有效性、业务授权求值、风险、审批与流程编排属于非数据库职责。
> 关系策略：同库、单一目标且目标键数据库唯一的直接引用使用 `RESTRICT` Foreign Key 保护存在性；多态、数组、外部系统和历史快照引用保留逻辑关系。租户、状态、授权和生命周期有效性始终由代码校验。
> 文档范围：本文档及 `docs/database` 定义业务模型、持久化事实、逻辑关系、数据库硬边界和数据库验收；`docs/implementation` 定义技术无关的命令、事务、CAS、幂等、事件和错误契约，仍不绑定具体 Handler、Repository、ORM 或框架。

## 1. 设计结论

1. 使用单一业务 Schema：`iam`。
2. 最终目标态共规划 113 张表，不按建设阶段拆减，不按一个 `CAP-*` 建一张表。
3. 数据库只创建结构性 `RESTRICT` Foreign Key 和统一 `updated_at` 技术 Trigger；不创建业务 Trigger、业务 Function、Stored Procedure、PostgreSQL Enum 或表达业务语义的 View。
4. 数据库保留 Primary Key、Unique、必要的基础 Check、索引、分区、默认值、权限和 Comment。
5. `*_id` 统一登记关系语义：可确定的内部直接引用由数据库校验目标存在；多态、数组和外部引用由代码校验。租户一致、状态允许、业务授权和并发处理属于后续实施职责。
6. 配置类能力统一存入版本化 `configuration_versions`，使用 `config_type + schema_version + payload jsonb` 承载，避免为每一种策略单独建表。
7. 跨事务流程统一使用 `operations + operation_steps`；不为注销、合并、换绑、恢复等流程分别建设数据库工作流引擎。
8. 所有领域状态使用 `varchar` 保存；数据库不维护状态全集、初态、转换边和终态，这些内容在后续代码实施文档和自动化验收中定义。
9. `created_at`、`recorded_at` 等技术时间由数据库生成；存在 `updated_at` 的表由唯一白名单技术 Trigger 使用 `statement_timestamp()` 自动刷新。
10. 聚合根和跨系统引用 ID 由应用生成；纯内部高频从属记录可以使用数据库 Identity。
11. 每张逻辑表必须映射到一个主要业务模型和一个权威持久化域；多域引用同一表不代表多方都可直接维护其生命周期，具体共享边界以 `业务模型与持久化边界清单.md` 为准。
12. 权威事实、Outbox、Audit 和幂等结果的共同提交属于数据库持久化原子性契约；数据库不负责流程编排，但后续实现不得拆散已确认的原子边界。

## 2. 数据库持久化边界与非数据库职责

| 内容 | 数据库职责 | 非数据库职责；后续实施必须关注 |
|---|---|---|
| 数据类型和长度 | 定义并拒绝非法结构 | 提供符合契约的数据 |
| 主键和唯一性 | PK、Unique、唯一索引 | 生成 ID、处理冲突错误 |
| 逻辑关系 | 保存 `*_id`、为确定的内部直接引用建立 `RESTRICT` FK、建立查询索引和 Comment | 解析多态/外部引用，校验租户一致、目标状态和业务作用域 |
| 状态 | 保存状态字符串及变更时间 | 定义状态全集、合法转换和前置条件 |
| 并发 | 保存 `row_version`，执行条件更新 | 传入 expected version、处理冲突和重试 |
| 安全水位 | 保存 epoch/watermark | 决定何时递增、传播和失败关闭 |
| 时间 | 生成创建、记录和数据库更新时间 | 计算业务有效期、冷静期和保护期 |
| 敏感数据 | 保存密文、摘要、盲索引和 Key 引用 | 规范化、加解密、HMAC、脱敏和密钥调用 |
| 幂等 | 唯一保存调用方、幂等键和请求摘要 | 判定相同请求、返回原结果或冲突 |
| Outbox/Audit | 与领域数据同事务持久化 | 生成事件、审计内容和投递语义 |
| 共享表权威 | 保存统一模型、版本和并发边界；用权限保护追加/不可变事实 | 遵守唯一权威域或实例 Owner，不建立影子状态和未声明双写 |
| 权限与风险 | 保存策略版本、决策和证据 | 执行 PDP/PEP、风险计算和审批判断 |
| 删除与保留 | 保存状态、证明和保留信息 | 编排下游删除、匿名化、Legal Hold 和对账 |

## 3. 分级引用完整性规则

### 3.1 数据库与代码的责任分界

以下关系使用 Foreign Key：

1. 来源与目标均位于当前 PostgreSQL 数据库。
2. 来源字段只有一个确定目标，不依赖类型字段解析。
3. 目标列由 Primary Key 或数据库 Unique 保证唯一。
4. 删除行为使用 `RESTRICT`，禁止级联删除、级联更新和数据库自动置空。

以下关系不创建 Foreign Key：

1. `actor_type + actor_id` 等多态引用。
2. `uuid[]` 等数组快照。
3. 可能引用外部消息总线或遗留系统、且本库没有统一登记对象的标识；KMS/HSM Key 必须先登记到 `cryptographic_keys`，内部 `key_id` 仍使用 Foreign Key。
4. 只保存签发时证据、不要求目标永久保留的历史快照。

无论是否存在 Foreign Key，代码仍必须校验目标类型、`business_line_id`、`tenant_id`、`organization_id`、目标状态、操作者权限、保证等级、风险和审批，并使用 `row_version` 或唯一键处理并发。

### 3.2 删除与终态处理

- Foreign Key 统一 `ON DELETE RESTRICT`，不依赖级联删除。
- 主体、标识、认证器、Grant、Consent、审计和事件优先使用终态、解绑、匿名化或墓碑，而不是直接删除。
- 纯技术从属记录由代码按明确顺序清理。
- 历史、审计、Outbox、撤销、迁移映射和删除证明可在主对象清除后继续保存逻辑引用。
- 多态、数组和外部逻辑引用定期执行孤儿或解析检查，并将结果作为发布和运行门禁证据。

### 3.3 逻辑关系登记

数据库基线必须维护机器可读取的逻辑关系索引，至少包含：

```text
source_table
source_column
target_table
target_column
relation_type
column_comment
```

`required`、`tenant_guard`、业务删除策略、锁定策略和校验 Owner 属于后续代码实施文档；数据库文档声明稳定的来源、目标、关系类型和是否由 FK 保护。

数据库字段 Comment 必须写明逻辑目标，例如：

```sql
COMMENT ON COLUMN iam.sessions.user_id IS
'逻辑引用 iam.global_users.id；数据库 FK 校验存在性，SESSION 领域服务继续校验生命周期、安全冻结和租户上下文。';
```

## 4. Schema、角色和数据库对象

### 4.1 Schema

```text
iam
```

首期和目标态均使用单一 Schema。敏感表与审计表通过独立数据库角色、表级或列级 Grant 隔离；只有明确出现独立备份、独立密钥域或独立实例要求时再物理拆分。

### 4.2 数据库角色

| 角色 | 用途 |
|---|---|
| `iam_owner` | Schema 和数据库对象所有者，禁止应用运行时使用 |
| `iam_migrator` | 执行版本化迁移和初始化数据 |
| `iam_app_rw` | 公共技术表能力，只供领域写角色继承，禁止直接授予登录身份 |
| `iam_{id/auth/plt/tenant/oap/session/profile/priv/authz/fed/risk/machine/ctrl/key/event/msg/mig}_rw` | 对应权威领域的最小读写；不跨领域写入，不获得运行时 DELETE |
| `iam_app_ro` | 受控只读查询；敏感表使用脱敏列级授权或完全收回 |
| `iam_identifier_reader`、`iam_auth_secret_reader`、`iam_token_secret_reader` | 用户标识、认证秘密和 Token 摘要的受控读取能力，不含写权限 |
| `iam_machine_secret_reader`、`iam_delivery_secret_reader`、`iam_migration_secret_reader` | 机器凭证、投递目标和迁移原文的受控读取能力，不含写权限 |
| `iam_audit_writer` | 仅追加审计数据 |
| `iam_audit_reader` | 受控审计查询，不可修改 |
| `iam_ops` | Outbox、Webhook、消息投递、目录同步和迁移队列运维；无 DELETE，不得修改用户、租户、权限、策略、审批或配置内容；分区 DDL 由版本化 Migration 执行 |

运行时登录身份必须从一个权威领域写角色或一个只读/运维角色起步，并在部署清单中显式登记组合。确需读取密文时只叠加对应 Reader；普通领域服务不得因为少数敏感操作而整体获得其他敏感数据读取能力。任何运行时身份均不得直接继承 `iam_app_rw`、`iam_owner` 或 `iam_migrator`。

运行时身份的最小组合契约：

| 运行时身份类型 | 必须继承 | 权限目的 |
|---|---|---|
| 普通领域写入方 | 对应 `iam_{domain}_rw` + `iam_audit_writer` | 只写本领域权威事实、公共技术事实和仅追加审计 |
| AUTH/OAP 敏感事务写入方 | `iam_auth_rw + iam_auth_secret_reader` 或 `iam_oap_rw + iam_token_secret_reader`，再叠加 `iam_audit_writer` | 对 Challenge、恢复码、授权码和 Token 元数据完成受控读改写闭环 |
| ID/MACHINE 敏感事务写入方 | 对应领域写角色 + `iam_identifier_reader` 或 `iam_machine_secret_reader` + `iam_audit_writer` | 写入仍由权威领域角色完成，Reader 只补充最小敏感读取 |
| 队列、投递与迁移 Worker | `iam_ops`；确需读取目标或迁移原文时叠加 `iam_delivery_secret_reader` 或 `iam_migration_secret_reader` | 只处理已登记运行队列、投递、同步和迁移状态 |
| 审计查询方 | `iam_audit_reader`；需要普通业务上下文时叠加 `iam_app_ro` | 只读审计与受控业务查询，不得修改历史证据 |

领域写角色与专用 Reader 采用拆分授权：写角色可 INSERT，并仅对明确生命周期字段获得列级 UPDATE；Reader 可 SELECT 但不可单独改写。稳定 ID、唯一键、创建/签发时间、请求摘要和不可变载荷没有运行时 UPDATE 权限。追加事实只开放 INSERT；不可变版本内容仅通过列级 `UPDATE` + `row_version` 修改审批或发布生命周期元数据。`verification/007_permissions_check.sql` 同时验证正向可用性、跨领域隔离、无整表 UPDATE、无 DELETE、不可变内容和分区子表不可绕过。

业务系统不得直接获得数据库账号或访问 `iam` Schema。

### 4.3 明确不创建的对象

- 业务 Trigger。
- 除 `iam.set_updated_at_technical()` 与 `trg_set_updated_at` 之外的持久化 Trigger/Function。
- `CASCADE`、`SET NULL` 或 `SET DEFAULT` Foreign Key 动作。
- 业务 Function 和 Stored Procedure。
- PostgreSQL Enum。
- 状态字典表。
- 表达“有效用户”“有效授权”等业务含义的 View 或 Materialized View。
- 在数据库内部执行加密、风险计算、权限决策或流程编排的例程。

## 5. ID、时间、版本和公共字段

### 5.1 ID 生成

| 类型 | 推荐方式 |
|---|---|
| 聚合根内部 ID | 应用生成 UUIDv7，数据库类型 `uuid` |
| Global User ID、Subject ID 等公开 ID | 应用生成随机、不可推断的独立标识 |
| Event、Operation、Session、Grant ID | 应用生成，保证事务提交前可引用 |
| 纯内部从属或追加记录 | 可使用 `bigint GENERATED ALWAYS AS IDENTITY` |
| 外部 ID | 保留外部原始值或加密值，只作为映射键 |

内部有序 ID 不得出现在对外 API、Token、URL、Webhook 和业务日志中。

### 5.2 技术时间

```sql
created_at  timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,
updated_at  timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,
recorded_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP
```

- `created_at`：数据库插入时间。
- `updated_at`：插入时数据库生成；更新时由白名单技术 Trigger 使用 `statement_timestamp()` 自动刷新，应用不得将其作为业务时间。
- `occurred_at`：业务事件实际发生时间，由代码传入。
- `recorded_at`：事件或审计实际落库时间，由数据库生成。
- 业务有效期、Token TTL、冷静期、保护期、等待期由代码计算后写入。

### 5.3 乐观锁和安全水位

```sql
row_version          bigint NOT NULL DEFAULT 0,
user_security_epoch  bigint NOT NULL DEFAULT 0,
client_security_epoch bigint NOT NULL DEFAULT 0
```

更新示例：

```sql
UPDATE iam.global_users
SET lifecycle_state = @new_state,
    row_version = row_version + 1
WHERE id = @id
  AND row_version = @expected_version;
```

数据库只执行原子条件更新；是否允许转换由代码决定。

### 5.4 聚合根公共字段

聚合根按需要包含：

```text
id
public_id
state
state_reason
state_changed_at
row_version
created_at
updated_at
```

不机械要求每张表都包含全部公共字段。不可变历史、关联表、追加日志和分区记录只保留其实际需要的列。

## 6. 敏感数据存储

### 6.1 标准字段

```text
value_ciphertext
blind_index
normalization_version
encryption_algorithm
encryption_version
key_id
value_fingerprint
```

### 6.2 存储要求

- 手机、邮箱等可等值检索标识：随机化密文 + HMAC 盲索引。
- 密码：现代自适应哈希及算法参数，不保存可解密密码。
- TOTP、第三方 Token 等秘密：应用加密后保存密文和 KMS Key ID。
- Passkey：保存 Credential ID 摘要、公钥和认证器元数据。
- Access Token、Refresh Token、授权码、验证码、恢复码：只保存摘要或必要元数据。
- 私钥：只保存 KMS/HSM 引用，不保存私钥明文或可导出副本。
- 日志、事件、审计和追踪禁止出现密码、验证码、完整 Token 和私钥。

## 7. 最终表目录

### 7.1 通用技术设施：6 张

| 表 | 核心数据 | 说明 |
|---|---|---|
| `idempotency_records` | caller、idempotency key、request hash、Operation、结果、过期时间 | 保证同键同请求结果稳定，同键不同请求由代码判定冲突 |
| `operations` | operation type/state、调用作用域、幂等键、请求摘要、能力、Saga、策略版本、Subject、Actor、Tenant、当前步骤、不可逆边界、结果 | 通用异步和跨域流程载体；创建快照不可被步骤改写 |
| `operation_steps` | step code/state、attempt、checkpoint、输入输出摘要、错误 | Operation 从属步骤；FK 校验 Operation 存在，代码校验步骤归属、顺序和状态 |
| `outbox_events` | event id/type/schema、Producer、Subject/Actor 标识类型、业务线、发生时间、数据版本、Trace/因果、敏感级别、payload、publish state | 与领域数据同事务写入；核心事件信封使用独立字段 |
| `inbox_messages` | consumer、event id、处理状态、结果 | 消费幂等和乱序保护 |
| `audit_events` | Actor、Subject、Tenant、Action、Object、前后摘要、审批、Trace | 追加写入，逻辑引用不建 FK |

### 7.2 身份主体与标识：7 张

| 表 | 核心数据 | 说明 |
|---|---|---|
| `global_users` | internal ID、Global User ID、正式/Guest 类型、生命周期、独立认证锁定、独立安全冻结、Guest 到期、security epoch | 全局用户主体，不保存业务会员状态 |
| `user_subjects` | user、client/audience、pairwise subject、生成版本 | 对外 Subject 映射 |

| `user_identities` | user、identity type、identifier/provider、external stable key、state | 本地、社交和企业登录身份 |
| `user_aliases` | alias type/value、canonical user、来源、状态 | 合并账号、旧 UID 和历史主体映射 |

## 8. 索引、唯一性和基础 Check

### 8.1 必须的唯一性

- `global_users.global_user_id`。
- `user_subjects(client_id, subject_id)` 永久唯一，以及 `(user_id, client_id, current_subject_slot)` 当前占位唯一。
- `identifier_claims(scope, identifier_type, blind_index)`。
- 外部身份源稳定键摘要。
- `oauth_clients.client_id`。
- `api_resources.audience`。
- `oauth_scopes.scope_code`。
- Membership 同一作用域和用户最多一个当前占位；终态历史保留原 Membership ID，重新加入创建新 ID。
- `access_token_records.jti` 数据库全局唯一。
- Challenge、授权码、Refresh Token、恢复码摘要。
- `idempotency_records(caller_scope, idempotency_key)`。
- `outbox_events.event_id`。
- `inbox_messages(consumer_id, event_id)`。
- 审计事件 `event_id`、授权决策 `decision_id`、风险信号 `signal_id`、Webhook `delivery_id` 和消息 `request_id`。
- Policy、Configuration、Event Schema 的 `(code/type, scope, version)`。
- `legacy_id_mappings(system_id, external_type, external_id_digest)`。

### 8.2 查询索引

- 每个逻辑引用 `*_id` 根据实际查询路径建立单列或组合索引。
- 优先建立组合索引，例如 `(user_id, state, expires_at)`，而非机械为所有 `*_id` 建单列索引。
- Tenant 作用域查询必须将 `tenant_id` 放入高选择性索引前缀或紧邻主查询字段。
- Outbox、Webhook、消息、Operation 建立 `(state, next_attempt_at)` 类工作队列索引。
- Audit、认证尝试、风险信号按主体、时间和事件类型建立分区内索引。
- JSONB 只对明确存在的查询路径建立 GIN 或表达式索引。

### 8.3 基础 Check

只保留不表达业务流程的稳定检查：

```text
row_version >= 0
security_epoch >= 0
attempt_count >= 0
expires_at IS NULL OR expires_at > created_at
数量和配额非负
摘要和 ID 长度合法
必要的字段互斥或至少一个存在
```

不使用 Check 表达状态转换、权限、风险、审批和租户业务规则。

## 9. 分区和容量

以下表按月使用 Range Partition：

- `authentication_attempts`
- `workload_attestations`
- `webhook_delivery_attempts`
- `message_delivery_attempts`
- `migration_change_logs`

以下表使用 8 路 Hash Partition：

- `outbox_events`：分区键 `event_id`，以维持数据库级 `event_id` 全局唯一。
- `inbox_messages`：分区键 `(consumer_id, event_id)`，以维持数据库级消费幂等唯一。
- `access_token_records`：分区键 `jti`，以维持数据库级 JTI 全局唯一。
- `audit_events`：分区键 `event_id`，以维持审计事件 ID 全局唯一。
- `authorization_decisions`：分区键 `decision_id`，以维持被 Token 引用的决策 ID 全局唯一。
- `risk_signals`：分区键 `signal_id`，以维持被风险评估引用的信号 ID 全局唯一。
- `webhook_deliveries`：分区键 `delivery_id`，以维持投递 ID 全局唯一。
- `message_requests`：分区键 `request_id`，以维持消息请求 ID 全局唯一。

技术原因：PostgreSQL 分区表的 Unique/Primary Key 必须包含分区键。凡全局标识承担去重键或逻辑关系目标时，优先使用该标识 Hash 分区并由数据库保证唯一；时间保留通过时间索引和受控批量归档完成。

要求：

- Range 分区键使用明确的业务/记录时间；Hash 分区键使用必须数据库全局唯一的稳定标识。
- 默认提前创建未来分区，禁止依赖运行时 Trigger 自动建分区。
- 活跃队列和历史归档使用不同索引策略。
- 删除旧分区前由代码或运维任务校验保留策略、Legal Hold 和审计要求。

## 10. Comment 规范

必须为 Schema、表、字段、关键索引、关键唯一约束和分区补充中文 Comment。

字段 Comment 至少说明：

1. 数据含义。
2. 权威域。
3. 是否为逻辑引用以及目标表字段。
4. 数据敏感级别和加密形态。
5. 空值含义。
6. 是否对外暴露。
7. 状态或业务规则属于哪个非数据库业务领域。

示例：

```sql
COMMENT ON TABLE iam.identifier_claims IS
'当前标识唯一性占用记录。数据库通过唯一索引维持同一作用域、类型和盲索引只有一个占用；占用创建、释放和隔离期判断由 ID 领域代码负责。';

COMMENT ON COLUMN iam.identifier_claims.identifier_id IS
'逻辑引用 iam.identifiers.id；数据库 FK 校验存在性，ID 领域服务继续校验规范化版本和当前状态。';
```

## 11. 初始化数据

Seed 只初始化稳定系统目录和待审批控制面候选版本：

- SP1、SP1-D、SP2、SP3、SP4、SP5 安全 Profile DRAFT 配置版本。
- 标准 OAuth Scope。
- 48 项稳定系统权限目录。
- 算法 Allowlist DRAFT。
- 完整 `SLO-*`、`TTL-*`、`TERM-*` DRAFT 基线。
- 默认数据分类和依赖失败策略 DRAFT；未批准的 Retention 数值不进入 Seed。
- 13 个核心安全通知模板 DRAFT。
- 28 个核心事件 JSON Schema DRAFT，并由 Seed 契约校验蓝图要求的核心事件名称。

控制面 Seed 不直接激活；后续实施完成审批和发布后才进入运行时有效集合。Seed 重复执行时同业务键内容摘要不一致必须失败，不允许 `DO NOTHING` 静默漂移。

禁止通过 Seed 创建：

- 用户和 Membership。
- 业务线和租户。
- 生产 Client。
- 管理员和 Break-glass 账号。
- 私钥、Client Secret 和机器凭证。

这些对象必须通过安全引导、控制面审批或运行期 API 创建。

```text
4. COMMENT ON COLUMN
5. Primary Key、Unique 和基础 Check
6. 查询索引
7. 权限说明
```

全部领域表创建完成后，`805_referential_integrity.sql` 集中建立可确定内部引用的 `RESTRICT` Foreign Key；多态、数组和外部引用继续进入 Comment、关系清单和孤儿扫描。

### 12.4 SQL 与业务文档的映射

- SQL 文件按存储依赖组织，一张表只在一个 Migration 文件中定义。
- 业务规则按能力域组织，一个领域文档可以引用多个 SQL 文件中的表。
- `业务模型与持久化边界清单.md` 记录每个核心业务模型必须保存的事实、数据库硬边界和明确不属于数据库的职责。
- `逻辑关系与非数据库校验清单.md` 同时记录 FK 保护关系和保留在代码中的逻辑引用；后续实施文档补充租户守卫、业务删除行为、锁和校验 Owner。
- `需求编号与数据库持久化覆盖索引.md` 是需求编号到数据库持久化边界的覆盖索引，不是代码实施或验收矩阵，也不声明 Owner、Phase 或逐条自动化测试绑定。

## 13. 验证门禁

数据库验证脚本必须检查：

1. 113 张目标表全部存在。
2. 直接内部引用使用已验证的 `RESTRICT` Foreign Key，且不存在级联动作。
3. 只存在白名单 `updated_at` 技术 Trigger；不存在业务 Trigger、业务 Routine、PostgreSQL Enum、View 和 Materialized View。
4. 表和字段 Comment 完整。
5. 主键、唯一索引、工作队列索引和分区存在。
6. 敏感数据字段未设计为明文。
7. 运行时角色没有 DDL、DELETE、跨领域写入、越权读取或审计修改权限；敏感 Reader 不可写，追加事实和不可变版本内容不可改写，组合身份具备受控读改写所需的正向权限。
8. 多态、数组和外部逻辑关系孤儿/解析扫描无未登记异常。
9. 高容量表的未来分区已创建。
10. Migration 与 Seed 可在空数据库重复构建出一致 Schema。
11. Security Profile、SLO/时长、权限、模板和核心事件 Seed 满足蓝图基线且未静默漂移。
12. 113 张逻辑表均映射到业务模型和至少一个领域持久化范围；多领域复用表写入权威无冲突。

后续实施验收必须检查；具体测试设计不在数据库文档中定义：

1. 非 FK 逻辑引用写入前校验存在性；所有引用都校验作用域、状态和业务有效性。
2. 删除、匿名化、合并和迁移不会制造未处理孤儿记录。
3. 并发写入使用 `row_version` 或技术对象的原子 CAS。
4. 权威数据、Outbox、Audit 和幂等结果同事务提交。
5. 状态转换、不变量、租户隔离、撤销和恢复路径符合蓝图。

## 14. 后续实施约束

- 本文档是数据库总体设计的确认基线。
- 实际 DDL 必须以本文档的表目录、分级引用完整性原则和职责边界为依据。
- 新增表前必须证明其保存的是独立、稳定、需要查询或审计的数据事实，而不是把某个代码流程固化为表。
- 数据库领域文档中的“业务模型要求”和“后续关注”用于证明当前持久化模型能够支撑需求；编码必须遵守 `docs/implementation`，具体类、接口和框架设计可在迭代内继续细化。
- 后续实施文档可以决定类、接口、事务编排和外部组件，但不得改变已确认的权威事实、唯一性、CAS、追加写和敏感数据边界。
- 新增配置类型优先扩展 `configuration_versions`，只有存在独立唯一性、高频查询或固定法规证据结构时才新增专用表。
- 所有重要设计变更必须同步更新本文档、SQL Comment、逻辑关系清单和追踪矩阵。
