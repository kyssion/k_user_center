# 阶段 0 实施状态、整改计划与技术方案

> 审计日期：2026-08-06  
> 当前结论：**允许进入阶段 0 整改与工程骨架建设；阶段 0 出口未通过；阶段 1a 业务实施 NO-GO**  
> 判断范围：仓库内能力地图、建设与验收蓝图、数据库设计与 SQL、代码实施契约、当前 .NET 工程和本地可验证工具链。

## 1. 判断

当前文档已经足以约束稳定的数据事实、领域边界、数据库职责、主要状态机、通用 API/事件原则和阶段 0 的目标，因此可以开始：

- 修复并固化可重复构建；
- 冻结技术选型并形成 ADR；
- 搭建模块化单体骨架和公共基础设施；
- 建设本地依赖、数据库实跑和 CI 门禁；
- 为阶段 1a 候选能力展开逐条矩阵和命令规格卡，但暂不实现生产业务命令；
- 使用测试夹具或内部技术探针验证事务、CAS、幂等、Outbox/Audit，不把探针作为业务能力交付。

当前文档和工程尚不足以支持阶段 1a 全量业务代码并行开发。禁止仅凭领域级概要直接实现认证、Token、密钥、租户、授权、隐私等模块。

依据：

- [能力地图 §11.0](../能力地图.md#110-技术基线与工程骨架)明确规定技术基线未冻结前阶段 1a 不得开工。
- [建设与验收蓝图 §18.4](../统一身份与访问平台建设与验收蓝图.md#184-需求到证据追踪矩阵)规定只有领域级模糊映射的能力不得开始实现。
- [代码实施契约索引](./代码实施索引.md#开始编码前门禁)要求每个进入迭代的命令先明确十类实施契约。

## 3. 允许与禁止的开工范围

### 允许立即开始

1. 修复依赖并恢复构建。
2. 固定 SDK、包管理、静态分析和构建规则。
3. 建立模块化单体目录、依赖方向和跨模块访问检查。
4. 建立健康检查、配置、结构化日志、追踪、错误中间件和可信时钟抽象。
5. 建立数据库连接、事务执行器、CAS、幂等、Outbox/Audit 和 Migration 测试基座。
6. 建立本地依赖编排和 CI 基础门禁。
7. 完成技术 ADR、Owner、Phase、算法合规与 SLO 决策。
8. 为阶段 1a 的第一个候选垂直切片填写实施矩阵和命令规格卡，但不提前实现生产业务命令。

### 当前禁止开始

1. 自研 OAuth/OIDC 协议实现。
2. 在授权服务器未选型前实现最终 Token/Grant/Logout/JWKS 流程。
3. 在算法合规未关闭前冻结密码哈希、签名算法和密码模块实现。
4. 在命令规格卡未绑定需求、权限、事务、事件和测试前批量创建 Handler/Repository。
5. 多团队并行实现全部领域，事后再补 Owner、矩阵和状态机测试。
6. 把数据库技术角色、前端控制或不可枚举 ID 当作业务授权。
7. 把阶段 0 的技术探针或最小协议链路当成阶段 1a 业务能力已经交付。

## 5. 阶段 0 改造计划

### 5.1 执行原则

- 先恢复构建，再冻结技术决策，再建设基础设施，最后进入业务垂直切片。
- 不要求先展开全部目标态需求；但任何进入当前迭代的能力必须先完成逐条矩阵和命令规格卡。
- 算法合规未关闭时，可以建设不绑定算法的端口、测试替身和基础设施骨架，不得冻结生产密码实现。
- 每项完成必须留下仓库内证据；会议结论或口头确认不算完成。

### 5.5 阶段 0 技术探针与阶段 1a 首个切片

阶段 0 使用测试夹具或内部技术探针验证以下工程能力，探针不得暴露为生产 API、不得写入正式实施矩阵的业务交付证据：

- 测试 Actor、Tenant/Business Line 上下文传播；

### 6.1 技术与版本

版本策略：所有 NuGet 包保持最新稳定版本，不固定钉住具体版本，也不使用 pre-release/预览版。任何包的新增、升级或随上游传递解析的版本变化，必须人工 review 包冲突、传递依赖兼容性、破坏性变更和安全公告（`dotnet restore` 后确认无未处理 NU1903/NU1902 告警），review 结论登记在本文或 ADR；确认后再重新生成锁文件。

下表版本为 2026-08-07 时的最新稳定版快照，实施时以当时的最新稳定版为准：

| 项目 | 版本/选择 | 约束 |
|---|---|---|
| .NET SDK | `10.0.302` | 根目录 `global.json`，`rollForward=latestPatch` |
| Target Framework | `net10.0` | 所有生产和测试项目统一 |
| ASP.NET Core OpenAPI | `10.0.10` | 仅用于非标准管理/领域 API 的开发期文档 |
| Microsoft.OpenApi | 随上游传递解析 | 不钉住、不直接引用；升级或传递版本变化时人工评审兼容性与安全公告，不引入与 ASP.NET Core OpenAPI 不兼容的主版本 |
| SqlSugar | `SqlSugarCoreNoDrive 5.1.4.216` | 不携带固定数据库驱动；不拥有 Schema |
| PostgreSQL 驱动 | `Npgsql 10.0.3` | 与 SqlSugar 的真实兼容性由用户手工验证 |
| JSON 兼容依赖 | `Newtonsoft.Json 13.0.4` | 仅按最新稳定版管理传递依赖；业务 API 默认使用 `System.Text.Json` |
| 测试 | `xunit 2.9.3`、`Microsoft.NET.Test.Sdk 18.8.1` | 不采用预览测试框架 |
| 覆盖率/架构 | `coverlet.collector 10.0.1`、`NetArchTest.Rules 1.3.2` | 建立采集和依赖门禁，不虚构覆盖率目标 |

依据：[.NET 10 发布元数据](https://dotnetcli.blob.core.windows.net/dotnet/release-metadata/10.0/releases.json)、[SqlSugar 官方仓库](https://github.com/DotNetNext/SqlSugar)、[SqlSugarCoreNoDrive](https://www.nuget.org/packages/SqlSugarCoreNoDrive/5.1.4.216)、[Npgsql](https://www.nuget.org/packages/Npgsql/10.0.3)、[Microsoft.OpenApi 安全公告](https://github.com/advisories/GHSA-v5pm-xwqc-g5wc)。

## 7. 模块边界与依赖

### 7.1 项目职责

| 项目 | 职责 | 禁止内容 |
|---|---|---|
| Host | 依赖注入、HTTP/协议适配、中间件、OpenAPI、健康检查 | 领域状态机、SQL、Repository、密码学实现 |
| BuildingBlocks | UTC 时钟、UUIDv7、错误基础类型、事务端口和通用上下文 | ASP.NET、SqlSugar、Npgsql、消息/KMS 客户端 |
| Persistence.SqlSugar | SqlSugar/Npgsql 注册、配置、事务、健康检查和映射基础设施 | 业务状态转换、授权、自动建表 |
| Module Contracts | 对 Host/其他模块公开的命令、查询和事件契约 | Repository、ORM Entity、内部领域对象 |
| Module Domain | 实体、值对象、不变量和领域端口 | HTTP、ORM、缓存、消息或系统时钟直接调用 |
| Module Application | 用例编排、权限/作用域入口、事务边界和端口调用 | 具体 SqlSugar/Npgsql API、跨模块改表 |
| Module Infrastructure | 模块端口适配器和唯一组合入口 | 被其他业务模块直接引用 |

### 7.2 允许的引用

```text
Host -> BuildingBlocks / Persistence.SqlSugar / Module.Infrastructure
Module.Infrastructure -> Application / Domain / Contracts / Persistence.SqlSugar
Module.Application -> Domain / Contracts / BuildingBlocks
Module.Domain -> BuildingBlocks
Module.Contracts -> BuildingBlocks
Persistence.SqlSugar -> BuildingBlocks
```

架构测试必须阻断：Domain/Application/Contracts 引用 SqlSugar、Npgsql 或 ASP.NET；Host 直接访问 Repository；跨模块引用 Infrastructure；跨模块直接改表；业务代码直接使用系统时钟或自行创建数据库连接。

跨模块同步调用使用目标模块公开 Application/Query Contract；异步传播使用标准 Outbox/Event Schema；长流程使用统一 `operations + operation_steps`；禁止同步双写多个权威域和影子状态。

## 8. SqlSugar 与 PostgreSQL 约束

- 禁止 `CodeFirst.InitTables`、`DbMaintenance.CreateDatabase` 和运行时 Schema 同步；`database/postgresql` 是 Schema、Migration、Seed、角色和权限的唯一可执行权威。
- SqlSugar Entity 只存在于 Infrastructure，不等于领域实体；Domain 不使用 `SugarTable/SugarColumn`。
- `iam` Schema、表、列和类型显式映射，不依赖自动命名推断。
- 每个 HTTP 请求、消息消费或 Worker 命令作用域创建一个 scoped Client；Npgsql 负责物理连接池，同一 Client 不并行执行。
- Application 命令处理器是事务入口；Repository 不自行提交。权威事实、领域 Outbox、本地审计、审计投递 Outbox 和幂等结果同事务提交。
- 不使用 `TransactionScope` 跨数据库或外部系统；外部调用在提交后由 Outbox/Worker 执行。
- CAS 更新显式包含状态、`row_version` 和作用域；0 行更新映射 `VERSION_MISMATCH` 或 `INVALID_STATE_TRANSITION`。
- 唯一冲突按约束名映射；无法识别的基础约束异常映射 `INTERNAL_CONSTRAINT_VIOLATION`。
- `uuid -> Guid(UUIDv7)`、`timestamptz -> DateTimeOffset(UTC)`；`jsonb` 和数组使用显式契约；状态保存字符串，不使用 PostgreSQL Enum。
- SQL 日志默认关闭；开启时只记录模板、耗时和参数数量，不记录参数值、Token、标识原文、密文或盲索引。

## 9. Host、测试与手工数据库验证

阶段 0 首批实现 UTC 时钟、UUIDv7、稳定错误信封、全局异常处理、`/health/live` 和 `/health/ready`。实施通用 500 响应前必须先登记错误码；连接串只从环境变量或 User Secrets 注入。

默认自动验证：

- `dotnet restore --locked-mode`
- `dotnet build -c Release --no-restore`
- `dotnet test -c Release --no-build --no-restore`
- `dotnet format --verify-no-changes --no-restore`
- 单元测试、程序集依赖测试和不访问 PostgreSQL 的 Host liveness 测试。

<a id="local-db-skip"></a>

本地 PostgreSQL 跳过规则：本地没有可用 PostgreSQL 环境（无 `psql`、无容器运行时或无法启动）时，直接跳过本地数据库实跑与手工数据库验证，不阻断构建、测试与工程骨架建设；真实实跑验证顺延到有条件的环境（托管数据库、CI 或受控测试库）执行，且必须在阶段 1a 门禁或发布前补齐，证据按本节要求保存。跳过不豁免 [database 发布门禁](../database/README.md#发布门禁) 本身的要求。

用户手工数据库验证至少覆盖：目标 PostgreSQL 主版本、Bootstrap/Migration/Seed/Verification、SqlSugar/Npgsql 参数化查询、提交/回滚、CAS 0 行、唯一冲突、`uuid/timestamptz/jsonb/array` 映射和 UTC 行为。证据形成前不得宣称数据库集成通过。
