# 阶段 0 技术方案与工程结构

> 状态：`PROPOSED`，待目录与依赖基线评审通过后实施。  
> 方案日期：2026-08-07。  
> 约束：本文件只定义阶段 0 工程整改和基础设施骨架，不授权实现认证、Token、用户、权限或隐私等生产业务命令。

## 1. 结论

阶段 0 采用以下技术基线：

- .NET 10 模块化单体；
- ASP.NET Core Minimal API 作为 Host 与协议适配层；
- SqlSugar 作为应用数据访问组件；
- Npgsql 作为 PostgreSQL 驱动；
- 现有 `database/postgresql` 版本化 SQL 是数据库结构的唯一可执行权威来源；
- xUnit 承载单元、架构和非数据库宿主测试；
- 所有 C# 源码、项目和测试必须位于 `k_user_center/` 目录内，仓库根目录不得新增 `src/` 或 `tests/`。

本方案通过后仍只允许实施阶段 0。阶段 1a 继续保持 `NO-GO`，直到实施矩阵、首个命令规格卡、Owner、技术门禁和数据库实跑证据全部满足。

## 6. SqlSugar 与 PostgreSQL 方案

### 6.1 数据库权威边界

- SqlSugar 不使用 `CodeFirst.InitTables`、`DbMaintenance.CreateDatabase` 或运行时 Schema 同步。
- 表、字段、索引、约束、角色和权限只由 `database/postgresql` 的 Bootstrap/Migration/Seed 管理。
- SqlSugar Entity 是 Infrastructure 内的持久化记录，不等于领域实体；Domain 不使用 `SugarTable`、`SugarColumn` 等特性。
- `iam` Schema、表名、字段名和类型必须显式映射，不依赖自动大小写或命名推断。

### 6.2 客户端生命周期

- 每个 HTTP 请求、消息消费或 Worker 命令作用域创建一个 scoped `ISqlSugarClient`/`SqlSugarClient`。
- `IsAutoCloseConnection=true`，物理连接池交由 Npgsql；不得把可变事务状态保存在全局 Singleton Client 中。
- 同一命令内 Repository 与 `IUnitOfWork` 必须解析到同一个 scoped Client。
- 禁止在同一 Unit of Work 中并行使用同一个 Client；需要并行只读时必须创建独立查询作用域并证明新鲜度契约允许。

### 6.3 事务

- Application 命令处理器是事务入口；Repository 不得自行提交事务。
- 权威事实、领域 Outbox、本地 `audit_events`、审计投递 Outbox 和幂等结果使用同一个数据库事务。
- 事务 API 封装为 `IUnitOfWork.ExecuteAsync`；提交失败时尝试回滚，回滚失败必须保留原始异常并记录 Critical 日志。
- 不使用 `TransactionScope` 跨数据库或外部系统制造伪原子性。
- 外部调用只能在提交后由 Outbox/Worker 执行。

### 6.4 并发与异常

- CAS 更新显式包含业务状态、`row_version` 和作用域条件；受影响行数为 0 时重新读取并映射 `VERSION_MISMATCH` 或 `INVALID_STATE_TRANSITION`。
- 唯一冲突按约束名映射稳定领域错误；无法安全识别的数据库约束异常映射 `INTERNAL_CONSTRAINT_VIOLATION`。
- 仅序列化失败、死锁和确认无外部副作用的技术失败允许有限重试；业务冲突不自动重试。

### 6.5 类型与日志

| PostgreSQL | .NET/持久化约束 |
|---|---|
| `uuid` | `Guid`，应用通过 UUIDv7 生成器创建 |
| `timestamptz` | `DateTimeOffset`，统一 UTC |
| `jsonb` | 显式序列化契约；禁止存储未分类任意对象 |
| `text[]/uuid[]` | 显式数组映射和逐项作用域校验 |
| 状态 `text` | 使用注册表字符串，不使用 PostgreSQL Enum |
| `row_version` | 整数 CAS，不使用客户端覆盖式 Save |

SQL 日志默认关闭；开发环境开启时只记录 SQL 模板、耗时和参数数量，不记录参数值、Token、标识原文、密文或盲索引。

## 7. Host 与通用基础设施

阶段 0 首批实现：

- `IClock` + `TimeProvider.System`；
- `IIdGenerator` + UUIDv7；
- 管理/领域 API 错误信封：`code/message/retryable/trace_id/details?`；
- 实施前先在错误码注册表登记通用 500 错误码；全局异常处理器只能返回该已登记代码和安全收敛消息，不得在代码中先行发明错误语义；
- `/health/live` 不访问数据库；
- `/health/ready` 执行 PostgreSQL `SELECT 1`，但本轮数据库结果由用户手工验证；
- OpenAPI 只在 Development 启用；
- 连接字符串从环境变量或 User Secrets 注入，仓库配置文件保留空值，不提交本地密码。

阶段 0 不实现：认证服务器、密码哈希、Token 签发、验证码、业务授权、领域 Handler、Repository、Outbox Worker 或生产消息/KMS 适配器。

## 8. 测试方案

### 8.1 默认自动验证

- `dotnet restore --locked-mode`
- `dotnet build -c Release --no-restore`
- `dotnet test -c Release --no-build --no-restore`
- `dotnet format --verify-no-changes --no-restore`
- 单元测试：时钟、UUIDv7、错误信封和配置校验；
- 架构测试：第 5 节全部依赖规则；
- Host 测试：应用可启动、`/health/live` 成功且不依赖 PostgreSQL。

### 8.2 用户手工数据库验证

本轮不由自动化代理启动 PostgreSQL，也不执行 Migration/Seed。用户手工验证至少包含：

1. 指定目标 PostgreSQL 主版本和连接串。
2. 执行 Bootstrap、全部 Migration、Seed 和 Verification。
3. 通过 SqlSugar/Npgsql 执行连接、参数化查询和 `SELECT 1`。
4. 验证提交、回滚、提交失败、CAS 0 行和唯一冲突映射。
5. 验证 `uuid/timestamptz/jsonb/array` 映射及 UTC 行为。
6. 保存 PostgreSQL 版本、Schema 快照、Migration 账本和验证输出作为证据。

SqlSugar + Npgsql 组合在上述证据形成前只能作为阶段 0 候选实现，不得宣称数据库集成已经验收。
