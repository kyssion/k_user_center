## ADR-0001：逻辑关系与外键策略

- 状态：`PROVISIONAL`
- 决策域：数据库完整性与可迁移性
- 冻结门禁：算法与密码合规关闭、真实 PostgreSQL 验证、215 个逻辑引用完成分类

当前候选 SQL 不创建 Foreign Key，通过字段 Comment、逻辑关系索引、应用写入前校验和孤儿扫描维护关系。业务授权和状态机不属于 Foreign Key 能力范围；“不能用 FK 表达业务规则”不等于“所有结构关系都不应使用 FK”，因此无 Foreign Key 不能在逐关系评审前视为最终结论。

暂定决策：

1. 当前 Migration 保持无 Foreign Key，避免分类完成前产生大范围 DDL 变更。
2. 每个逻辑引用分类为：
   - `STRUCTURAL`：同权威域、稳定目标、父对象不得早于子对象清理；必须评估 FK。
   - `CROSS_DOMAIN`：跨权威域、生命周期独立；默认逻辑引用。
   - `POLYMORPHIC`：目标由类型注册表解析；禁止 FK。
   - `HISTORICAL`：主对象清理后仍保留审计、墓碑或证据；禁止级联 FK。
   - `PARTITIONED_GLOBAL_ID`：受分区唯一性限制；由高熵 ID、幂等和代码检查保证。
3. 授权、Tenant/Business Line、状态、Owner、风险和审批始终由代码校验。
4. 禁止 `ON DELETE CASCADE` 承载业务删除；物理清理由受审批维护流程执行。

最终冻结需要：215 个关系均登记分类、必填性、作用域守卫、删除行为、锁/CAS 和 Owner；逐项评审 `STRUCTURAL` FK；并发/终态/匿名化/迁移负向测试以及真实 PostgreSQL 孤儿检查和执行计划通过。

## ADR-0002：审计事实与远端审计投递

- 状态：`ACCEPTED`
- 决策域：事务、审计、防篡改与故障语义

1. `iam.audit_events` 是本地权威审计事实，不是可覆盖日志或临时投递队列。
2. 安全敏感命令同事务提交领域事实、`audit_events`、领域 Outbox、审计投递 Outbox 和幂等结果。
3. 审计投递复用 `iam.outbox_events`，Payload 只含远端投影所需最小字段或 `audit_event_id`；禁止复制密码、验证码、完整 Token、私钥或未登记 PII。
4. 远端审计域按 `audit_event_id` 幂等消费，是查询、取证、隔离存储和长期保留投影，不参与业务事务同步双写。
5. 本地审计或对应 Outbox 写入失败时，高风险命令失败关闭；远端短时不可用时积压 Outbox，超过批准阈值后停止受影响高风险写入并告警。

结果：不新增第二套 Audit 状态机或 `audit_outbox` 表；OBS 持有审计不可变和最小字段规则；EVENT 持有 Outbox 领取、重试、死信和对账；部署验证同时证明本地仅追加权限和远端安全域隔离。

## ADR-0003：.NET 10、SqlSugar 与 PostgreSQL 工程技术基线

- 状态：`ACCEPTED`
- 日期：2026-08-07
- 决策范围：阶段 0 工程骨架、数据访问组件和目录
- 实施细节：[阶段 0 实施状态与技术方案](../代码实施/阶段0实施状态.md#stage0-technical-baseline)

项目使用 .NET 10、SqlSugar 和 PostgreSQL。现有版本化 PostgreSQL SQL 是 Schema 权威，ORM 不能在运行时自动建表或修改结构。

决策：

1. 所有项目使用 `net10.0`；SDK 由 `global.json`（`rollForward=latestPatch`）固定；NuGet 包保持最新稳定版，不钉住具体版本，新增、升级或传递解析版本变化时人工评审包冲突、兼容性与安全公告，锁文件保证可复现构建（见阶段 0 实施状态 §6.1）。
2. 采用单项目结构：仓库根是工作区容器；内层 `k_user_center/` 是一个自包含解决方案（`k_user_center/k_user_center.sln` 仅含唯一项目 `k_user_center.csproj`）；生产代码在 `src/`、测试在 `tests/`，同项目编译；解决方案级配置保留在仓库根目录；禁止新建任何其他 csproj 或 sln。
3. 采用单项目内的经典分层（Common/Middleware/Models/Services/Repositories，后续落地 Controllers），目录即命名空间，依赖方向由架构测试保障。
4. 使用 `SqlSugarCoreNoDrive` 并显式引用 Npgsql，避免完整包锁定旧 PostgreSQL 驱动。
5. SqlSugar 使用 scoped Client；Application 控制事务，同事务包含事实、Outbox、本地审计、审计投递 Outbox 和幂等结果。
6. 禁止 SqlSugar CodeFirst 和运行时 Schema 同步。
7. 数据库实跑、类型映射和 SqlSugar/Npgsql 兼容性由用户手工验证；证据形成前不能宣称集成通过。

该决策增加项目和锁文件维护成本，且 NoDrive/Npgsql 组合及传递依赖仍须验证和审计。若组合无法通过验证，必须以新 ADR 取代，禁止静默退回旧驱动或启用 CodeFirst。

验证条件：Release restore/build/test/format 通过且无未接受的 High/Critical 漏洞；架构测试阻断错误依赖；用户完成 PostgreSQL Migration/Verification、事务、CAS、类型和错误映射验证；目录与技术方案一致。

修订记录：2026-08-07 决策 1 的版本治理由“固定钉住”修订为“最新稳定版 + 人工评审”；同日决策 2 明确为多解决方案结构：仓库根为工作区容器，内层 `k_user_center/` 为一个自包含解决方案（`k_user_center/k_user_center.sln`）；同日按用户要求将内层解决方案目录扁平化为 .NET 默认布局；同日再次按用户要求收敛为单项目结构：解决方案仅含唯一 `k_user_center.csproj`，生产代码在 `src/`、测试在 `tests/`，模块边界由命名空间与架构测试保障，不再拆分程序集；同日按用户要求将 `src/` 目录改为经典分层命名（Common/Middleware/Models/Services/Repositories，Program.cs 位于项目根），取代此前的 Host/BuildingBlocks/Persistence.SqlSugar/Modules 组织。其余决策不变。

## ADR-0004：授权服务器选型与协议能力逐项评估

- 状态：`ACCEPTED`（2026-08-07 项目负责人批准，含 front-channel 移除与 back-channel Outbox 替代方案；运行时逐项验证仍为实施前必过门禁）
- 日期：2026-08-07
- 决策域：协议组件选型与信任边界
- 关联决策：`DEC-008`（Authorization Code + PKCE S256 已冻结）、`DEC-014`（算法合规 OPEN）、`R0-005`、`R0-012`、`R0-018`

### 背景

本平台自身即统一身份与访问产品，数据库 Schema（113 张表，含认证、会话令牌、联合、密钥控制域）已按自有权威事实设计；蓝图禁止“临时自研协议代码”（阶段 1a 门禁），因此必须选定协议组件。算法与密码合规（`R0-012`）未关闭，本 ADR 只冻结协议组件形态，不冻结生产密码实现；按阶段 0 执行原则，可建设不绑定算法的端口与测试替身。

### 候选与评估矩阵

评估方式为文档级证据核对（链接见脚注）；本地无容器运行时，运行时逐项验证按[本地环境跳过规则](../代码实施/阶段0实施状态.md#local-db-skip)顺延，批准前必须在有条件环境补齐。

| 能力项 | A. OpenIddict（内嵌） | B. Duende IdentityServer（内嵌） | C. Keycloak（外部 IdP） | D. 自研协议层 |
|---|---|---|---|---|
| PKCE（S256） | ✅ 内建且强制约束¹ | ✅ 内建 | ✅ 内建 | 需自证 |
| private_key_jwt | ✅ RFC 7523² | ✅ 内建 | ✅ RFC 7523（26.5 JWT Grant）⁶ | 需自证 |
| mTLS 客户端认证 | ✅ 含令牌绑定³ | ✅ FAPI 支持 | ✅ 文档完备⁷ | 需自证 |
| Refresh 重放 | ⚠️ 默认滚动+兑换失效，重放检测语义待运行时确认⁴ | ✅ 内建复用检测 | ✅ 内建 | 需自证 |
| 三种 Logout | ⚠️ RP-initiated ✅；back-channel 列入 8.0 里程碑未交付；front-channel 官方不实现⁵ | ✅ RP-initiated + back-channel（front-channel 同样受第三方 Cookie 禁令限制） | ✅ 三种均支持 | 需自证 |
| Discovery/JWKS | ✅ 内建 | ✅ 内建 | ✅ 内建 | 需自证 |
| 扩展钩子 | ✅ 事件管道，可挂自定义存储/加密 | ✅ DI 接口全可替换 | ⚠️ Java SPI，跨语言 | 完全自控 |
| Device Flow | ✅ 内建（DEC-008 仅限输入受限设备） | ✅ 内建 | ✅ 内建 | 需自证 |
| 存储归属 | ✅ 自定义 Store 可落在自有 iam Schema | ⚠️ 自带 Operational Store，需映射或并行 | ❌ 独立用户库，与自有 113 表权威冲突 | ✅ |
| .NET 10 | ✅ 主线跟随 | ✅ IS 8.0 已定位 .NET 10⁸ | ❌ JVM 边车 | ✅ |
| 许可证 | ✅ Apache 2.0 | ⚠️ Fair Trade：营收 ≤100 万美元免费，商用超额付费⁹ | ✅ Apache 2.0 | — |

### 推荐决策

1. 推荐候选 A：OpenIddict 内嵌于模块化单体，实现自定义 Store 把应用、授权、令牌、会话事实落在自有 `iam` Schema，保持 SQL Migration 为唯一 Schema 权威（与 ADR-0003 一致）。
2. back-channel logout 缺口用 ADR-0002 的 Outbox 模式补齐：登出事实同事务写入，经 Outbox 投影向已登记 Client 投递 Logout Token；front-channel logout 因浏览器第三方 Cookie 禁令已事实失效，建议从验收范围移除并以“短时会话 + back-channel 传播”替代，该替代须随本 ADR 一并批准。
3. Refresh 重放语义（重放即吊销整链）作为冻结前必验项，负向测试进入 R0-018 验收。
4. 密码实现一律走可替换加密端口；算法 Allowlist 由 `R0-012` 关闭后注入，禁止在组件默认值中冻结算法。
5. 候选 B 为备选：若协议完备性优先且许可证预算获批准，可改选 Duende，但需重新评审其 Operational Store 与自有 Schema 的边界。

### 拒绝理由

- 候选 C：外部 IdP 自带用户库与协议运行时，与本平台“自有权威事实 + 113 表 Schema”的产品定位冲突，且引入 JVM 边车运维面；仅保留为联合登录对端，不作核心组件。
- 候选 D：蓝图阶段 1a 门禁明确禁止临时自研协议代码；协议负向测试成本与合规风险不可接受。

### 验证条件（批准与冻结门禁）

1. 身份协议负责人批准本 ADR，含 front-channel 移除与 back-channel Outbox 替代方案。
2. 有条件环境完成七项能力运行时逐项验证（含 Refresh 重放负向测试），证据入库。
3. `R0-012` 算法合规关闭并注入加密端口；密钥控制域与 JWKS 轮转窗口（`R0-013`）完成批准。
4. OpenIddict back-channel logout 上游交付状态在实施前复核；若仍未交付，验证 Outbox 替代方案通过协议负向测试。

## ADR-0005：依赖组件选型（缓存、消息、KMS/HSM、短期秘密存储、可观测）

- 状态：`PROPOSED`（待架构负责人与 SRE 负责人批准；批准前不得作为实现约束）
- 日期：2026-08-07
- 决策域：基础设施组件与本地替代方案
- 关联决策：`DEC-014`（算法合规 OPEN）、`DEC-015`（部署形态 OPEN）、`ADR-0002`（Outbox 模式）、`R0-007`、`R0-009`

### 背景

Schema 已对依赖组件提出硬约束：投递秘密不进入 IAM 数据库，仅保存外部短期秘密存储的非承载型句柄（`iam.message_requests.delivery_secret_handle`，840 契约含 CHECK 拦截）；`iam.cryptographic_keys` 仅保存 KMS/HSM 不可导出引用与公有材料，私钥绝不落库；`iam.outbox_events` 自带发布状态机，EVENT 代码持有领取/重试/死信/对账。算法合规（`R0-012`）未关闭，本 ADR 只冻结组件形态与端口，不冻结具体算法与供应商实例。

### 决策

| 域 | 推荐 | 备选 | 本地替代（R0-009 一键环境） |
|---|---|---|---|
| 缓存 | Redis（StackExchange.Redis）作为唯一分布式缓存，经 `IDistributedCache` + 自有 TTL 端口访问 | 无（禁止第二套缓存） | `MemoryDistributedCache` 测试替身 |
| 消息 | 阶段 1 不引入外部 MQ；Outbox 由进程内轮询 relay 分发（`SELECT … FOR UPDATE SKIP LOCKED`），at-least-once + 消费端幂等 | 吞吐实证后经 `IMessageTransport` 端口接入 RabbitMQ/Kafka，不改信封 | relay 直连本地 PostgreSQL，无额外组件 |
| KMS/HSM | `IKeyControlService` 端口；生产接托管 KMS（AWS KMS/Azure Key Vault/GCP KMS，随部署地区由 `R0-015` 关闭），私钥不可导出 | 自建 Vault Transit | 开发密钥环（进程内生成密钥，仅 dev 配置可启用，禁止接真实数据） |
| 短期秘密存储 | Redis + TTL + 信封加密：秘密经 KMS 数据密钥加密后存储，句柄=密钥引用+nonce，仅凭句柄不可读 | 独立秘密管理服务 | 内存秘密存储测试替身 |
| 可观测 | OpenTelemetry .NET SDK：日志/指标/链路统一，OTLP 导出 | 供应商后端随部署选型 | Console exporter |

补充约束：

1. 缓存是非权威加速层：会话有效性、授权与风险判定必须以数据库权威事实为准；缓存不可用对安全敏感路径失败关闭，不得回落陈旧数据。
2. Outbox relay 的领取、重试上限、死信与对账阈值由 EVENT 代码配置并纳入状态机注册表；重复投递由消费端按 `event_id` 幂等（与 R0-017 幂等基础设施一致）。
3. 秘密原值不得进入数据库、事件、日志或审计（840 CHECK 已在库层拦截）；可观测导出同样受敏感数据扫描门禁约束。
4. 信封加密的数据密钥由 KMS 生成与包装，算法 Allowlist 由 `R0-012` 关闭后注入端口，禁止在组件默认值冻结算法。

### 拒绝理由

- 阶段 1 引入外部 MQ：Outbox 已提供同事务可靠性，新增 MQ 只增加运维面与双写风险；端口保留使后续接入不需改信封。
- 把短期秘密直接存主库：违反 840 契约与失败隔离原则；主库被拖慢不得连带验证码不可用。
- 开发密钥环用于非 dev 配置：配置层硬拦截，违反即启动失败。

### 验证条件（批准与冻结门禁）

1. 架构负责人与 SRE 负责人批准本 ADR。
2. 有条件环境完成：SKIP LOCKED relay 吞吐与积压告警验证、Redis 不可用时失败关闭注入测试、KMS 对接与密钥轮换演练、OTLP 链路含敏感字段过滤验证。
3. `R0-012` 关闭后确认信封加密与 KMS 算法在 Allowlist 内；KMS 供应商随 `R0-015` 部署形态一并冻结。
