# 《统一身份与访问平台能力地图》评审意见

> 评审对象：[能力地图.md](./能力地图.md)（1132 行）
> 评审视角：把该文档当作要被工程团队直接执行的规范，而非愿景文档
> 行号引用格式：`L###` 指被评审文档的行号，`§x.y` 指其章节号

## 0. 评审结论

覆盖广度与安全深度超过绝大多数内部 IAM 设计文档。以下四项设计选择是行家判断，应当保留并作为后续所有修订的基线：

- 原则 12「状态机与不变量优先」（L42）与 §3.4 的正交状态机建模。
- 原则 11「保证等级驱动」（L41）与 §3.5 的 IAL/AAL/FAL 显式建模。
- 原则 14「机器身份同等治理」（L44）与 §4.17 把机器身份定为生产 P0（L631）。
- 原则 17「恢复路径不降级」（L47）与 §4.15「恢复流程不得比正常认证更容易」（L598）。

同时存在三类需要处置的问题：

| 类别 | 数量 | 影响 |
|---|---|---|
| 阻塞级：内在矛盾与自相冲突 | 9 | 导致 §12 验收清单当前不可判定，或落地时必然返工 |
| 领域模型实质缺口 | 5 | 后补需要改数据模型、Token 声明或授权链 |
| 能力域遗漏 | 12 | 5 项建议必补，7 项建议补充 |
| 优先级与路线图不合理 | 2 | 阶段 1 不可交付，优先级失去信息量 |
| 文档结构缺陷 | 4 | 阻碍文档自身要求的「自动化验收追踪」 |

最小修订集见 §6「建议的修订批次」——若只做一批，做批次 1。

## 1. 阻塞级：内在矛盾与自相冲突

### B-01　通篇要求写具体数字，自身 0 个数字（严重度：高）

**位置**：§4.13 说明段（L547-L555）、§9（L890-L923）、§12（L1020、L1025、L1057）

**问题**
§4.13 明确要求「建议明确以下服务目标，而不是仅写"高可用"」，并列出 7 项：月度可用性、登录与 Token 签发 P95/P99、峰值容量、RTO/RPO、账号冻结到全部会话失效的最大时间、资料变更到业务可见的最大延迟、安全告警与响应时间。**全文未填入任何一个数值。**

**后果（连锁）**
1. §12 验收项「修改密码、冻结账号后，会话在**约定时间内**失效」（L1020）不可判定——"约定"无处可查。
2. §12 验收项「全局退出……并有**传播 SLA**」（L1025）不可判定。
3. §5.7 第 7 条「满足**最大残留 SLA**」（L777）不可判定。
4. §12 把「定义并验证可用性、延迟、RTO、RPO 和容量目标」本身作为验收项（L1057），即把数字外置为待办，于是依赖数字的其他验收项全部悬空。
5. 更关键：§4.13「故障降级：已签发 Token 尽量可本地验证」（L544）与 §9.2「已签发 Token 可在短期内由业务本地校验」（L906）**同原则 13「端到端撤销」（L43）构成直接取舍**——Token 本地验证的有效期就是撤销延迟的下界。不给数字，等于把这个核心架构决策留空。

**建议**
在 §9 新增 §9.0「服务目标（SLO）」表，最少钉死三个数，其余可留 TBD 但必须列出条目与责任人：

| 目标 | 建议先定 | 影响的设计决策 |
|---|---|---|
| Access Token 最大有效期 | 必须 | 撤销延迟下界、是否需要内省、决策缓存 TTL |
| 全局冻结 → 全部会话失效 P99 | 必须 | 是否需要撤销表/安全 epoch/近实时通道 |
| 月度可用性目标 | 必须 | 多活形态、依赖降级策略、容灾投入 |
| 登录 P95/P99 延迟 | 建议 | 风控同步/异步、PDP 是否在认证链路 |
| RTO / RPO | 建议 | 备份形态、跨区复制方式 |
| 资料变更可见延迟 | 建议 | 事件投递 SLA、对账周期 |

同时把 §12 中所有出现「约定时间」「传播 SLA」「最大残留 SLA」的表述替换为引用 §9.0 的具体条目编号。

### B-02　IAL 是 P0，但产生 IAL 证据的能力是 P2 且推给业务（严重度：高）

**位置**：§4.15「保证等级模型」P0（L592）、§3.5（L248）、§4.4「实名与认证信息」P2（L338）

**问题**
三处叠加产生架构级矛盾：

- §4.15 将「保证等级模型 IAL/AAL/FAL、acr/amr/auth_time 映射」定为 **P0**。
- §3.5 正确地禁止推断：「不得由'手机号已验证'推断为'自然人已实名'」（L248）。
- §4.4 将「实名与认证信息」定为 **P2**，且写明「按业务需要**独立建设**，严格隔离和最小化访问」（L338）。

于是：平台承诺 P0 建模 IAL，却没有任何提升 IAL 的手段，实际永久停留在 IAL1；而一旦实名核验结果由各业务自建自存，平台在**结构上就不再是 IAL 断言的权威方**，§4.15「敏感操作要求：最低等级、最大认证年龄」（L593）与 §3.5「每个敏感操作必须声明最低保证等级」（L252）随之空转。

这不是优先级排序问题，是权威边界问题——与 §3.3「数据权威边界」（L207-L216）的方法论冲突：该表未列「身份核验结果 / IAL 断言」的权威系统。

**建议**
拆分「核验实施」与「断言存储」两件事：

1. §4.4 保留「实名核验**实施**（OCR、活体、要素核验对接）」为 P2，可由业务或外部服务完成。
2. §4.1 或 §4.15 新增 P0 条目「**身份核验断言的接收与签发**」：平台是 IAL 等级、核验时间、证据类型、核验方标识的**唯一权威存储与签发方**，业务只能提交核验结果、不得自行解释 IAL。
3. §3.3 权威边界表新增一行：`IAL 断言、核验时间、核验方 | 用户中心`。
4. 若首期确实不做，则在 §4.15 明确写「首期仅支持 IAL1；需要 IAL2+ 的场景在核验断言能力上线前不受理」，避免文档承诺无法兑现的等级模型。

### B-03　UID「不得包含注册时间」与数据库有序主键需求冲突（严重度：中高）

**位置**：§3.2 设计要求（L200）

**问题**
L200 要求「UID 不包含手机号、地区、注册时间、业务类型等可推断信息」。但主流有序 ID（UUIDv7、ULID、雪花）**全部内嵌时间戳**，而有序性对 B 树索引局部性、写放大、分区裁剪至关重要。文档把该条写成硬约束却未给解法，实现时必然二选一后返工。

同时 L202「UID、Subject ID、Membership ID 均不得被重新分配」与不变量 1（L233）已覆盖不可复用，但**未涉及"不可枚举"**——这是与"不泄漏可推断信息"同源但不同的要求（有序 ID 可被遍历探测用户规模与注册速率）。

**建议**
在 §3.2 补写标识分层实现约束（文档已有一半：L204 已要求"对外部应用默认使用应用级 Subject"）：

- **内部主键**：允许使用有序 ID（UUIDv7/雪花），但**永不出现在对外 API、Token、日志与 URL 中**。
- **Global User ID（跨服务传递）**：不可枚举、不含时间信息的随机标识；仅 L205 所述受信任服务可获取。
- **Subject ID（对外发布）**：默认应用级、随机、与 Global User ID 无可计算关系。
- 明确"不可推断"与"不可枚举"是两条独立要求，并分别指出由哪一层标识承担。

### B-04　禁用 ROPC/Implicit 是 P0 铁律，与 §10 双轨运行冲突；缺"安全例外治理"能力（严重度：高）

**位置**：§4.14（L564、L565）、§10「双轨运行」（L935）、§6 集成约束（L842-L843）

**问题**
§4.14 P0 要求「Authorization Code + PKCE S256，**禁用 Implicit 与 ROPC**」（L564）、「回调精确匹配、禁止生产通配符」（L565），§6 再次强化（L842）。§10 却要求「迁移期间支持新旧认证系统有限期并行」（L935）。存量 App 在迁移期几乎必然依赖 ROPC 或自有登录接口。

更根本的是：**全文缺少一条通用治理能力——安全例外/豁免登记（waiver register）**。§4.18 控制面章节有状态机、双人复核、配置漂移检测（L646-L648），但没有"已知违规项的登记、补偿控制、到期日与到期自动收紧"。

**后果**
第一个存量业务接入时，P0 铁律会被无声破坏，且不留痕、无到期约束——这恰好违反原则 8「全程可审计」（L38）与原则 17「恢复路径不降级」的精神。

**建议**
1. §4.18 新增 P0 条目「**安全例外登记**」：例外项、申请人与批准人、影响范围、补偿控制、**强制到期日**、到期后自动收紧或阻断、例外清单纳入发布门禁与月度复核。
2. §4.14 在说明段（L579 附近）补一句：偏离本节 P0 约束的接入必须走安全例外登记，且例外有效期不超过 N 个月（N 待定，随 §9.0 一起定）。
3. §10「双轨运行」行内补充：旧认证方式属于登记在册的限期例外，须写明退役时间表与阻断开关。

### B-05　验收要求覆盖备份删除，但该能力被定为 P1（严重度：中高）

**位置**：§12（L1051）、§4.19「全介质删除」P1（L669）、§4.9「删除与注销」P0（L448）、§4.19「下游处理证明」P0（L667）

**问题**
§12 验收项要求「删除流程覆盖阻断、重试、法律保留、**备份策略**和完成证明」（L1051）。但 §4.19「全介质删除（备份、日志、事件、索引、分析和训练数据策略）」为 **P1**（L669）。

P0 的「完成证明」（L667）若不覆盖备份与日志，便是一份假证明——这正是 §5.10 第 5 条自身警告的「不得因部分失败宣布完成」（L804）。

**建议**
二选一，不要含糊：

- **方案 A（推荐）**：把「全介质删除」中的"备份与日志"部分升为 P0（其余介质如分析域、训练数据可留 P1），并在 §4.19 明确备份场景的合规做法（如加密删除/密钥销毁、保留期自然过期 + 恢复时二次清理钩子）。
- **方案 B**：把 §12 验收项 L1051 改为「删除流程覆盖阻断、重试、法律保留和**在线介质**完成证明；备份与日志介质的删除策略于阶段 2 交付」，并在 §4.9 的删除能力说明中写明当前证明的介质边界。

### B-06　「端到端撤销」是核心原则，但撤销状态的分发机制不是一条能力（严重度：高）

**位置**：原则 13（L43）、§6 集成约束（L847）、§7 下游要求（L871）、§4.19「持续安全信号」P1（L664）、§4.18「决策缓存」P0（L643）

**问题**
- 原则 13 要求冻结、改密、离职、权限回收、风险事件「必须传播到会话、令牌、应用和下游缓存」（L43）。
- §6 要求「高风险授权、冻结、撤销和保证等级变化必须通过**近实时控制通道**传播」（L847）。
- §7 要求下游具备「基于 security epoch、policy version 和 **revocation watermark** 的缓存失效」（L871）。

但**能力清单中没有任何一条负责"这个通道本身"**：谁 push、拉取协议是什么、水位如何对齐与追赶、RP SDK 是否内置、断连与冷启动如何补齐、传播完成率如何度量。§4.18「决策缓存」（L643）只覆盖 PDP 侧的 epoch 与主动失效；实现跨域传播的「持续安全信号」被定为 P1（L664）。

**这等于把平台的核心责任写成了对下游的要求**（L871 的措辞是"下游系统需具备"）。

**建议**
1. §4.3 或 §4.19 新增 P0 条目「**撤销与安全状态分发**」：security epoch / policy version / revocation watermark 的**发布接口**、推拉两种消费模式、水位追赶与冷启动补齐、RP SDK 内置支持、传播完成率与滞后度指标。
2. §4.19「持续安全信号（CAEP/RISC）」可保留 P1，但需说明：P1 指"标准协议形态"，其**平台自有形态属于上述 P0 条目**，两者不可混淆。
3. §7 的下游要求段保留，但在其前加一句：以下下游能力由平台提供的分发接口与 SDK 承载，非纯粹的下游自建要求。

### B-07　用户搜索 P0 + 字段级加密 P0，未解决可搜索加密（严重度：中高）

**位置**：§4.11「用户搜索」P0（L500）、§4.8「数据加密（含字段级加密和脱敏）」P0（L433）、§9.3（L915）

**问题**
§4.11 要求支持按「UID、Subject、**手机号、邮箱**、外部 ID 等受控查询」（L500）；§4.8 要求字段级加密（L433）。两者的冲突——确定性加密、HMAC 盲索引、独立受控检索域三种方案的取舍——既未在 §4.8 出现，也**未进入 §13 的 23 个"必须尽早决策的问题"**。§9.3 只笼统说「对用户检索、审计检索和在线认证采用不同存储及性能策略」（L915）。

**后果**
此决策影响存储层结构、索引形态与查询能力边界，后期变更需要重写数据访问层并全量重加密。

**建议**
1. §4.8 新增子能力「**可检索加密**」P0：明确手机号/邮箱采用 `随机化加密存储 + HMAC(salt) 盲索引` 支持精确查找；**明确不支持模糊/前缀检索**（或说明前缀检索仅在独立受控检索域中提供，并纳入 §4.9 隐私审计）。
2. §4.11「用户搜索」行内补充查询能力边界：精确匹配可用、模糊匹配的适用范围与审批要求。
3. §13 新增决策问题（见 §5「补充的早决策问题」Q-25）。

### B-09　「删除」与「匿名化」两种终态被合并（严重度：中）

**位置**：§3.4 用户生命周期（L222）、§4.1「删除与匿名化」（L280）、§4.9「匿名化」（L450）

**问题**
用户生命周期状态机的终态只有 `ANONYMIZED`（L222），但 §4.1 的能力名是「删除与匿名化：PII 删除、业务通知、保留例外、不可逆确认」（L280），§4.9 另有独立的「匿名化：删除直接标识，评估重新识别风险」P1（L450）。

硬删除与匿名化在法律含义、残留数据、可否用于统计、以及"是否还存在主体记录"上完全不同，合并为单一终态会导致：不变量 8「已匿名化主体不得恢复，旧 UID 只能作为受控墓碑」（L240）无法区分两种情形下墓碑内容的差异。

**建议**
§3.4 将终态拆为两个：`ANONYMIZED`（保留不可逆摘要与统计价值）与 `ERASED`（仅保留墓碑与法律必需的最小记录），并在 §4.1 与 §4.9 分别说明适用条件与选择依据。

## 2. 领域模型实质缺口

### M-01　缺 `Login Transaction / Authentication Session` 核心对象（严重度：高）

**位置**：§3.1 核心对象表（L158-L185）、§3.4 会话状态机（L226）、§4.14「请求绑定」（L566）

**问题**
§3.1 的 24 个对象中没有"一次进行中的登录/授权事务"。§3.4 的会话状态机是 `ACTIVE → EXPIRED/REVOKED`（失陷先入 `COMPROMISED`），**没有任何"部分认证"中间态**：已过一 factor、待 MFA、待补充必填资料、待接受协议、待选择租户、待同意授权。

§4.14「请求绑定：state、nonce、PKCE、Client、redirect URI 和授权码绑定」（L566）是**约束**，不是有状态对象与状态机。

**为什么关键**
1. 它是登录流程的实际状态载体：授权请求参数、已完成的 amr 列表、剩余步骤、步骤超时、重试计数、风控决策快照。
2. 它是**安全事故最高发处**——"未完成认证的临时凭据被当作已认证会话使用"是 MFA 绕过的经典成因。
3. 文档自身原则 12 是「状态机与不变量优先」（L42），此处恰恰漏掉了最需要状态机的对象。

**建议**
1. §3.1 新增对象：

| 对象 | 定义 | 关键要求 |
|---|---|---|
| Login Transaction | 一次进行中的登录或授权事务 | 保存授权请求上下文、已完成认证因子、剩余步骤、风险快照、短过期、单次消费、不可提升为会话除非全部步骤完成 |
| Authorization Code | 一次性授权码 | 绑定 Client、redirect URI、PKCE challenge、Login Transaction；单次使用、重放即撤销关联 Grant |
| Device | 跨会话的设备实体 | 指纹、可信状态、推送标识、命名、挂失与撤销，独立于 Session 生命周期 |

2. §3.4 新增 Login Transaction 状态机：
`CREATED → IDENTIFIED → PARTIALLY_AUTHENTICATED → PENDING_CONSENT → COMPLETED`，另有 `EXPIRED / ABANDONED / BLOCKED` 分支。
3. §3.4 新增不变量：**Login Transaction 未达 `COMPLETED` 不得签发任何 Session、Token 或 Authorization Code**；其标识不得被当作会话标识使用。

### M-02　用户状态机与 §5.5 流程矛盾，且缺三个状态（严重度：中高）

**位置**：§3.4（L222）、§5.5（L753）、§5.2（L727）、§4.19 法律保留（L668）

**问题**

| 缺陷 | 依据 |
|---|---|
| 状态机是单向箭头，但 §5.5 第 5 条明确「冷静期内……**允许撤销**」（L753）——缺 `DELETION_PENDING → ACTIVE` 回边 | L222 vs L753 |
| 缺 `MERGED` 终态。§5.2 第 7 条要求「旧 UID 保留别名映射，不允许复用」（L727），但被合并账号处于何种状态无法表达 | L222 vs L727 |
| 缺 `DORMANT / DEACTIVATED`（长期不活跃休眠、可自助恢复）。它与注销语义完全不同，且与 §4.16「回收号码防护」（L608）强相关——休眠账号是号码回收风险的主要载体 | L222 |
| `LEGAL_HOLD`（L668）与 `DELETION_PENDING` 冲突时的状态无处表达 | L222 vs L668 |

**建议**
§3.4 用户生命周期改为：

```
PROVISIONAL → ACTIVE ⇄ DORMANT
ACTIVE/DORMANT → DELETION_PENDING → ANONYMIZED | ERASED
DELETION_PENDING → ACTIVE          （冷静期内撤回，须重新强认证）
DELETION_PENDING → DELETION_BLOCKED（法律保留或业务阻断，须给出原因与预计处理方式）
ACTIVE → MERGED                    （终态，仅保留别名映射，不可复用、不可恢复为 ACTIVE）
```

并补一条不变量：`MERGED` 与 `ANONYMIZED`/`ERASED` 均为终态，任何路径不得回到 `ACTIVE`；`DELETION_BLOCKED` 必须携带阻断原因与责任方。

### M-03　缺少 `Invitation`、`Approval / Case` 等流程对象（严重度：中）

**位置**：§3.1（L158-L185）、§4.5「成员管理」（L351）、§4.11「高风险审批」（L507）、§4.11「合并拆分工单」（L505）

**问题**
文档有邀请能力（L351）、高风险审批能力（L507）、合并拆分工单能力（L505）、Break-glass（L509），但 §3.1 没有对应对象，§3.4 没有对应状态机。而这些恰恰是**双人复核、职责分离、到期回收**赖以实现的载体——§4.18「双人复核」（L647）与 §4.6「职责分离：申请与审批人隔离」（L386）没有对象可挂。

**建议**
§3.1 新增 `Invitation`（受邀标识、邀请人、目标租户/业务线、预授权角色、单次使用、过期）与 `Approval Case`（发起人、审批人、类型、理由、附件、前后值、状态、有效期、执行结果）。§3.4 相应补两条状态机，并补不变量：**发起人不得同时是审批人；审批通过后的执行必须绑定该 Case 且不可复用**。

### M-04　只有"机器代表人"，没有"人代表人"（严重度：中高）

**位置**：§4.17「代表用户调用」P0（L626）、§4.9「未成年人保护」P2（L452）、§4.6「关系型授权」P2（L385）

**问题**
§4.17 的 Actor/Subject 分离、Token Exchange 委托链、禁止无边界 impersonation（L626）把**机器委托**做得很扎实。但**自然人之间的委托**只以两种间接形式出现：「监护人同意」（L452，P2）与「关系型授权：上下级」（L385，P2）。

缺少 `Delegation / Guardianship` 作为一等对象：委托范围（哪些操作、哪些数据）、期限、可撤销、**被代理人的知情与通知**、审计、以及在 Token 中的表达。

覆盖场景：家长管理儿童账号、财务代管理者审批、护理人代患者、企业管理员代员工操作、以及"共享账号"的合规化替代。

**后果**
一旦后补，需要改 Token 声明（`act` 链）、授权链与审计模型——属于伤筋动骨的改动，因此应在模型层先留位。

**建议**
1. §3.1 新增对象 `Delegation`：委托人、被委托人、范围、生效与到期、撤销、创建证据、通知记录。
2. §3.4 新增状态机 `PENDING → ACTIVE → REVOKED/EXPIRED`。
3. §4.17 的「代表用户调用」行内补充：Actor 可为自然人；人对人委托必须显式建模、范围受限、可撤销、被代理人可见，且 Token 中保留完整委托链。
4. 不要求首期实现完整能力，但要求 Token 声明与审计模型**首期即预留 Actor 为自然人的表达**。

### M-05　缺「外部身份主键迁移」能力（严重度：中高）

**位置**：不变量 3（L235）、§4.16「外部身份主键」（L606）、§4.7「账号链接」P2（L415）

**问题**
不变量 3 与 §4.16 把外部主键正确地钉死为 OIDC `issuer + sub`、SAML `entityID + NameID(+Format, SPNameQualifier)`。但现实中企业**更换 IdP**（如 Okta → Entra ID）或 IdP 变更 entityID 时，**全部 sub/NameID 会同时改变**。§4.7 只有抽象的「账号链接」（L415，P2），没有"IdP 迁移 / 外部主键批量安全重绑定"能力。

**后果**
没有该能力时，企业换 IdP 只能人工改库——直接违反 §9.4「管理后台避免直接操作底层数据」（L923）与原则 8「全程可审计」。

**建议**
§4.7 新增条目「**外部身份源迁移**」P1（有企业客户后升 P0）：新旧 issuer/entityID 并存窗口、按可信属性（如已验证企业邮箱 + 目录侧断言）批量重绑定、逐用户审计记录、失败进入人工处置、迁移期间禁止 JIT 创建重复主体、回滚方案。同时在 §4.16「外部身份主键」行内注明：主键不可变的例外仅限登记在册的身份源迁移，须走 §4.18 双人复核。

**问题**：以下属于"不知道就会返工"级别，且直接影响 Identity 表唯一键设计：

| 约束 | 影响 |

## 4. 优先级与路线图

### P-01　「阶段 1：统一身份最小闭环」不是最小闭环（严重度：高）

**位置**：§11 阶段 1（L970-L982）

**问题**
阶段 1 包含：五大核心对象 + 手机/邮箱/密码/验证码 + 统一登录页 + 合规 OIDC/OAuth Profile + 公共资料与换绑 + **基础 MFA、Step-up、认证器生命周期、安全找回** + 会话、Grant、**Token family**、**完整退出（前后通道）**、吊销 + 冻结/封禁/注销 + **Client/API Resource、机器身份** + API 与 SDK + 安全事件通知 + **基础 RBAC、业务作用域、数据范围** + 管理后台、**控制面审批**、审计、限流、监控、高可用 + **Webhook 验签、防重放、补拉、对账、协议一致性门禁**。

这是成熟商业 IdP 的完整功能集，不是最小闭环。以此定义，团队会长期停留在"阶段 1 进行中"，且无法判断是否可以接入第一个业务。

**同源问题**：P0 条目占全部能力半数以上。当多数条目都是 P0 时，优先级不再提供排序信息，实际执行会退化为"谁催得急"。

**建议**：把阶段 1 拆为两个可交付里程碑，并给每个里程碑一个**可判定的出口条件**：

**阶段 1a（首个业务可安全接入）**
- Global User、Identity、Credential、Application/Client、Membership
- 手机/邮箱验证码 + 密码登录，统一登录页
- Authorization Code + PKCE S256、Token 校验 Profile、JWKS 与双钥窗口
- Session、Access/Refresh Token（含家族轮换与重放检测）、RP-Initiated Logout、改密/冻结触发的吊销
- 全局冻结、业务封禁、注销（含冷静期）
- 认证与管理审计、登录限流与枚举防护、基础监控与合成探针
- 出口条件：一个真实业务线完成接入，且通过协议一致性与撤销 SLA 验证

**阶段 1b（可规模化接入）**
- MFA、Step-up、认证器生命周期、安全找回与高保证恢复
- Back-Channel / Front-Channel Logout、Grant 管理、用户自助安全中心
- 机器身份与 Client Credentials、服务间授权
- 基础 RBAC + 作用域 + 数据范围
- Webhook 验签/防重放/补拉/对账、事件 Outbox
- 控制面状态机与双人复核、安全例外登记
- 出口条件：三个以上业务线接入，发布门禁包含协议负向测试与租户隔离测试

### P-02　优先级模型过于单薄（严重度：中）

**位置**：§4 优先级定义（L256-L262）、§4.10（L463）

**问题**
1. §4.10「权限 API」优先级写作 `P0/P1`（L463）——**含糊值不可执行**，验收时无法判定。
2. §4 说明（L262）正确地把 P2 定义为"场景条件能力"，但**未把触发条件写成可判定规则**。
3. 缺两个必要维度：
   - **依赖前置**：例如「数据范围」（L378）依赖「组织结构」（L350，P2）；「Consent 传播」（L670）依赖「事件总线」（L467）。当前表格无法表达，会导致排期时把依赖项排在被依赖项之后。
   - **成熟度**："有审计日志"与"审计可自动检索并驱动告警"差异巨大，单一 P0 标记无法区分。

**建议**
1. 拆分 L463 为两条：「角色与权限管理 API」P0、「策略与决策 API」P1。
2. 为 P2 条目补"启用触发器"列，写成可判定规则，例如：`接入第一个企业客户 → §4.5 租户/委派管理员、§4.7 企业 SSO 升为 P0`；`处理未成年人数据 → §4.9 未成年人保护升为 P0`；`涉及资金或批量敏感数据 → §4.14 PAR/DPoP/FAPI 升为 P0`。
3. 能力表增加「依赖」列（填被依赖能力编号，编号见 D-01）与「成熟度目标」列（手工 / 半自动 / 自动）。

## 5. 文档结构与可执行性

### D-01　能力没有稳定编号（严重度：高，投入产出比最高）

**位置**：§4 全部表格、§11、§12、§14；§11 阶段 0（L968）

**问题**
§11 阶段 0 明确要求「建立威胁模型、协议负向测试和**自动化验收追踪规则**」（L968）。但全文约 20 张表、200 余条能力**没有任何 ID**。因此 §12 验收清单、§11 路线图、§14 所有权表与能力条目之间**没有可机器追溯的引用**——文档自身要求的"自动化验收追踪"在结构层面即不可能实现。

**建议**
为每条能力分配稳定编号 `CAP-<域>-<序号>`（域码如 IDN 身份主体、AUT 认证、SES 会话令牌、PRF 资料、ORG 组织租户、AZ 权限、FED 联合、SEC 安全风控、PRV 隐私、API 开放平台、OPS 运营、OBS 审计可观测、PLT 平台工程、MCH 机器身份、CTL 控制面、EVT 事件）。编号一经分配不再变更（与文档自身的标识不可复用原则一致）。随后：

- §11 路线图每个条目引用编号列表；
- §12 每条验收项引用它所验证的能力编号；
- §14 所有权表按编号段落分配 owner。

### D-02　同一能力在多处以不同粒度重复定义，缺唯一归属（严重度：中高）

**位置**：§2 mindmap（L51-L152）与 §4.1-§4.20

**问题**
§4.1-§4.13 是经典分域，§4.14-§4.20 是后加的深度专题，两者交叉重叠：

| 能力 | 重复出现位置 |
|---|---|
| 认证器 / MFA 生命周期 | §4.2「多因素认证」L297、「认证强度」L301 + §4.15 整节 |
| 机器身份 | §4.1「服务账号」L276 + §4.3「服务间身份」L321 + §4.17 整节 |
| Refresh Token 安全 | §4.3 L315 + §4.14 L569 |
| 退出 | §4.3「单点退出」L310 + §4.14「完整退出」L573 + §5.7 |
| 风控 | §4.8 整节 + §4.20 整节 |
| 隐私与 Consent | §4.9 整节 + §4.19 L666-L670 |
| 决策缓存与撤销 | §4.6「策略决策服务」L387 + §4.18 L643 |

同时 §2 mindmap 是 **11 个一级分支**，能力清单是 **20 节**，两者无映射关系；§4.14-§4.20 的内容在 mindmap 中被塞入既有分支。

**后果**：同一能力可能有两个 owner、两套验收、两个优先级（如"退出"在 §4.3 与 §4.14 均为 P0 但子能力集不同），§14 所有权分配与 §12 验收会打架。

**建议**
1. 确定 **§4.1-§4.13 为唯一能力主索引**（每条能力只在此定义一次并持有编号）。
2. 将 §4.14-§4.20 降级为「跨域专题 Profile / 约束」，其条目不再独立定义能力，而是**引用主索引编号并附加约束**（例如：`CAP-SES-007 完整退出 —— 附加约束：必须支持 RP-Initiated/Front-Channel/Back-Channel 三种模式，见本节`）。
3. §2 mindmap 与主索引的一级域一一对齐，并在 mindmap 后补一句说明：专题章节不新增能力，仅追加约束。

### D-03　§12 验收清单缺「验证方法 / 证据 / 责任人」（严重度：中高）

**位置**：§12（L1004-L1064）

**问题**
当前为纯 checkbox，多条是无法判定的定性断言，例如「业务后端正确验证签发方、audience、签名和有效期」（L1022）——谁去验证？如何证明所有 RP 都做了？文档把判定方法委托给不存在的蓝图（B-08）。

**建议**
§12 每条改为五列表格：

| 能力编号 | 验收项 | 验证方法 | 证据形式 | 责任人 |
|---|---|---|---|---|
| CAP-SES-0xx | 冻结后会话在 SLO-03 内失效 | 自动化：注入冻结事件后轮询各 RP 受保护接口 | 门禁流水线报告 + 时延分布 | 身份平台团队 |
| CAP-API-0xx | 业务后端正确校验 iss/aud/签名/exp | 接入认证：每个新 Client 上线前跑 Profile 检查（L691 已有此能力） | 接入认证报告，随 Client 记录归档 | 身份平台 + 接入方 |

注：L691「应用上线认证：每个新 Client 自动执行适用 Profile 检查」已经是现成的验证机制，§12 应直接引用它，而不是另立无方法的断言。

### D-04　第三方 Cookie 淘汰对前通道能力的破坏未写明（严重度：中）

**位置**：§4.14「完整退出」P0（L573）、§4.14「客户端安全 Profile」含 SPA/BFF（L563）、§4.3「明确 SSO 域边界」（L309）、§5.7（L769-L778）

**问题**
§4.14 将 **Front-Channel Logout 列为 P0**，§5.7 第 5 条也描述其实现。但浏览器隐私策略（Safari ITP、Chrome 第三方 Cookie 限制）已使跨站 iframe 中的 Cookie 基本不可用，**前通道退出与 `prompt=none` 静默续期在跨站场景下不再可靠**。文档已具备 BFF 概念（L563）与 SSO 域边界意识（L309），但未把结论写成显式约束。

**后果**：实现者会按 P0 去保证一个浏览器不再允许的能力，并在验收时无法通过。

**建议**
§4.14 说明段补充约束：
1. **后通道退出为主**，前通道退出降级为"尽力而为"，不得作为撤销正确性的依据；
2. 跨站场景的 SSO 与静默续期必须依赖 **BFF + 同站 Cookie** 或后端会话，不得依赖第三方 Cookie；
3. §5.7 的"部分退出"状态展示（L776）应明确把前通道失败归入预期情形而非故障。

## 8. 影响评审权重的待确认前提

以下两项会显著改变上述建议的优先级，建议在批次 1 之前确认：

1. **团队规模与组织形态**：§14 列出 9 类负责团队（L1092-L1108）。若实际为小团队，则 G-04（Build vs Buy）应提升为最高优先，且 §14 需要重写为"当前由谁兼任 / 暂缺"；若为集团级平台，§14 可保留。
2. **运营地区**：若限于境内，G-02（等保/密评/国密）为上线准入，优先级高于 §4.14 的 FAPI 2.0（L577，P2）、§4.5 的 SCIM（L355，P2）与 §4.7 的 SAML（L409，P2），后三者可长期搁置；若涉及出海，则 §4.9「跨境与地域」（L451）与 §15 国际标准的权重反过来上升。
