# PostgreSQL 数据库构建文档

## 1. 方案结论

本目录是按最新能力地图与建设蓝图重新整理的空库基线，目标技术栈为 PostgreSQL 16+、.NET 10 与 SqlSugar。基线不兼容旧 SQL 文件层级，不包含回滚脚本。

核心原则：

- 保留 18 个业务 Schema，避免把边界重新混入 `public`。
- 每个 Schema 只有一份 `tables.sql`，包含全部基表、同 Schema 约束、索引及对应 COMMENT。
- 函数、过程和局部触发器集中在 `routines.sql`；视图、跨域绑定、种子只在需要时增加单文件。
- 所有业务表先独立创建，跨 Schema 外键和绑定在第二阶段统一执行。
- 完整状态机、调用上下文匹配、权限组合、JSON Schema 和协议校验由 .NET 领域层实现。
- 数据库只保留结构完整性、唯一性、引用完整性、不可变证据、终态保护以及令牌/验证码等关键原子安全底线。

## 4. 文件职责

### 4.1 bootstrap.sql

负责：

- `pgcrypto` 扩展；
- Database、Extension、18 个 Schema 的显式 COMMENT；
- `core.schema_migration` 与迁移登记函数；
- `core.public_id_ledger` 与公开 ID 原子登记；
- updated_at、row_version、epoch、追加型对象和终态保护等跨模块基础触发器函数。

这两个基础表和函数是所有模块的共同前置，因此保留在 bootstrap，而不是放入 `core/build.sql`。

### 4.2 Schema 局部文件

- `tables.sql`：表、追加列、PK/UQ/CHECK、同 Schema FK、显式查询索引、外键前导索引和 COMMENT。
- `routines.sql`：本 Schema 函数/过程、只依赖本 Schema 或 core 基础函数的触发器及 COMMENT。
- `views.sql`：视图与视图列 COMMENT。
- `build.sql`：一个事务内执行局部文件并登记 `baseline:<schema>`；不包含 links 或 seed。
- `README.md`：职责、表清单、依赖、执行方式和 .NET 边界。

### 4.3 links.sql

`links.sql` 归属于被修改的源表 Schema，包含：

- 跨 Schema 外键；
- 调用其他业务 Schema 函数的绑定触发器；
- 为跨域外键补充的非部分前导索引；
- 上述约束、索引、触发器的 COMMENT；
- 独立事务与 `baseline:<schema>:links` 登记。

所有表已在第一阶段创建，因此循环依赖不会影响建表。

### 4.4 seed.sql

只有 `core`、`org`、`authz` 存在基线种子。种子必须幂等，并在跨域 links 完成后执行。

### 4.5 平台级文件

- `finalize.sql`：调用注释补全函数检测遗漏；只要返回非零就抛错并回滚，不把运行时补全当作基线实现，也不动态生成业务约束或外键索引。
- `roles.sql`：NOLOGIN 角色、对象所有权、最小授权、列级授权和默认权限。
- `rls_optional.sql`：可选 RLS，不进入默认构建。
- `verify.sql`：统一静态契约在数据库实例上的结构验收。
- `build.sql`：按正确阶段一键编排。

## 5. 执行顺序

### 5.1 一键构建

```powershell
psql --dbname "$env:KUC_DATABASE_URL" --file docs/database/baseline/build.sql
```

### 5.2 按 Schema 分步构建

1. 执行 `baseline/bootstrap.sql`。
2. 逐个执行 18 个 `baseline/schemas/<schema>/build.sql`。这些文件之间没有业务表级前置依赖。
3. 全部局部对象完成后，逐个执行 18 个 `links.sql`。
4. 执行 `finalize.sql`。
5. 执行 `core/seed.sql`、`org/seed.sql`、`authz/seed.sql`。
6. 执行 `roles.sql`。
7. 以 `kuc_owner` 执行 `verify.sql`。
8. 只有在事务级租户上下文经过连接池集成测试后，才使用可 `SET ROLE kuc_owner` 的迁移账号单独执行 `rls_optional.sql`；脚本在事务内切换到对象所有者。

`build.sql` 使用 PostgreSQL advisory lock，避免同一数据库并发构建。

## 6. COMMENT 设计

COMMENT 与对象定义位于同一 SQL 文件，而不是集中在单独注释脚本。

默认基线显式覆盖：

- Database；
- Extension；
- Schema；
- Table；
- View；
- Column；
- Function / Procedure；
- Index，包括 PK/UQ 的约束支撑索引；
- Constraint；
- Trigger；
- Role。

可选 RLS 文件在创建 Policy 后立即添加 Policy COMMENT。当前模型未使用独立 Sequence、Materialized View、Type 或 Domain；验收脚本仍检查这些维度，一旦后续新增就必须同时添加 COMMENT。

`core.fn_apply_complete_column_comments` 与 `core.fn_apply_complete_object_comments` 只作为迁移遗漏的安全网。正常基线执行时，显式 COMMENT 应已完整，安全网不应承担主要注释生成职责。

## 7. 数据库与 .NET 责任边界

数据库继续保证：

- 类型、非空、PK、UQ、简单 CHECK；
- 同域和跨域引用完整性；
- 所有外键的非部分前导索引；
- 公开 ID 不可复用、row_version 单调递增、security epoch 不回退；
- 审计/撤销/投递等证据追加不可变；
- 已登记终态不能离开；
- Refresh Token 轮换、授权码/验证码/设备码消费等必须原子完成的安全动作；
- 发布对象与控制面审批之间的关键数据库绑定。

.NET 10 领域层负责：

- 完整状态迁移图和动作权限；
- tenant、business line、actor、client、session、grant、consent、risk 等上下文匹配；
- 策略优先级、冲突处理、授权义务与错误码映射；
- JSON Schema、URI/SSRF、协议报文、密码学算法 allowlist；
- 跨聚合流程、补偿、幂等编排和审计事件内容。

具体规则见 [.NET 业务规则与状态机实现清单](./.NET业务规则与状态机实现清单.md)。

## 8. SqlSugar 接入约束

- 实体显式声明 Schema 与表名，不依赖 `search_path`。
- 写操作使用数据库事务和显式隔离级别；不使用 SqlSugar 自动建表替代基线。
- 对含 `row_version` 的表执行 compare-and-set 更新。
- 安全消费、轮换、撤销和水位推进使用单条原子 SQL 或数据库函数。
- RLS 启用时，`SET LOCAL app.tenant_id` 必须和业务 SQL 位于同一事务、同一物理连接。
- PostgreSQL 的 `jsonb`、数组、`bytea`、`timestamptz`、部分索引和 `NULLS NOT DISTINCT` 必须按 [SqlSugar 接入约定](./SqlSugar接入约定.md) 显式映射。

## 9. 后续迁移

空库基线稳定后，`migrations/` 仅存放版本优先的增量变更：

```text
migrations/
└─ YYYYMMDD_NNN_change_name/
   ├─ README.md
   ├─ up.sql
   └─ verify.sql
```

增量 SQL 必须声明受影响 Schema、锁风险、数据回填方式、.NET 兼容窗口、COMMENT 变化与验证条件。本方案不生成回滚脚本；未上线阶段通过重建空库修正基线。

## 10. 验收范围

`baseline/verify.sql` 检查：

- 18 Schema、145 张表、3 个视图及全部基线版本；
- Database/Extension/Schema/Table/View/Column/Index/Constraint/Trigger/Routine/Role/Policy COMMENT；
- 缺失外键前导索引；
- public_id、row_version、updated_at、安全 epoch 与敏感字段加固；
- 关键数据库触发器完整性；
- 禁止把已下放到 .NET 的完整业务状态机重新塞回数据库；
- RLS 启用时的直接与派生租户策略。

当前工作只进行文件级和静态验证，不连接 PostgreSQL 实例。
