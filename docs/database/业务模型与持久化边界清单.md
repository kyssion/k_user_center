# 业务模型与数据库持久化边界清单

> 本文件只定义业务模型需要持久化的事实、逻辑关系和数据库应承担的硬边界，不定义具体语言、类、接口、Handler、Repository、API 路由或事务代码。进入编码阶段后，应另行生成代码实施文档；该实施文档不得反向改变本文件已经确认的业务语义和持久化事实。

## 1. 数据库文档范围

数据库文档回答以下问题：

1. 业务模型是否有足够的稳定事实支撑状态恢复、查询、审计、撤销、对账和迁移。
2. 哪些对象拥有独立生命周期，哪些只是值对象、快照、事件或逻辑关系。
3. 哪些事实必须结构化为独立字段，哪些扩展内容可以进入版本化 JSON。
4. 哪些完整性边界必须由 PostgreSQL 最终兜底。
5. 哪些规则明确不属于数据库，后续实施必须在应用层完成。

数据库文档不回答代码目录、类名、方法签名、框架用法、外部组件调用顺序和 API DTO；这些内容属于后续代码实施文档。

## 2. 持久化原则

1. 只有独立、稳定、需要查询、审计、恢复或对账的数据事实才建表或独立字段，不把代码流程步骤机械翻译成表。
2. PostgreSQL 保存状态值、版本、原因、业务时间和结果事实，但不定义状态全集、合法转换、授权条件、风险处置或审批流程。
3. PostgreSQL 不创建 Foreign Key、业务 Trigger、持久化业务 Routine、PostgreSQL Enum 或表达业务语义的 View。
4. 逻辑引用只保存标识和查询索引；目标存在性、类型、租户/业务线一致性、生命周期和权限由后续实施负责。
5. Primary Key、Unique、NOT NULL、数据类型、长度、行内基础 Check、`row_version`、必要原子消费和面向部署身份的粗粒度技术权限属于数据库硬边界。
6. 唯一性和 CAS 不得只依赖“先查询再写入”的应用判断，数据库必须作为并发竞争的最终裁决者。
7. JSONB 只承载版本化配置、协议扩展、快照、证据和低频扩展属性；高频过滤、唯一性、逻辑关系、安全水位和生命周期字段必须独立建模。
8. `operations + operation_steps` 只保存跨事务流程的权威状态、检查点、结果和证据，不在数据库中建设工作流引擎。
9. Outbox、Audit Outbox、幂等结果与权威事实需要同事务持久化，但事件生成、投递、补偿和重试语义不在数据库中实现。
10. 敏感原文不落库；数据库只保存密文、摘要、盲索引、公开材料和 KMS/HSM 引用。
11. 追加事实和不可变版本以代码中的只追加命令/仓储接口、版本新增规则、摘要校验和审计为主要保护；审计、敏感存储和选定的高价值追加证据表可额外使用粗粒度数据库 Grant 防御纵深，但不要求数据库角色表达业务主体、作用域、Owner 或每个状态的可写性。
12. 数据库对象的存在不代表当前阶段必须实现全部业务能力；建设阶段由能力与实施计划决定，数据库模型保持目标态语义一致。
13. 每张逻辑表必须映射到一个主要业务模型和一个权威持久化域；领域文档中的“持久化范围”可以包含复用表，但不得据此形成第二个权威状态或未声明的并行写入方。
14. “持久化原子性”描述必须共同提交的数据库事实，不等同于类、Handler 或事务代码设计；后续实现可以选择技术方式，但不得拆散已经确认的原子边界。
15. 最终用户、管理员、租户、数据范围、领域 Owner 和业务操作权限由用户中心代码默认拒绝地校验；数据库账号不映射这些业务主体和作用域。
16. 基线不依赖 RLS、数据库 Policy、`SECURITY DEFINER`、按租户建账号/Schema 或存储过程承载业务授权，以保持数据库升级、迁移和替换路径可控；少数存储安全特性只能作为防御纵深，不得成为业务正确性的唯一来源。

## 3. 业务模型持久化检查

下表“数据库硬边界”只登记当前 DDL、事务原子性或技术 Grant 能够最终裁决的结构约束。跨表存在性、无法由目标表唯一约束直接覆盖的跨 Range 分区全局唯一/业务幂等、追加/不可变语义、状态转换和业务授权必须登记在“非数据库职责与后续关注”中；审计以及选定高价值追加证据表的技术 Grant 是明确的粗粒度防御纵深，但仍不代替代码契约。

| 用户自助安全中心 | 复用 `identifiers`、`authenticators`、`authentication_attempts`、`devices`、`sessions`、`authorization_grants`、`consents`、`privacy_requests`、`profile_documents` | 自助操作所依赖的权威事实仍归原领域表保存，不建立第二套 SSC 状态 | 不新增重复用户、凭证、会话、Grant 或 Consent 表 | 自助视图、命令编排、最后凭证保护、脱敏活动历史、撤销入口和通知偏好 |

## 4. 共享表与跨域写入权威

“权威域”负责表结构语义、生命周期字段和并发写入规则；“使用域”可以读取、引用或按统一追加契约写入事实，但不得自行定义更弱状态、绕过 CAS/唯一性或并行维护同一事实。若一个共享载体承载多个领域实例，则必须由稳定类型或能力编号确定每一行的唯一业务 Owner。这些是代码模块、应用服务、命令与仓储边界，不要求为每个领域或每一行建立对应的数据库角色、RLS Policy 或动态 Grant。

| 共享持久化载体 | 权威域 | 使用域 | 写入边界 |
|---|---|---|---|
| `operations`、`operation_steps` | OPS | API 及所有需要跨事务恢复的领域 | OPS 拥有模型和状态字段；每个 Operation 由 `capability_code/operation_type` 确定唯一业务 Owner，只有该 Owner 可以推进对应实例，其他领域不得并行改写状态或步骤。 |
| `user_identities` | ID | FED、AUTH、SSC | ID 持有身份链接生命周期；FED 提供外部身份源事实并消费链接结果，不得直接形成第二套链接、解绑或防接管状态。 |
| `identifiers`、`identifier_bindings` | ID | SSC、AUTH、PROFILE | ID 持有标识、验证和绑定生命周期；使用域只能引用当前有效事实或提交受控命令，不得另建联系方式占用状态。 |
| `login_transactions`、`authentication_contexts` | AUTH | OAP、ASR | AUTH 持有登录事务和认证上下文；OAP 使用其完成协议交互，ASR 使用其计算保证等级，均不得跳过未完成事务或改写认证证据。 |
| `oauth_clients`、`api_resources`、`oauth_scopes` | OAP | PLT、CTRL、API、SESSION | OAP 持有协议对象、安全水位和生命周期；PLT 负责接入编排，CTRL 负责配置审批，使用域不得绕过 OAP 直接改变有效配置或状态。 |
| `authorization_grants` | OAP | SESSION、SSC、PRIV | OAP 持有 Grant 生命周期；SESSION/SSC/PRIV 只能查询、请求撤销或消费撤销结果，不得直接形成另一套授权状态。 |
| `approval_cases`、`approval_actions` | CTRL | ASR、OPS 及所有高风险操作领域 | CTRL 持有审批单和动作证据；发起域保存请求摘要/资源版本并消费审批结果，不得自行写入审批结论或执行终态。 |
| `revocation_entries` | SESSION | OAP、AUTH、KEY、PRIV、RISK | SESSION 持有统一撤销事实和查询语义；使用域提交撤销目标与原因并消费水位，不得建立独立 Denylist 或改写已有撤销记录。 |
| `devices`、`sessions`、`session_participants` | SESSION | SSC、OAP | SESSION 持有设备和会话生命周期；SSC 只展示和提交退出命令，OAP 只引用会话事实，不得复制登录态或直接放宽撤销结果。 |
| `authenticators`、`credential_materials`、`password_history`、`recovery_code_batches`、`recovery_codes`、`authentication_attempts` | AUTH | ASR、SSC | AUTH 持有认证器、凭证材料、恢复码和认证尝试；ASR/SSC 只能发起受控恢复或展示命令，不得直接降低保证等级或修改材料状态。 |
| `identity_assurance_assertions` | PROFILE | ASR、AUTH、PRIV | PROFILE 持有保证断言及撤销事实；ASR 定义和使用保证等级模型，其他使用域只引用有效断言和最小证据，不得自行提升断言等级。 |
| `user_profiles`、`profile_documents` | PROFILE | SSC、PRIV | PROFILE 持有资料版本和字段权威；使用域按授权读取或发起隐私处理，不得建立不可对账的资料副本。 |
| `consents`、`privacy_requests`、`data_export_artifacts` | PRIV | SSC、OAP、PROFILE | PRIV 持有 Consent、隐私请求和导出物生命周期；使用域只能展示、引用或提交受控请求，不得改写合法依据与撤回状态。 |
| `configuration_versions`、`configuration_releases`、`configuration_release_items` | CTRL | PLT、OAP、RISK、KEY、MSG、FED 及其他配置消费域 | CTRL 持有版本、审批和发布状态；业务域可以生成候选或验证结果，但不得原地修改已发布版本或绕过发布指针。 |
| `business_lines` | TENANT | PLT、OAP、AUTHZ | TENANT 持有业务线生命周期；使用域只引用作用域和安全水位，不得建立重复业务线台账。 |
| `user_role_assignments`、`group_role_assignments`、`machine_role_assignments` | AUTHZ | TENANT、MACHINE | AUTHZ 持有角色授予关系、范围和有效期；主体领域提供被授权对象事实，不得直接形成绕过策略与审计的第二套角色关系。 |
| `applications`、`resource_quotas`、`usage_records` | PLT | OAP、OBS 及业务接入域 | PLT 持有应用、配额和使用计量模型；OBS 读取或聚合观测，业务域只按幂等计量契约提交用量，不得修改历史记录。 |
| `audit_events` | OBS | 所有产生审计事实的领域 | OBS 持有 Schema、权限、分区和留存；各领域只能通过审计 Writer 追加自身动作事实，任何普通业务角色不得更新或删除。 |
| `outbox_events`、`inbox_messages` | EVENT | 所有事件生产者和消费者 | EVENT 持有信封、去重、分区和保留契约；生产者在本地权威事务中追加 Outbox，消费者按统一契约写 Inbox，不得改写其他领域事件或消费记录。 |

未列入本表且只出现在一个领域持久化范围内的表，其权威域即对应业务模型所属领域。新增共享表或新增第二使用域时，必须先更新本节再修改 SQL。

## 5. 模型变更判定

新增业务要求时，按以下顺序判断是否需要调整数据库：

1. 是否产生新的独立生命周期对象或需要长期审计的事实；若否，优先扩展现有模型。
2. 是否需要按该值高频过滤、唯一约束、建立逻辑关系或执行安全水位判断；若是，使用独立字段，不隐藏在 JSONB。
3. 是否只是可重算决策、中间计算结果或代码流程；若是，不建立永久表。
4. 是否跨越同步事务边界并需要恢复；若是，复用 `operations + operation_steps`。
5. 是否是历史版本；若是，新增不可变版本，不原地改写已发布内容。
6. 是否需要数据库最终解决并发竞争；只有唯一性、CAS、单次消费和必要原子写入进入数据库硬边界，其余业务判断留给后续实施。

## 6. 与后续代码实施文档的关系

进入代码阶段后，应基于本文件另行生成实施文档，补充命令、接口、类、事务步骤、外部依赖、错误码和测试。实施文档可以选择实现方式，但必须满足以下约束：

- 不新增与本文件重复的权威事实。
- 不绕过数据库唯一性、CAS 和已明确的技术访问隔离；不绕过代码中的业务授权、领域 Owner 和追加/不可变写入边界。
- 不把状态机、授权、风险、审批或跨系统工作流下沉为数据库 Trigger/Routine。
- 发现业务模型无法表达需求时，先回到数据库模型评审，不通过临时 JSON 字段或影子表规避。
