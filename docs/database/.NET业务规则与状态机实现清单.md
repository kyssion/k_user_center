# .NET 10 业务规则、状态机与上下文匹配实现清单

> 文档版本：v1.0  
> 适用技术栈：.NET 10、SqlSugar、PostgreSQL 16+  
> 规范来源：`docs/能力地图.md` v1.3、`docs/统一身份与访问平台建设与验收蓝图.md` v1.3  
> 数据库边界脚本：`baseline/schemas/*/tables.sql`、`routines.sql` 与 `links.sql`

## 1. 目的与边界

本文件把原先散落在数据库触发器中的领域规则整理为 .NET 实现清单。状态集合和合法转换仍以能力地图 §3.4、蓝图对应领域章节为权威；本文件定义代码应在什么事务内读取哪些上下文、如何比较、如何并发更新、写哪些证据以及返回什么错误。

数据库继续负责：

- 主键、外键、`NOT NULL`、数据类型、长度、哈希长度和简单 `CHECK`。
- 全局/范围唯一性、部分唯一索引和外键前导索引。
- `row_version` 自动递增、security/consent epoch 不回退。
- 公开 ID 永不复用、审计/Outbox/风险/迁移日志不可改写。
- Refresh Token 代际、单一 `CURRENT`、successor 和重放失陷的原子处理。
- Authorization Code 单次消费与重放处置、Reference Token 撤销不可逆。
- 设备挂失与关联 Session/Token Family 撤销同事务完成。
- 已完成、已撤销、已销毁等终态不得恢复，以及迁移不可逆边界。

.NET 负责：

- 聚合初态、完整合法转换图、转换前置条件、状态原因和状态时间写入。
- User、Client、Tenant、Organization、Consent、Approval、Risk 等跨表上下文匹配。
- scope/resource 子集、角色/成员范围、授权决策新鲜度、审批人数与职责分离。
- 规范化上下文摘要的生成与比对。
- 同一事务内推进 epoch、撤销相关对象、写 Outbox/Audit Outbox。
- 协议、密码学、风控、隐私、授权和远端系统校验。

原则：数据库不再维护第二套完整业务规则；应用也不得绕开数据库的唯一性、终态和一次性消费底线。

OAuth/OIDC、SAML、SCIM、FIDO/WebAuthn 和密码学原语仍按能力地图要求采用成熟、持续维护并经审计的组件；本清单只定义平台领域上下文、持久化事务和组件扩展点，不授权自行重写协议解析、签名验证、Token 编解码或认证算法。

## 2. 建议的 .NET 代码结构

每个聚合只暴露命令式用例，不提供可任意修改 `*_state` 的通用 Repository 方法。

```text
Application/
  Identity/Commands/ActivateUser.cs
  Authentication/Commands/CompleteLoginTransaction.cs
  Authorization/Commands/ActivateGrant.cs
  Organization/Commands/AcceptInvitation.cs
  Privacy/Commands/DecideConsent.cs
  Control/Commands/ExecuteApproval.cs
Domain/
  StateMachines/IStateTransitionPolicy.cs
  Rules/IBusinessRule.cs
  Context/IContextHashService.cs
  Errors/DomainErrorCodes.cs
Infrastructure/
  Persistence/SqlSugarUnitOfWork.cs
  Persistence/*Repository.cs
  Time/DatabaseClock.cs
```

建议公共抽象：

```csharp
public interface IStateTransitionPolicy<TState>
{
    void EnsureAllowed(TState from, TState to);
}

public interface IBusinessRule<in TContext>
{
    ValueTask CheckAsync(TContext context, CancellationToken cancellationToken);
}

public interface IContextHashService
{
    byte[] Sha256<T>(T canonicalContext);
}
```

状态机策略应为无副作用纯代码；数据库读取、锁、更新、Outbox 和审计由 Application Command Handler 组织。

## 3. 统一事务模板

涉及状态、epoch、单次消费、审批执行、邀请接受、Consent 决定或 Token 签发的命令必须使用显式事务：

1. 读取幂等记录；同键不同请求摘要立即返回 `IDEMPOTENCY_CONFLICT`。
2. 按固定顺序锁定本次会修改的聚合根、计数器和单次消费行；纯读取依据不默认使用 `FOR UPDATE`。
3. 一致性读取所需上下文，记录其 `row_version`、epoch、策略版本或有效期，执行状态转换和业务规则。
4. 用 `WHERE id = @id AND *_state = @expected_state AND row_version = @expected_version` 条件更新。
5. 状态时间来自数据库可信时钟；一个命令需要多表共享时间时先读取一次 `clock_timestamp()`，后续写入复用同一时间值。
6. 检查影响行数必须为 1；否则返回并发或状态冲突。
7. 同事务写撤销记录、Outbox、Audit Outbox 和幂等响应摘要。
8. 数据库事务内不得调用短信、邮件、Webhook、IdP、KMS/HSM 等远端服务；通知类副作用提交后由 Outbox 驱动。

SqlSugar 推荐使用参数化原生 SQL 处理锁和条件更新：

```csharp
var result = await db.Ado.UseTranAsync(async () =>
{
    var aggregate = await db.Ado.SqlQuerySingleAsync<MembershipRow>(
        """
        SELECT * FROM org.membership
         WHERE id = @id
         FOR UPDATE
        """,
        new SugarParameter("@id", membershipId));

    membershipTransitions.EnsureAllowed(aggregate.State, "ACTIVE");
    await membershipRules.CheckAsync(context, cancellationToken);

    var affected = await db.Ado.ExecuteCommandAsync(
        """
        UPDATE org.membership
           SET membership_state = 'ACTIVE',
               joined_at = clock_timestamp(),
               state_reason_code = @reason
         WHERE id = @id
           AND membership_state = @expected_state
           AND row_version = @expected_version
        """,
        new SugarParameter("@reason", reasonCode),
        new SugarParameter("@id", membershipId),
        new SugarParameter("@expected_state", aggregate.State),
        new SugarParameter("@expected_version", aggregate.RowVersion));

    if (affected != 1)
        throw DomainErrors.OptimisticLockConflict();

    await outbox.AppendAsync(...);
});
```

必须先完成远端校验或生成的命令，使用 `Async Operation + step` 分阶段执行：先在短事务中登记待办，事务外调用远端，再在新事务中校验返回证据并完成状态转换；不得为等待远端响应长期占用数据库锁。

全局锁级别统一为：幂等记录 → Business Line/Tenant/Organization → User/Machine/Client → 主业务聚合 → Authorization/Risk/Consent/Approval 依据 → 子对象。只锁本次会更新或必须串行分配的行；同一级批量对象按 UUID 升序。若具体命令无法遵循该顺序，必须在 Handler 旁登记专用锁计划和并发测试。

## 4. 通用校验顺序

所有高风险命令按以下顺序执行，避免不同 Handler 产生不同失败语义：

1. 请求格式、枚举和必填字段。
2. 幂等键及请求摘要。
3. Actor 身份、认证强度、风控处置和安全冻结状态。
4. Tenant/Business Line/Organization 隔离范围。
5. 聚合当前状态、版本和有效期。
6. 授权决策：主体、动作、资源、Tenant、策略版本、PIP 版本、security epoch 与 `valid_until`。
7. 业务上下文匹配和不可扩张规则。
8. 状态转换及必须写入的原因、时间、审批/风险证据。
9. epoch、撤销、Outbox、审计和幂等结果。

任何第 3 至 8 步失败都不得产生部分状态更新。

## 6. 状态机 Handler 的必做副作用

### 6.1 User、Identifier、Authenticator、Device

- User 冻结、删除、匿名化、合并、解冻均必须更新适用 `user_security_epoch`；冻结、删除和合并同时撤销 Session、Token Family、有效 Grant，并写 `revocation_record`。
- `ANONYMIZED`、`ERASED`、`MERGED` 为数据库保护终态；删除撤回只允许冷静期内、完成重新强认证且不存在不可逆步骤。
- Identifier 验证前校验所有权证明；解绑后依次进入隔离和释放。写 `identifier_tombstone` 后不得删除；隔离期内不得重新绑定。
- Authenticator 激活/恢复前校验 User 可认证；失陷时推进 User epoch 并撤销相关 Session/Token Family；`REVOKED/REPLACED` 不恢复。
- Device 挂失只调用普通设备状态更新，数据库触发器会原子撤销关联 Session/Family；解除挂失前 .NET 必须完成强认证和风险复核，且不得自动恢复 TRUSTED。

### 6.2 Login Transaction、Challenge、Grant、Session、Token

- Login Transaction 的请求上下文在离开 `CREATED` 后视为不可变：Client、Tenant、redirect URI、PKCE、scope/resource、Profile、nonce/state 摘要不得替换。
- 每次状态推进写对应时间；`BLOCKED` 必须写原因，恢复后保留历史证据。
- Challenge 尝试次数每次只加 1；验证成功不等于业务成功，业务命令必须再消费一次。
- Grant ACTIVE 后主体、Client、Tenant、scope/resource、Consent 和 epoch 快照不可改；变更需求必须新建 Grant。
- Session/Token Family 失陷或撤销必须写原因、时间、撤销记录和 Outbox；资源服务器缓存键包含所有适用 epoch。
- Refresh Token 必须继续使用数据库 `oauth.fn_mark_refresh_token_reuse` 处理已用 Token 重放，不得改为纯应用标记。

### 6.3 Business Line、Tenant、Organization、Membership、Invitation

- 暂停/关闭 Business Line 前检查所有下属 Tenant；越过 `irreversible_at` 后只能前向完成或补偿。
- 关闭 Tenant 前停止新登录/授权，撤销活动 Session/Token，处理 Client、Membership、Webhook 和数据保留任务；推进 `tenant_security_epoch`。
- Organization 改父级时在同事务锁定旧/新父链并检测循环；数据库仍保留组织树和用户组循环底线。
- Membership 的 Business Line/Tenant/Organization 必须与 Role 和 Authorization Decision 一致；业务解封不得改变 User 全局冻结状态。
- Invitation 接受使用 `UPDATE ... WHERE invitation_state='PENDING' AND row_version=@version`；100 并发最多一个成功。

### 6.4 Consent、Approval、Release

- Consent Aggregate 使用 `SELECT ... FOR UPDATE` 串行分配 `consent_version` 和 `current_epoch`；PENDING 不推进 epoch，有效决定变化才推进一次。
- Consent 上下文一经创建不可改；变更用途、类别、recipient、Client 或范围时新建版本。
- Approval Decision 追加写入，不修改不删除；审批 Handler 校验发起人与审批人分离、风险快照一致和决定理由。
- Approval 执行使用新 `Guid.CreateVersion7()` 或加密安全 UUID 作为 `execution_id`，依靠唯一约束和条件更新确保仅执行一次。
- Release 离开 DRAFT 后内容摘要和内容引用不可原地修改；回滚创建新 Release，不改旧版本。数据库保留内容不可变和终态底线，转换顺序与审批匹配由 .NET 负责。

### 6.5 Machine、Delegation、Crypto、Emergency Access

- Machine 从 SUSPENDED 恢复前重新验证 Owner、用途、环境、权限、到期和凭证，写新的 `last_revalidation_evidence_hash` 并推进 epoch。
- Credential 轮换允许短重叠窗口；新凭证激活成功后再撤销旧凭证，任何失败必须可重试且不留下两个长期活动凭证。
- Trust Bundle、Certificate、JWKS、Key Asset 只通过版本发布，不原地替换公钥材料或内容摘要。
- Delegation 每次鉴权都计算 Subject 权限、Actor 权限、委托允许动作和禁止项的交集，不把 ACTIVE Delegation 当作静态角色。
- Security Exception 和 Break-glass 必须有自动到期任务；到期任务同样使用状态 + row_version 条件更新，重复执行幂等。

### 6.6 Operation、Privacy Request、Migration

- `BLOCKED/PARTIAL` 是可恢复状态，不得当作终态；恢复前验证阻断条件已消失。
- Operation/Privacy Request 每个外部步骤写独立 step/task，主表只汇总状态；远端调用不持有数据库事务。
- Migration 阶段顺序由 Orchestrator 实现；数据库只保护 `COMPLETE`、`irreversible_at` 和切换后的 `authority_side=PLATFORM`。

## 7. 规范化上下文摘要

所有摘要使用 SHA-256，输入为 UTF-8 编码的 Canonical JSON。必须提供共享 `ContextHashService`、固定 DTO 和黄金测试向量，禁止 Controller 自行拼 JSON。

规范化规则：

- 属性名和 DTO 字段集合固定；未知字段不得进入摘要。
- UUID 使用小写 `D` 格式；`bytea` 使用小写十六进制；时间转换为 UTC Unix 秒。
- 集合去重后按 ordinal 升序；对象字典按 key ordinal 升序递归规范化。
- `null` 与缺失字段语义不同；固定 DTO 中需要参与摘要的可空字段必须显式输出 `null`。
- 数值使用不带区域设置的 JSON 数字；禁止浮点参与安全上下文，比例使用定点整数或 decimal 规范文本。
- 摘要比较使用 `CryptographicOperations.FixedTimeEquals`；日志只记录摘要前缀，不记录敏感原文。

固定摘要字段：

| 摘要 | 字段 |
|---|---|
| Delegation | `subject_user_id`、`actor_user_id`、`tenant_id`、排序后的 `allowed_actions`、`resource_scope`、排序后的 `prohibited_operations`、`max_depth`、`parent_delegation_id`、`risk_assessment_id`、两侧 assurance hash、`valid_from`、`valid_until` |
| Trust Bundle | `trust_domain`、`bundle_version`、`issuer`、排序后的 `allowed_audiences`、`environment`、`selector_schema`、`public_material`、`max_attestation_age_seconds`、`active_until` |
| Security Exception | `exception_code`、排序后的 `requirement_ids`、`scope_definition`、`risk_statement`、`compensating_controls`、`risk_acceptor_ref`、`owner_ref`、`tenant_id`、`starts_at`、`expires_at` |
| Break-glass | `user_id`、`tenant_id`、排序后的 `permission_codes`、`justification`、`expires_at`、`post_review_due_at` |
| Consent | `aggregate_id`、`purpose_code/version`、排序后的类别和 scope、`recipient_code`、`source_client_id` |
| Challenge Risk | Risk Assessment 的完整输入 DTO；`risk_context_hash` 必须等于不可变 `risk_assessment.input_hash` |

Approval 的 `after_value_hash` 必须直接使用目标资源对应摘要，不能再对摘要包一层 JSON 后重复哈希。

## 8. 错误与并发语义

| 条件 | 返回错误 |
|---|---|
| `row_version`、expected state 或单次消费条件不成立 | `OPTIMISTIC_LOCK_CONFLICT`；已知被消费时返回领域专用 `*_ALREADY_CONSUMED` |
| 唯一索引冲突 | 映射为 `IDENTIFIER_ALREADY_BOUND`、`INVITATION_ALREADY_ACCEPTED`、`ACTIVE_GRANT_EXISTS` 等稳定领域码 |
| 跨 Tenant/Organization/Client 上下文不一致 | `CONTEXT_SCOPE_MISMATCH`，对外不泄漏目标是否存在 |
| 状态边不合法 | `INVALID_STATE_TRANSITION`，记录对象类型、public ID、from/to，不记录敏感内容 |
| 审批已使用或失效 | `APPROVAL_NOT_EXECUTABLE` |
| Risk/Authorization Decision 过期 | `DECISION_STALE`，调用方重新评估，不自动重试旧决定 |
| PostgreSQL `40001`/`40P01` | 仅幂等命令可按退避重试，默认最多 3 次 |

禁止把 PostgreSQL 异常文本直接返回 API；按 SQLSTATE、约束名和命令上下文映射到 `core.error_registry`。
表内 `DOMAIN_API` 错误码用于领域层和内部 API；OAuth/OIDC、SCIM、SAML 协议端点必须在边界层映射为相应标准错误，例如将授权码、Refresh Token 或 Grant 上下文失败对外收敛为 `invalid_grant`，不得把内部对象关系泄漏给协议客户端。

## 9. 必须实现的测试

1. 每个状态机生成全部允许边和禁止边的参数化测试；终态恢复同时有 .NET 单元测试和数据库集成测试。
2. 每个上下文矩阵逐字段篡改，任一字段不一致均失败且事务无部分写入。
3. 100 并发 Invitation 接受、Challenge 消费、Approval 执行、Consent 决定和 Refresh Token 轮换最多一个成功。
4. `row_version` 冲突、PostgreSQL 序列化失败和死锁重试不产生重复 Outbox、副作用或 execution_id。
5. Context hash 在 Windows/Linux、不同进程和不同 JSON 属性声明顺序下结果一致；固定黄金向量不可漂移。
6. User/Tenant/Machine epoch 变化后，旧 Grant、Session、Token、Consent 依据立即失效。
7. 设备挂失、Refresh Token 重放和 Authorization Code 重放验证数据库原子安全路径仍然有效。
8. Repository SQL 快照确认所有状态更新包含 expected state 和 `row_version`，所有租户查询包含可信 Tenant 条件。
9. Outbox/Audit Outbox 与领域写入同事务；提交失败时全部回滚，提交成功后消费者可幂等重试。
10. Webhook 激活时并发撤回/更新 Consent，旧 epoch 必须失败；Message Send 逐字段替换 Template/Route/channel/purpose/region，任一不一致均不得入队。
11. `verify.sql` 的 `V024_APPLICATION_RULE_TRIGGER_PRESENT` 必须为零，防止业务触发器被重新引入。

## 10. 实现完成定义

- 每个能力对应一个明确 Command Handler、状态策略、规则集合和自动化测试编号。
- 所有跨表规则均能从本文件矩阵追踪到代码类、蓝图 REQ/INV 和测试。
- 没有 Controller、通用 Repository 或后台任务直接任意更新 `*_state`。
- 没有业务规则同时在 .NET 和数据库触发器中维护两套实现。
- 关键原子安全能力仍通过 `build.sql` 和 `verify.sql` 验证。
