# 统一身份与访问平台（IAM/CIAM）能力地图

> 文档状态：规范基线 v1.4（已与配套蓝图和 PostgreSQL 持久化基线交叉核对；项目级 Owner、交付阶段与代码实施证据矩阵须在阶段 0 实例化）
> 适用范围：集团或平台内多个业务线共用统一用户身份、登录认证与访问控制能力
> 核心目标：一次建设、多业务复用；统一身份、隔离业务；安全可控、标准接入、持续演进
> 配套蓝图：[统一身份与访问平台建设与验收蓝图](./统一身份与访问平台建设与验收蓝图.md)（已发布，承载 MUST 级规范、失败语义、契约与自动化验收编号）
> 文档分工：本文档定义「平台需要具备哪些能力」，使用 `CAP-{领域}-{序号}` 编号，并给出优先级、实现策略和依赖；蓝图定义「每项能力必须满足什么规范、如何验证」，使用 `REQ-`/`INV-`/`API-`/`EVT-`/`AT-`/`SLO-` 编号。两侧领域代码保持一致，可按代码互相检索。

## 1. 平台定位

统一身份与访问平台不是一张公共用户表，也不只是登录注册服务，而是所有业务系统共同依赖的身份基础设施。

平台负责：

- 建立全局、稳定、不可变的用户主体。
- 管理手机号、邮箱、密码、第三方账号、企业账号、Passkey 等登录身份。
- 向 Web、App、小程序、服务端和第三方系统提供统一认证。
- 管理登录会话、令牌、单点登录和账号安全。
- 管理公共用户资料、隐私授权和账号生命周期。
- 提供业务线、租户、组织、成员关系及统一授权能力。
- 提供管理后台、审计、风控、事件通知、SDK 和开放 API。

平台原则上不负责：

- 订单、资产、会员等级、积分、内容、客户标签等具体业务数据。
- 替代 CRM、会员系统、组织人事系统或业务后台。
- 把所有业务数据集中到用户中心。
- 允许业务系统直接访问用户中心数据库。

### 1.1 建设原则

1. **身份与业务解耦**：全局用户只表达“是谁”，业务成员关系表达“在哪个业务中是什么状态”。
2. **认证与授权分离**：认证解决“是谁”，授权解决“能做什么、能访问哪些数据”。
3. **标识与登录名分离**：手机号、邮箱会变化，不能作为用户主键。
4. **公共资料与业务资料分离**：公共信息统一管理，业务私有信息由业务系统负责。
5. **全局状态与业务状态分离**：安全冻结可全局生效，业务封禁只能影响指定业务。
6. **协议优先**：优先使用 OpenID Connect、OAuth 2.0、WebAuthn、SCIM 等标准能力。
7. **默认最小权限**：业务线、管理员、应用和服务只获得完成任务所需的最小权限。
8. **全程可审计**：身份、凭证、权限和管理操作必须留痕。
9. **避免强耦合**：通过标准协议、API 和事件集成，不共享表、不依赖内部实现。
10. **安全与可用性并重**：身份平台属于 Tier-0 基础设施，必须考虑高可用、容灾和应急处置。
11. **保证等级驱动**：身份核验、认证和联合保证等级必须显式建模，敏感操作按等级和认证新鲜度执行。
12. **状态机与不变量优先**：所有关键对象必须定义合法转换、并发语义和不可破坏的不变量。
13. **端到端撤销**：冻结、改密、离职、权限回收和风险事件必须传播到会话、令牌、应用和下游缓存。
14. **机器身份同等治理**：服务账号、工作负载、Client 和代理调用必须具备负责人、最小权限、到期和轮换。
15. **控制面与数据面分离**：配置、策略、密钥和应用接入必须版本化、审批、灰度、回滚并与在线认证隔离。
16. **持续验证而非一次验收**：协议一致性、不变量、租户隔离、密钥轮换、容灾和攻击负向用例必须自动化验证。
17. **恢复路径不降级**：找回、客服处置、管理员恢复和应急操作不得成为绕过 MFA 或审批的低保证后门。
18. **自建与复用分层**：协议实现与密码学原语优先复用经过审计的成熟组件；身份语义、隔离模型、业务状态与标识治理必须自建。复用组件必须能满足本文档的安全 Profile 与撤销时效，否则不得选用。
19. **例外必须登记并到期**：任何偏离 P0 约束的接入或配置都必须登记风险接受人、补偿控制和到期日，到期自动收紧；不留痕的例外等同违规。

## 3. 核心领域模型

### 3.1 核心对象

| 对象 | 定义 | 关键要求 |
|---|---|---|
| Global User | 平台内唯一的用户主体 | UID 永久、不可变、无业务含义、不可复用 |
| Identity | 用户可用于认证的身份 | 手机、邮箱、用户名、微信、Apple、企业账号等，一个用户可有多个 |
| Credential | 证明身份的凭证 | 密码哈希、Passkey 公钥、TOTP 密钥等，与用户资料隔离 |
| Authenticator | 用户实际持有或控制的认证器 | 记录类型、保证等级、状态、登记、替换、挂失、撤销和恢复生命周期 |
| Identifier | 可被识别或检索的标识 | 手机号、邮箱、外部账号 ID；需记录验证状态、归属和历史 |
| Application | 接入用户中心的应用 | 维护 Client、回调地址、协议、密钥、作用域和环境 |
| Business Line | 业务域或产品线 | 作为应用、权限、数据隔离和管理授权边界 |
| Tenant | 企业客户或隔离单元 | 支持租户级账号策略、数据隔离和管理员委派 |
| Organization | 租户内组织结构 | 公司、部门、门店、项目组等 |
| Membership | 用户与业务线、租户或组织的关系 | 保存业务状态、加入来源、业务角色、业务昵称等 |
| Invitation | 加入业务线、租户或组织的邀请 | 邀请人、目标范围、预授权角色、单次使用、过期和撤回 |
| Profile | 用户资料 | 分为平台公共资料和业务扩展资料 |
| Login Transaction | 一次进行中的登录或授权事务 | 保存授权请求上下文、已完成认证因子、剩余步骤和风险快照；短过期、单次消费，未完成不得升级为会话 |
| Operation | 一次跨同步事务边界的异步操作 | 统一承载处理中、阻断、部分完成、失败、取消、人工接管和最终结果；必须绑定幂等键、权限上下文与 Saga |
| Authorization Code | 一次性授权码 | 绑定 Client、redirect URI、PKCE challenge 和 Login Transaction；单次使用，重放即撤销关联授权 |
| Session | 一次持续登录关系 | 关联设备、应用、认证强度、过期时间和风险状态 |
| Device | 跨会话的设备实体 | 指纹、可信状态、推送标识、命名、挂失和撤销，生命周期独立于会话 |
| Authorization Grant | 主体授予 Client 的访问关系 | 关联资源、scope、同意、有效期、撤回和策略版本 |
| Token Family | 一组可轮换的 Refresh Token 关系 | 支持重放检测、家族级吊销、设备和 Client 绑定 |
| Token | 应用访问凭证 | 有 audience、scope、有效期、签发方和吊销机制 |
| Authentication Context | 一次认证的保证上下文 | 记录 IAL/AAL/FAL、acr、amr、auth_time、风险和证据来源 |
| Consent | 用户授权与协议同意 | 记录用途、范围、版本、时间、来源和撤回状态 |
| Role / Permission / Policy | 授权模型 | 支持作用域、数据范围、条件和有效期 |
| Approval Case | 一次高风险操作的审批单据 | 发起人、审批人、类型、理由、附件、前后值、状态和执行结果；发起人不得自审，通过后仅可执行一次 |
| Audit Event | 不可抵赖的操作记录 | 记录操作者、对象、动作、前后值、原因和结果 |
| Risk Event | 登录与账号风险事件 | 保存信号、风险评分、处置动作和证据 |
| Delegation | 一个自然人代表另一个自然人行动的关系 | 监护、代管、协作或客服代理；范围受限、可撤销、被代理人可见，Token 中保留 Actor 与委托链 |
| Machine Principal | 非自然人主体 | 服务账号、工作负载、机器人、设备和代理主体，有负责人、用途和到期 |
| Client / API Resource | OAuth Client 与受保护资源 | 定义认证方式、回调、scope、audience、环境、负责人和生命周期 |
| Policy Decision | 一次授权决策 | 保存输入摘要、允许或拒绝、原因、义务、策略版本和有效期 |
| Security Signal | 持续安全状态信号 | 表达账号失陷、保证等级变化、会话撤销和风险升级 |
| Privacy Request | 数据主体权利请求 | 编排访问、更正、导出、限制、删除、撤回及跨系统证明 |
| Key / Certificate | 密钥与证书资产 | 记录用途、算法、负责人、版本、状态、到期、轮换和吊销 |

### 3.2 ID 体系

建议同时保留四层标识：

| 标识 | 用途 |
|---|---|
| Global User ID | 用户中心内部统一 UID，永久稳定 |
| Subject ID | 通过 OIDC 等协议向应用发布的用户标识，可配置为全局或应用级 |
| Membership ID | 用户在某业务线、租户或组织中的成员标识 |
| External ID | 旧系统、合作方、企业目录中的原始用户 ID |

设计要求：

- UID 不包含手机号、地区、注册时间、业务类型等可推断信息。
- 手机号和邮箱只是可变登录标识，不能作为主键。
- UID、Subject ID、Membership ID 均不得被重新分配给其他用户。
- 账号合并后保留旧 ID 到主账号的受控映射，防止历史数据失联。
- 对外部应用默认使用应用级 Subject，避免一个标识泄漏后串联全部业务数据。
- 只有确有跨业务关联需求的受信任服务，才允许获取 Global User ID。

标识分层实现约束（区分“不可推断”与“不可枚举”两条不同要求）：

| 层次 | 形态要求 | 暴露范围 |
|---|---|---|
| 内部主键 | 允许使用有序 ID（UUIDv7、雪花等）以保证索引局部性与分区效率 | 仅限平台内部存储与索引；禁止出现在对外 API、Token、日志和 URL 中 |
| Global User ID | 不含时间、地区、序号等可推断信息，且不可枚举 | 仅受信任服务可获取 |
| Subject ID | 默认应用级 pairwise，随机且与 Global User ID 无可计算关系 | 对外部应用发布 |
| Membership ID | 不可推断所属业务规模与创建顺序 | 业务线与租户内部 |
| External ID | 保留原系统形态，仅作为映射键 | 仅迁移与对账链路可见 |

### 3.3 数据权威边界

| 数据 | 权威系统 |
|---|---|
| 全局 UID、账号状态、登录身份、凭证 | 用户中心 |
| 公共头像、昵称、已验证手机号和邮箱 | 用户中心 |
| 身份核验断言（IAL 等级、核验时间、证据类型、核验方） | 用户中心；核验实施可由业务或外部服务完成，但断言的存储与解释权在平台 |
| 用户在业务线中的启停状态 | 对应业务线或成员服务 |
| 订单、积分、等级、资产、内容数据 | 业务系统 |
| 企业员工、部门、岗位 | 企业目录或组织人事系统，用户中心同步映射 |
| 角色、权限和策略 | 统一授权中心或明确指定的业务权限域 |

### 3.4 全局状态机与不变量

关键对象必须使用正交状态机，禁止用一个账号状态同时表达生命周期、安全处置和业务状态：

- 用户生命周期：`PROVISIONAL → ACTIVE ⇄ DORMANT`；长期未完成注册且无下游业务事实的 `PROVISIONAL → ERASED`（保留 UID 墓碑）；`ACTIVE/DORMANT → DELETION_PENDING → ANONYMIZED | ERASED`；`DELETION_PENDING → ACTIVE`（冷静期内撤回，须重新强认证）；`DELETION_PENDING ⇄ DELETION_BLOCKED`（法律保留或业务阻断成立/解除）；`ACTIVE → MERGED`（被合并账号终态）。`ANONYMIZED` 保留不可逆摘要，`ERASED` 仅保留墓碑，两者法律含义不同不得合并。
- 认证锁定状态：`ENABLED ⇄ LOCKED`；安全冻结状态独立为 `CLEAR ⇄ FROZEN`。解冻不得清除原有锁定。
- 成员状态：`INVITED → PENDING_APPROVAL → ACTIVE ⇄ SUSPENDED`；`INVITED/PENDING_APPROVAL → REJECTED/EXPIRED`；`ACTIVE/SUSPENDED → BANNED → ACTIVE`（解封需独立授权）；`ACTIVE/SUSPENDED/BANNED → LEFT`。`REJECTED`、`EXPIRED`、`LEFT` 为终态，重新加入必须新建 Membership。
- 邀请状态：`PENDING → ACCEPTED/REJECTED/EXPIRED/REVOKED`，单次消费。
- 认证器状态：`PENDING → ACTIVE ⇄ SUSPENDED/LOCKED → EXPIRED/COMPROMISED/REVOKED/REPLACED`，与 `CAP-AUTH-015` 的状态集一致；`REVOKED`、`REPLACED` 为终态。
- 登录事务状态：`CREATED → IDENTIFIED → PARTIALLY_AUTHENTICATED → AUTHENTICATED`；需要同意时 `AUTHENTICATED → PENDING_CONSENT → COMPLETED`，无需同意时 `AUTHENTICATED → COMPLETED`；另有 `EXPIRED/ABANDONED/BLOCKED` 分支。
- 会话状态：`ACTIVE → EXPIRED/REVOKED`，失陷时先进入 `COMPROMISED` 并撤销。
- Grant 状态：`PENDING → ACTIVE/DENIED/EXPIRED`；`ACTIVE → REVOKED/EXPIRED`。`DENIED/REVOKED/EXPIRED` 为终态。
- Consent 状态：`PENDING → GRANTED/DENIED/EXPIRED`；`GRANTED → WITHDRAWN/EXPIRED/SUPERSEDED`。`DENIED/WITHDRAWN/EXPIRED/SUPERSEDED` 为终态。
- 委托状态：`PENDING → ACTIVE`；`PENDING → REJECTED/REVOKED/EXPIRED`；`ACTIVE → REVOKED/EXPIRED`。`REJECTED/REVOKED/EXPIRED` 为终态。
- 审批单状态：`DRAFT → PENDING_REVIEW → APPROVED → EXECUTED`；`PENDING_REVIEW → REJECTED`；`DRAFT/PENDING_REVIEW/APPROVED → CANCELLED/EXPIRED`。`EXECUTED/REJECTED/CANCELLED/EXPIRED` 为终态。
- 控制面配置：`DRAFT → VALIDATED → APPROVED → STAGED → ACTIVE → DEPRECATED/REVOKED`。
- 业务线状态：`PROVISIONING → ACTIVE ⇄ SUSPENDED`；`ACTIVE/SUSPENDED → CLOSING → CLOSED`，`CLOSING → ACTIVE` 仅在不可逆关闭步骤前允许；暂停或关闭前必须先处置下属 Tenant。
- 租户状态：`PROVISIONING → ACTIVE ⇄ SUSPENDED`；`ACTIVE/SUSPENDED → CLOSING → CLOSED`，`CLOSING → ACTIVE` 仅在不可逆关闭步骤前允许。
- 组织状态：`ACTIVE ⇄ SUSPENDED → CLOSED`；关闭前必须先处置有效子组织和 Membership，`CLOSED` 不得恢复。
- 标识状态：`PENDING → VERIFIED → UNBOUND → QUARANTINED → RELEASED`，隔离期内不得被新持有人绑定，`RELEASED` 只解除唯一键占用、不删除历史墓碑，用户名默认不进入 `RELEASED`。
- 设备状态使用三个正交维度：生命周期 `REGISTERED → RETIRED/REVOKED`，可信维度 `UNTRUSTED ⇄ TRUSTED`，挂失维度 `CLEAR ⇄ LOST`。进入 `LOST` 必须撤销该设备全部会话、Refresh Token 家族与可信标记；解除误报挂失需要强认证、风险复核和审计，不自动恢复可信标记。设备状态不随单个会话结束而改变。
- 验证 Challenge 状态：`ISSUED → VERIFIED → CONSUMED`，另有 `EXPIRED/LOCKED/CANCELLED`，单次消费且绑定用途、Client 与原事务。
- 授权码状态：`ISSUED → CONSUMED`，另有 `EXPIRED/REVOKED`，重放即撤销关联授权。
- Token 家族与实例状态：家族 `ACTIVE → COMPROMISED/REVOKED/EXPIRED`，实例 `CURRENT → USED/REVOKED/EXPIRED`，任一时刻每家族最多一个 `CURRENT`。
- Client 与机器主体状态：Client `DRAFT → VALIDATED → APPROVED → ACTIVE ⇄ SUSPENDED → RETIRED`，`ACTIVE/SUSPENDED → COMPROMISED → RETIRED`；机器主体 `PROVISIONING → ACTIVE ⇄ SUSPENDED → RETIRED`，`ACTIVE/SUSPENDED → COMPROMISED → RETIRED`。暂停恢复必须重新验证 Owner、用途、权限、环境、到期和凭证；失陷主体不得原地恢复。
- 机器凭证状态：`PENDING → ACTIVE ⇄ ROTATING → EXPIRED/REVOKED`；任一可用状态发现失陷时进入 `COMPROMISED → REVOKED`。轮换必须通过不可变的替代凭证链记录，新凭证激活前旧凭证处于受控重叠窗口。
- 工作负载信任包状态：`DRAFT → VALIDATED → APPROVED → ACTIVE → VERIFY_ONLY → RETIRED`；任一非终态可紧急进入 `REVOKED`。回滚通过新建版本完成，不反向改写历史状态。
- 密钥状态：`GENERATED → PUBLISHED → SIGNING_AND_VERIFYING → VERIFY_ONLY → RETIRED → DESTROYED`，失陷时进入 `COMPROMISED → REVOKED`。
- 证书状态：`ISSUED → ACTIVE → GRACE/EXPIRED`，任一非终态可进入 `REVOKED`；证书不得复用通用配置状态。
- JWKS 发布状态：`DRAFT → PUBLISHED → ACTIVE → SUPERSEDED`，任一非终态可进入 `REVOKED`；从发布到激活必须满足缓存传播窗口，取代后旧验证键按 Token TTL、缓存和时钟偏差保留。
- 隐私请求状态：`SUBMITTED → IDENTITY_VERIFIED → IN_PROGRESS`；`IN_PROGRESS ⇄ BLOCKED`，`IN_PROGRESS → PARTIAL → IN_PROGRESS`，完成后进入 `COMPLETED`；证据不足或请求不成立可从未完成状态进入 `REJECTED`。
- 异步 Operation 状态：`PENDING → RUNNING`；`RUNNING ⇄ BLOCKED`，`RUNNING → PARTIAL → RUNNING`；`RUNNING/PARTIAL → COMPLETED/FAILED`；在不可逆边界前可进入 `CANCELLED`。`COMPLETED/FAILED/CANCELLED` 为终态。
- 迁移批次状态：`DISCOVERED → CLEANSED → MAPPED → SHADOW → CANARY → CUTOVER → OBSERVING → COMPLETE`，可逆阶段可进入 `PAUSED/ROLLED_BACK`。

上述状态集必须与蓝图 §4.1 的状态字段登记表保持一致，该登记表为全集（另含 `attestation_state` 与业务线、组织状态）；风险评估使用不可变的 `risk_level + disposition`，不虚构 `risk_state`。每个状态机的转换前置条件、原子结果、失败语义与验收编号见蓝图 §5.3、§7.1、§8.1、§9.1、§10.1、§11.1、§13.1、§13.4、§14.1、§15.1 与 §17，本节只负责收口状态集合，不重复定义转换细节。

实现责任统一为：PostgreSQL 保存权威事实、逻辑关系标识、唯一性、乐观锁版本、安全水位、不可变证据、必要的原子消费边界和部署身份的粗粒度技术隔离；最终用户/管理员授权、租户与数据范围隔离、领域 Owner、完整状态转换、跨对象上下文匹配、审批/风险新鲜度、规范化摘要和流程副作用属于用户中心代码职责。数据库角色不映射业务主体和作用域，也不依赖 RLS、按租户建账号/Schema 或存储过程实现第二套业务权限；若使用数据库特性做防御纵深，必须保留代码契约和可迁移路径。所有运行时技术角色无物理 `DELETE`，业务删除和匿名化由代码及受审批维护流程编排。数据库模型能否支撑这些业务要求见 [`database/业务模型与持久化边界清单.md`](./database/业务模型与持久化边界清单.md)，命令、事务、权限与校验契约见 [`implementation/README.md`](./implementation/README.md)；不得在应用逻辑与数据库触发器中维护两套完整业务规则。

全局不变量：

1. UID、Subject ID、Membership ID 一经签发不得变更、复用或重新分配。
2. 同一唯一性作用域内，一个有效 Identifier 最多绑定一个有效 Global User。
3. 外部身份必须使用协议专用稳定键：OIDC 为 `issuer + sub`；SAML 为 IdP entityID、NameID 值、NameID Format、适用的 NameQualifier、SPNameQualifier 及 SPProvidedID 语义；不得仅凭邮箱静默关联账号。
4. 全局安全状态、业务成员状态、租户状态必须正交建模并按最严格结果执行。
5. 冻结主体不得创建或刷新会话、登记认证器、完成找回或获得新授权。
6. Grant 或权限撤回后不得继续签发相关 Token；高风险权限不得使用过期缓存放行。
7. Client 禁用后不得签发新 Token，存量 Token 必须按安全等级在约定时限内失效。
8. 已匿名化主体不得恢复，旧 UID 只能作为受控墓碑或映射存在。
9. 高风险写入与领域事件必须通过本地事务和 Outbox 保证状态与事件不失配。
10. 相同幂等键和相同请求必须得到相同业务结果；相同幂等键的不同请求必须冲突。
11. Login Transaction 未达 `COMPLETED` 不得签发任何 Session、Token 或 Authorization Code，其标识不得被当作会话标识使用。
12. `ANONYMIZED`、`ERASED`、`MERGED` 均为终态，任何路径不得回到 `ACTIVE`；`DELETION_BLOCKED` 必须携带阻断原因、责任方和预计处理方式。
13. 审批单的发起人不得同时是审批人；审批通过后的执行必须绑定该审批单且不可重复使用。
14. 委托关系不得扩大被代理人的权限边界，且不得用于绕过被代理人本人才能完成的高保证操作。

### 3.5 身份、认证与联合保证等级

平台采用 IAL/AAL/FAL 或等价内部模型：

- **IAL**：自然人或组织身份核验程度，不得由“手机号已验证”推断为“自然人已实名”。
- **AAL**：本次认证强度，区分单因素、多因素、抗钓鱼和硬件保护。
- **FAL**：联合断言的保护程度，包括签名、加密、受众限制和持有者证明。

每个敏感操作必须声明最低保证等级、最大认证年龄、允许的认证器组合和风险上限。`acr` 表达达到的保证等级，`amr` 表达实际认证方式，`auth_time` 表达认证时间，三者不得混用。找回、认证器替换、客服处置和管理员恢复后必须重新计算保证等级。

IAL 的核验实施与断言签发必须分离：证件核验、活体检测、要素比对等**实施**可由业务或外部服务完成；IAL 等级、核验时间、证据类型和核验方的**断言**由平台唯一存储与签发，业务不得自行解释 IAL。首期只支持 IAL1 时必须显式声明并拒受需要更高等级的场景，不得让等级要求空转。

## 4. 详细能力清单

能力编号格式为 `CAP-{域码}-{序号}`。域码与 §2 能力地图、§14 能力所有权一致，并与蓝图的 `REQ-`/`AT-` 域码同名，可按域码在两份文档之间检索。编号一经发布不得复用，能力下线时保留编号并标注废弃。

每张能力表包含六列：

| 列 | 含义 |
|---|---|
| 编号 | `CAP-{域码}-{序号}`，全文唯一，供蓝图、验收清单和工单引用 |
| 能力 | 能力名称。同一能力只在唯一主责小节出现，其他小节只做引用 |
| 子能力 | 该能力必须覆盖的关键点，不是穷举的功能列表 |
| 优先级 | P0/P1/P2 |
| 实现策略 | 自建、复用、集成、暂缓——回答「由谁完成」 |
| 载体 | 代码、设施、流程——回答「在哪一层完成」 |

实现策略取值：

- **自建**：语义、数据与状态机由平台拥有，不得外包给业务方或第三方。
- **复用**：采用经过审计的开源或商业组件，平台负责选型、加固、配置和撤销时效；组件无法满足 §4.14 的安全 Profile 或 §9 的撤销时效时不得选用。
- **集成**：依赖外部服务，例如运营商、外部身份源、短信与邮件供应商、云 KMS；平台只保留断言、映射、审计和降级策略。
- **暂缓**：目标态需要但本轮不建设，必须在所属小节的启用触发中登记可判定的触发条件和责任人。

优先级定义：

- **P0**：目标态关键能力；到达追踪矩阵登记的交付阶段时必须具备，否则该阶段不得发布。P0 不再隐含“全部在阶段 1a 同时交付”。
- **P1**：规模化运营或安全增强能力；具体交付阶段由追踪矩阵登记，不预设为固定阶段。
- **P2**：复杂组织、企业场景或精细化授权能力，按场景启用。

这里的优先级表示目标态关键程度，不直接等同于交付阶段。具体 `phase` 由 §11 和蓝图 §18.4 的追踪矩阵共同确定；发布门禁只检查 `phase` 不晚于当前里程碑的适用能力。P0/P1 属于通用目标态能力；P2 在对应场景启用后即成为该场景上线前的必备能力。因此每个含 P2 的小节都必须给出**启用触发**，以可判定的事实表述，例如接入了某类客户端、开通了某个地区、出现了某类数据；不得写成“视业务需要”。

本文所称“蓝图 §18.4 追踪矩阵”始终指编码阶段维护的正式代码实施与验收矩阵。`docs/database/需求编号与数据库持久化覆盖索引.md` 只说明编号可能使用的数据库事实，不包含 Owner、Phase、接口或逐条测试绑定，不得替代 §18.4 矩阵。

成熟度（手工、半自动、自动化）不在能力表中表达，由 §12 验收清单按能力逐项约定证据形式。

实现策略不是描述性标注而是约束：协议端点、Token 签发与校验、密码哈希、WebAuthn、SCIM、SAML、JWKS、密钥管理这些已有成熟实现的领域必须标为复用或集成，若要改为自建，需按 `CAP-CTRL-006` 登记例外并给出安全团队签署的理由。全文实现策略分布属于可审查指标：若自建比例持续高于预期，说明原则 18 未被真正执行。

载体取值与判定规则：

| 载体 | 含义 | 完成的证据形式 | 主要交付方 |
|---|---|---|---|
| 代码 | 逻辑在服务进程内，随版本发布 | 自动化测试、数据库约束 | 开发团队 |
| 设施 | 主体是部署、网络、存储、云服务、流水线、可观测栈的配置与拓扑 | 声明式配置 + 配置扫描 + 演练 | 平台工程/SRE |
| 流程 | 主体是人的活动：审批决策、演练组织、调查、评估、法务判定 | 记录抽样 + 报告 + 台账快照 | 安全/隐私/法务/SRE/客服 |

判定规则（用于消除主观差异）：大多数能力跨多层，本列只标**主载体**，判断标准是「只交付这一层时，该能力是否基本成立」。例如：`CAP-OPS-009` 高风险审批需要代码实现审批单据与自审阻断，人的审批动作是在使用该功能，故为代码；`CAP-PLT-006` 灾备演练不需要平台实现「演练功能」，故为流程。

载体的约束作用：

- 决定验收证据形式：代码类必须有自动化用例；设施类必须有声明式配置与配置扫描；流程类必须有台账、记录或报告，并指定执行频度。
- 决定 Owner：§14 的第一责任方按域分配，但域内设施类与流程类能力必须另行指定共同交付方，不得默认归给开发团队。
- 决定排期归属：§11 各阶段的工作量估算只对代码类能力成立；设施类与流程类必须单独排期，不得隐含在开发工量里。
- 流程类能力没有编译器与测试兜底，因此必须写明执行周期与责任人；无周期、无责任人的流程类能力视为未交付。

- 例外到期必须默认收紧而不是默认延期；延期本身是一次需要审批的变更。
- `CAP-CTRL-013` 是接入自助的正确形态：接入配置以声明式定义为权威来源，控制面 UI 只是其编辑入口。它与 `CAP-PLT-013` 共用一套版本化与回滚机制，并为 `CAP-CTRL-005` 的漂移检测提供可比对的声明版本；缺少声明源时漂移检测与审批均无法自动化。
- `CAP-CTRL-013` 不得绕过 `CAP-CTRL-001` 的状态机与 `CAP-CTRL-003` 的双人复核：代码仓合并不等于生产生效，高风险变更仍需走审批与分环境晋级。
- 紧急控制允许跳过事前审批，但不允许跳过审计与事后复核，见 `CAP-CTRL-010`。
- 控制面自身的操作审计归 §4.12，本小节不重复定义审计字段。

## 5. 关键业务流程

本章只描述编排顺序与关键判定点：能力定义与优先级见 §4，时限数值统一引用 §9，本章不自行定义任何时间常量。每个流程标注其依赖的能力编号，供 §12 验收追溯。

### 5.1 新用户注册

主责能力：`CAP-AUTH-001`、`CAP-AUTH-002`、`CAP-AUTH-003`、`CAP-AUTH-021`、`CAP-ID-001`、`CAP-ID-004`、`CAP-RISK-011`。

~~~mermaid
sequenceDiagram
    participant U as 用户
    participant A as 业务应用
    participant I as 身份平台
    participant R as 风控
    participant E as 事件总线

    U->>A: 发起注册
    A->>I: 跳转统一注册页
    I->>R: 评估设备、IP、行为风险
    R-->>I: 风险等级与验证要求
    I->>U: 验证手机号/邮箱及必要的 MFA
    I->>I: 创建 Global User、Identity、Membership
    I-->>A: 返回授权码
    A->>I: 换取 Token
    I->>E: 发布用户和成员创建事件
    A-->>U: 完成登录
~~~

注册全程运行在一个服务端 Login Transaction 上（见 §3.1）：已完成的验证步骤、风险结论、待满足要求和过期时间均以会话侧状态为权威，不得由客户端参数声明“已验证”。事务一旦完成或过期即不可重放。

### 5.2 账号合并

主责能力：`CAP-ID-015`、`CAP-ID-016`、`CAP-ID-017`、`CAP-ID-018`。

1. 用户明确发起合并，而不是系统静默合并。
2. 对两个账号分别完成强身份验证。
3. 检查账号状态、风险、实名冲突、租户冲突和资产冲突。
4. 各业务系统返回资产处理策略或阻断原因。
5. 展示不可逆影响并由用户再次确认。
6. 确定主账号，迁移登录身份和成员关系。
7. 旧 UID 保留别名映射，不允许复用。
8. 吊销双方全部会话并要求重新登录。
9. 发布合并事件，执行下游对账。
10. 保存完整审计记录和有限期恢复方案。

### 5.3 修改手机号

主责能力：`CAP-ID-005`、`CAP-ID-008`、`CAP-ID-009`、`CAP-ASR-006`、`CAP-RISK-014`。

1. 验证当前登录态和原手机号；无法使用时进入增强找回流程。
2. 验证新手机号并检查占用、黑名单和风险。
3. 对高风险场景要求 MFA、等待期或人工审核。
4. 修改后吊销高风险会话，通知原、新手机号。
5. 记录历史，但普通管理员不得直接查看完整旧号码。

### 5.4 冻结与封禁

主责能力：`CAP-ID-013`、`CAP-ID-014`、`CAP-OPS-003`、`CAP-EVENT-009`。

- **全局安全冻结**：用户中心执行，阻止所有业务新登录并吊销会话。
- **业务封禁**：仅修改对应 Membership，不影响其他业务。
- **租户停用**：阻止用户进入指定租户，不影响个人账号或其他租户。
- **权限回收**：可独立于账号状态执行，适用于员工转岗、离职等场景。

### 5.5 注销与删除

主责能力：`CAP-ID-020`、`CAP-ID-021`、`CAP-ID-022`、`CAP-ID-023`、`CAP-PRIV-011`、`CAP-PRIV-012`、`CAP-EVENT-013`、`CAP-EVENT-014`。

1. 强身份验证和风险检查；风险不可接受时进入人工复核，不得直接放行也不得静默驳回。
2. 汇总受影响业务、权益、余额、合同和未完成事项。
3. 业务系统返回可注销或阻断结果。存在法律保留、未结算资金或进行中纠纷时进入 `DELETION_BLOCKED`，并向用户返回明确原因、责任方和解除条件；阻断原因消失后必须能回到冷静期继续执行。
4. 用户确认后进入 `DELETION_PENDING`，冷静期时长引用 §9。
5. 冷静期内限制新增关键业务，并允许撤回。撤回必须重新完成与发起时同等强度的认证，撤回动作本身进入审计并作为 `CAP-RISK-014` 的风险信号；撤回后账号回到 `ACTIVE`，不得保留任何降权残留。
6. 冷静期届满后执行全局登出、标识解绑与墓碑登记，并按 §3.4 选定的终态执行：需保留账务与统计关联时进入 `ANONYMIZED`，无保留需要时进入 `ERASED`。两种终态不可互相替代，也不得以“已匿名化”回应“已删除”的请求。
7. 通知各业务系统执行其数据策略，并按 `CAP-PRIV-012` 覆盖备份、日志、事件、索引、分析与训练副本；备份介质允许按备份周期延迟，但必须登记预期完成时间并可验证。
8. 由 `CAP-EVENT-014` 逐系统对账并形成可审计的处理结果；存在下游未完成时不得对用户宣布完成，只能返回处理中及预计完成时间。
9. 身份源侧发起的注销（`CAP-FED-014`）、用户自助注销（`CAP-SSC-009`）与客服代办注销走同一编排，不设旁路。

### 5.6 认证器登记、替换与高保证恢复

主责能力：`CAP-AUTH-014`、`CAP-AUTH-015`、`CAP-AUTH-016`、`CAP-ASR-005`、`CAP-ASR-007`、`CAP-ASR-009`。

1. 校验当前会话保证等级、认证新鲜度和风险。
2. 对新认证器完成持有证明、用户验证和必要的可信度检查。
3. 原子创建认证器并递增用户 security epoch。
4. 替换场景将旧认证器标记为 `REPLACED`，不得直接删除审计证据。
5. 撤销相关高风险会话和 Refresh Token family。
6. 向原渠道和新渠道发送安全通知，并在保护期内限制敏感操作。
7. 无可用认证器时进入高保证恢复：多证据、等待期、人工复核和双人审批。
8. 恢复后重新计算 AAL，禁止自动恢复到高保证状态。

### 5.7 完整全局退出

主责能力：`CAP-SESSION-002`、`CAP-SESSION-010`、`CAP-SESSION-013`、`CAP-OAP-012`、`CAP-EVENT-009`、`CAP-EVENT-012`。

1. 确定退出作用域：当前应用、当前设备、租户、全部设备或全局。
2. 撤销目标 OP Session、设备 Session 和 Refresh Token family，并递增相关 security epoch。
3. RP-Initiated Logout 只允许已注册的 post-logout URI，校验请求上下文并原样返回 state。
4. Back-Channel Logout 是退出正确性的主通道：向 RP 发送签名 Logout Token，RP 校验 `iss + aud + sid/sub + iat + jti + events` 并防重放。
5. Front-Channel Logout 通过已注册 URI 传递 `iss + sid`，不使用 Logout Token。受浏览器第三方 Cookie 限制，跨站前通道退出属于尽力而为，不得作为撤销正确性的依据。
6. 对不可达 RP 重试并进入死信，平台展示“部分退出”状态；该状态必须区分“后通道未确认”与“前通道未生效”，只有前者触发安全告警，后者计为预期情形。
7. 对短期 Access Token 使用撤销表、`CAP-SESSION-013` 的安全状态水位或等待自然过期；最大残留时效引用 §9 的撤销传播目标，本节不另定数值。
8. 完成对账并记录每个 RP 的退出结果；超过 §9 目标仍未确认后通道的 RP 由 `CAP-EVENT-012` 计入消费方合规度并告警。
9. 跨站场景的 SSO 与静默续期必须依赖 BFF 加同站 Cookie 或后端会话；SSO 域边界必须在接入时就登记，跨域应用不得假定共享浏览器会话。

### 5.8 企业离职与持续撤权

主责能力：`CAP-FED-007`、`CAP-FED-009`、`CAP-AUTHZ-024`、`CAP-EVENT-009`。

1. 企业目录通过 SCIM/API 将人员状态置为停用。
2. 用户中心验证来源和版本，停用对应企业 Identity 与 Membership。
3. 撤销该租户内角色、Grant、Session 和委托权限。
4. 通知应用清理本地会话和缓存，不影响个人账号及其他租户。
5. 超过撤权 SLA 未完成时触发安全告警和人工处置。
6. 目录恢复人员时不得自动恢复历史高权限，必须重新评估授权。

### 5.9 Client 或机器凭证失陷

主责能力：`CAP-MACHINE-003`、`CAP-RISK-015`、`CAP-RISK-021`、`CAP-KEY-007`。

1. 将 Client、证书或机器凭证标记为 `COMPROMISED` 并阻止新签发。
2. 确定受影响 audience、scope、租户、Token、Webhook 和委托链。
3. 吊销相关 Token family，轮换密钥并保持安全的双钥或零信任切换窗口。
4. 通知资源服务器和订阅方执行紧急拒绝。
5. 对异常调用、数据访问和权限使用进行回溯调查。
6. 恢复前必须更换凭证、修复根因并重新通过接入 Profile。

### 5.10 Consent 撤回与隐私请求

主责能力：`CAP-PRIV-002`、`CAP-PRIV-003`、`CAP-PRIV-007`、`CAP-SSC-006`、`CAP-SSC-008`、`CAP-EVENT-013`、`CAP-EVENT-014`。

1. 强认证用户并确认请求范围、合法依据和数据主体。
2. 原子更新 Consent/Privacy Request 状态并停止新的相关 Grant。
3. 编排下游系统停止处理、撤销订阅、删除或导出数据。
4. 法律保留或业务阻断必须返回明确原因、范围和预计处理方式。
5. 失败任务按幂等语义重试，不得因部分失败宣布完成。
6. 汇总下游证明、审计、例外和完成时间，形成用户可获取的结果。

### 5.11 标识回收后的重新验证

主责能力：`CAP-ID-008`、`CAP-ID-009`、`CAP-ID-012`。

1. 新持有人验证手机号或邮箱时查询受控历史墓碑和隔离期。
2. 结合解绑时间、设备、SIM swap、历史主体和行为风险评估。
3. 不得凭新验证结果自动登录、恢复或链接旧账号。
4. 需要关联时必须对旧账号和新标识分别提供足够证据。
5. 关联失败时创建新主体或进入人工处置，不泄漏旧主体存在性。

### 5.12 身份源迁移与外部主键重绑定

主责能力：`CAP-FED-004`、`CAP-FED-012`、`CAP-FED-013`、`CAP-ID-007`、`CAP-CTRL-006`。

1. 在身份源台账上登记迁移事项：新旧 issuer 或 entityID、切量窗口、回滚条件和风险接受人。外部主键不可变的唯一例外就是登记在册的迁移，必须走 `CAP-CTRL-006` 的例外登记与双人复核。
2. 新旧身份源并存期内，两侧断言都可登录，但只有一侧拥有凭证与属性写权威。
3. 按可信属性批量重绑定：仅允许使用已验证企业邮箱加目录侧断言等双方证据，禁止仅凭邮箱静默关联。
4. 迁移期间禁止对已存在主体执行 JIT 创建，避免产生重复身份。
5. 每一条重绑定逐用户入审计，失败进入人工处置而不是静默跳过；不得通过直接修改底层数据完成迁移。
6. 切量完成后旧身份源进入只读观察期，确认无异常后退场并保留主键映射关系。

## 6. 系统交互边界

~~~mermaid
flowchart TB
    C["Web / App / 小程序 / 企业门户"] --> G["认证入口 / API 网关"]
    G --> AUTH["认证与联合登录"]
    G --> USER["用户、身份与资料"]
    G --> SESSION["会话与 Token"]
    G --> AUTHZ["权限策略与决策"]
    AUTH --> RISK["风险与 MFA"]
    USER --> CONSENT["隐私、协议与同意"]
    AUTH --> AUDIT["审计与安全事件"]
    SESSION --> AUDIT
    AUTHZ --> AUDIT
    USER --> EVENT["事件总线 / Webhook"]
    EVENT --> BIZ["各业务系统"]
    ADMIN["平台、业务、租户管理后台"] --> G
~~~

集成约束：

- 业务应用只通过标准协议和 API 接入。
- 禁止业务直接写用户中心数据表。
- 业务本地保存的用户资料副本必须明确用途、字段和同步机制。
- 事件消费必须幂等，并支持根据数据版本拒绝旧事件覆盖新数据。
- 用户中心不在 Token 中放入不必要的 PII。
- 内部领域事件若需要关联 Global User，必须使用显式的 `global_user_id`/`subject_ref` 语义；面向应用或租户的 Webhook 默认改写为接收方 pairwise Subject，禁止用含糊的 `subject_id` 字段向外泄露 Global UID。
- 业务后端校验 issuer、audience、有效期、签名和授权范围。
- 人类用户客户端默认使用授权码模式和 PKCE S256；仅登记为输入受限且无法安全调用系统浏览器的 Client 可按 `CAP-OAP-017` 使用 Device Authorization Grant。任何 Client 均不得使用 Implicit 或 ROPC。
- 回调地址必须精确匹配；浏览器、移动端和小程序不得保存客户端密钥。
- ID Token 只用于客户端确认认证结果，不得作为 API Access Token 使用。
- 业务必须区分 Subject 与 Actor，代理服务代表用户调用时保留完整委托链。
- Webhook 必须验签、校验时间戳并拒绝重放；事件消费者必须支持权威快照补拉。
- 高风险授权、冻结、撤销和保证等级变化必须通过近实时控制通道传播。
- 消费方在 `CAP-SESSION-013` 的安全状态水位不可确认时，高风险请求必须失败关闭；“未收到撤销通知”不构成继续放行的理由。
- 跨站场景的浏览器端应用必须采用 BFF 加同站 Cookie 或后端会话，不得依赖第三方 Cookie 实现 SSO、静默续期或前通道退出；接入时必须登记其 SSO 域边界。
- 业务不得自建验证码与安全通知的发送通道，统一由 §4.18 的平台通道代发，以保证频控、模板审核、可达性状态和成本归属可统一度量。
- 代理调用中的 Actor 可以是自然人（如客服代客操作、监护人代管），业务侧必须能区分“本人操作”与“代人操作”并分别审计；委托不得扩大原有权限边界，见 `CAP-ASR-012`。
- 业务不得自行定义错误文案与错误语义，统一使用 `CAP-API-004` 的错误契约，尤其不得将不泄露主体存在性的错误重写为具体原因。

## 7. 数据一致性与缓存策略

| 数据类型 | 一致性建议 | 原因 |
|---|---|---|
| 密码、MFA、身份绑定 | 强一致 | 防止旧凭证继续生效 |
| 全局冻结、Token 吊销 | 接近实时 | 属于安全控制面 |
| 角色和高风险权限 | 实时或短缓存 | 防止权限变更延迟 |
| 普通资料 | 最终一致 | 可通过事件同步提高可用性 |
| 业务成员关系 | 权威域写入、事件同步 | 避免跨域双写 |
| 审计日志 | 可靠追加 | 不允许业务更新覆盖 |
| 标识绑定与认证器 | 强一致 + 唯一约束 | 防止并发绑定和恢复竞态 |
| Grant 与高风险权限 | 强一致或有界陈旧 | 撤回后不得继续签发或放行 |
| 控制面配置 | 版本化发布 | 未审批版本不得在线生效 |
| 隐私请求 | Saga + 对账 | 跨系统处理允许部分进度但不得虚假完成 |
| Login Transaction | 强一致，服务端权威 | 已完成验证步骤不得由客户端参数声明 |
| 委托关系 | 强一致 | 委托撤销后不得继续签发含 Actor 的 Token |
| 消息发送与可达性状态 | 最终一致 + 幂等 | 重复发送验证码必须可去重，回调不保证顺序 |
| 审批与风险案件 | 强一致 | 审批结果不得并发产生两次执行 |

下游系统需具备：

- 基于事件 ID 的幂等消费。
- 基于数据版本的顺序保护。
- 失败重试和死信处理。
- 定期全量或增量对账。
- 事件丢失后的主动补拉能力。
- 基于 security epoch、policy version 和 revocation watermark 的缓存失效。
- 当处理依据为 Consent 时，基于 consent epoch、用途、数据类别与接收方共同失效相关 Token、订阅和缓存，不影响无关合法依据。
- 对跨领域流程展示处理中、部分失败、已补偿和需人工处置状态。

## 8. 管理角色建议

| 角色 | 管理范围 |
|---|---|
| 平台安全管理员 | 安全策略、风险规则、全局冻结和安全事件 |
| 平台应用管理员 | 业务线、应用、Client、回调地址和协议配置 |
| 平台用户管理员 | 用户生命周期处置，不默认拥有敏感信息明文权限 |
| 平台审计员 | 只读查看审计，不可修改用户或策略 |
| 业务线管理员 | 仅管理本业务成员、业务角色和业务配置 |
| 租户管理员 | 仅管理本租户成员、组织和租户策略 |
| 客服人员 | 脱敏查询和有限处置，敏感操作需审批 |
| 隐私管理员 | 数据请求、授权记录、删除和保留策略 |
| 紧急管理员 | 仅在应急场景使用，强制告警和事后复核 |

## 9. 核心非功能要求

### 9.0 服务等级目标引用

本文档不自行定义 SLO 数值，全部引用《统一身份与访问平台建设与验收蓝图》的 `SLO-*` 条目。任何章节需要时限、可用性或 RTO/RPO 时，只允许引用下表编号，不得就地写数值，以避免多处各写一套。

| 引用编号 | 目标对象 | 关联能力 |
|---|---|---|
| `SLO-AUTH-001` | 核心认证与 Token 端点可用性 | `CAP-PLT-001`、`CAP-OBS-012` |
| `SLO-API-001` | 管理面与非关键用户 API 可用性 | `CAP-API-002`、`CAP-OPS-001` |
| `SLO-TOKEN-001` | Token 签发延迟 | `CAP-SESSION-007` |
| `SLO-AUTHZ-001` | 在线授权决策延迟 | `CAP-AUTHZ-011` |
| `SLO-REVOKE-001` | 安全事件类变更与 SP2/SP3/SP5 的撤销传播时效 | `CAP-SESSION-010`、`CAP-EVENT-009`、`CAP-EVENT-010` |
| `SLO-REVOKE-002` | SP1 非安全类授权变更允许的最大陈旧窗口 | `CAP-PLT-011`、`CAP-AUTHZ-015` |
| `SLO-EVENT-001` | 普通资料事件可见时延 | `CAP-EVENT-007` |
| `SLO-PRIV-001` | 个人权利请求的响应与完结期限 | `CAP-PRIV-007`、`CAP-OPS-012` |
| `SLO-ALERT-001` | 安全告警确认与进入处置的时效 | `CAP-OBS-014`、`CAP-RISK-019` |
| `SLO-DR-001` | 区域灾难 RTO 与普通资料 RPO | `CAP-PLT-005`、`CAP-PLT-006` |
| `SLO-DR-002` | 标识、凭证、认证器、Grant 撤销与 security epoch 的 RPO | `CAP-PLT-009`、`CAP-SESSION-013` |
| `SLO-HA-001` | 同可用区数据库故障切换 RPO | `CAP-PLT-002` |

引用约束：

- 蓝图缺失或未批准某条 SLO 时，相关能力不得宣布验收通过，也不得由实现方临时约定数值。
- 注销冷静期、换绑保护期、标识隔离期、恢复等待期、Token 与会话有效期等时长统一登记在蓝图 §15.3.1 的时长基线表（`TTL-*`、`TERM-*`），本文档只引用。
- 外部依赖（短信、邮件、上游 IdP）引起的认证失败计入平台错误预算，不得以“外部依赖”为由排除，见 §4.18。
- SLO 达成率与错误预算由 `CAP-OBS-013` 度量，判定信号必须包含 `CAP-OBS-012` 的合成探针，不得只依赖被动指标。

### 9.1 安全

- 凭证与普通用户资料分库或至少分安全域存储。
- 密码采用现代自适应哈希算法，参数可升级；算法与参数选型必须与 `CAP-KEY-006` 的合规基线一致。
- TOTP 密钥、第三方令牌和客户端密钥应加密存储。
- 登录接口统一实施限流、枚举防护和错误信息收敛。
- 管理后台必须强制 MFA，并限制高风险操作。
- 日志、追踪、指标和事件中不得记录密码、验证码、完整 Token。
- 对手机号、邮箱、证件号等信息按角色脱敏。
- 所有客户端和服务端密钥均具备负责人、用途、有效期和轮换记录。

### 9.2 可用性

- 认证链路避免依赖非核心业务服务。
- 已签发 Token 可在短期内由业务本地校验，降低认证中心故障影响；本地校验窗口上限即适用的撤销目标，SP1 的非安全类请求适用 `SLO-REVOKE-002`，其余适用 `SLO-REVOKE-001`。这意味着高保证场景不存在「靠本地校验扰过长时间故障」的选项，对应的可用性必须由 §4.13 的高可用能力而非降级策略提供。
- 冻结、吊销和高风险授权需有实时或近实时通道，时效引用 `SLO-REVOKE-001`。
- 短信、邮件、第三方身份源故障时提供替代认证或明确降级策略，降级链见 `CAP-PLT-012`。
- 不同业务线和租户之间进行配额、资源和故障隔离。
- 安全相关依赖不可用时失败关闭，可用性优先的依赖失败开放，每个依赖的失败方向必须预先登记而不是运行时临时判断。

### 9.3 性能与容量

- 按日活用户、并发登录、峰值倍数、验证码量、Token 签发量估算容量。
- 单独评估大促、开学、发薪、直播和批量企业登录等瞬时峰值。
- 对用户检索、审计检索和在线认证采用不同存储及性能策略。
- 避免把完整权限列表和大量资料放入 Token。

### 9.4 可维护性

- 领域 API 和事件契约版本化。
- 业务规则、认证策略、风险规则和租户策略可配置但必须可审计。
- 所有策略变更支持校验、审批、灰度和回滚。
- 管理后台避免直接操作底层数据。

## 10. 旧系统迁移能力

迁移不是一次性脚本，而是一组长期能力：

| 能力 | 说明 |
|---|---|
| 旧 ID 映射 | 保存旧系统用户 ID 与 Global User ID 的映射 |
| 数据清洗 | 手机、邮箱规范化，异常值和重复值识别 |
| 重复识别 | 形成候选关系，不直接自动合并 |
| 密码迁移 | 支持合规的渐进式密码升级或用户重置 |
| 双轨运行 | 迁移期间支持新旧认证系统有限期并行 |
| 灰度切换 | 按业务线、租户、用户比例逐步迁移 |
| 差异对账 | 比对用户、身份、状态和资料差异 |
| 回滚方案 | 保留切换点、映射和回退路径 |
| 用户沟通 | 需要改密、重新绑定或重新授权时明确通知 |
| 下游改造 | 禁止继续以手机号或旧业务 ID 作为跨系统主键 |

### 10.1 双轨运行的安全例外约束

双轨运行可能要求临时保留本文档已禁用的机制（如旧系统的密码直传、非标准登录接口）。这类保留不是例外的默认权利，而是必须登记的安全例外：

- 每一项偏离必须在 `CAP-CTRL-006` 的例外台账上登记：适用范围、风险接受人、补偿控制、到期日和退役计划；无台账记录的偏离等同违规。
- 旧机制只得在登记的业务线与客户端范围内开启，不得作为平台默认能力向新接入方提供。
- 例外到期默认收紧而不是默认延期；延期本身是一次需审批的变更，并由 `CAP-CTRL-007` 定期复盘。
- 迁移期内必须同时运行 `CAP-PLT-014` 的协议一致性门禁，确保新链路不被旧机制拖低到不合规水平。
- 退役时间表必须写入接入合约或变更单，而不是口头约定；超期未退役触发安全告警。

### 10.2 推荐迁移顺序

1. 盘点所有业务用户表、登录方式、ID、资料、状态和权限。
2. 确定 Global User ID 和旧 ID 映射规则。
3. 先接统一认证协议，再迁移公共资料。
4. 建立重复账号处置流程。
5. 小业务或内部用户先灰度。
6. 逐步迁移核心业务并持续对账。
7. 停止旧系统新增账号。
8. 完成存量迁移后下线旧认证能力。

## 11. 分期建设路线

本章定义交付顺序，§4 的 P0/P1/P2 定义目标态关键程度，二者不得互相替代。每个 `CAP-*` 的最终 `phase` 必须写入蓝图 §18.4 的机器可解析追踪矩阵；同一能力跨阶段演进时拆成可独立验收的矩阵行。发布门禁只检查当前里程碑及更早阶段的适用行。

### 11.0 技术基线与工程骨架

本节把「复用优先」的原则 18 落成可执行的技术基线。未完成本节冻结前，阶段 1a 不得开工——否则协议实现方式会在编码中被默认值决定，而不是被决策决定。

| 决策项 | 基线 | 约束与理由 |
|---|---|---|
| 运行时与语言 | .NET LTS 版本（具体版本号在阶段 0 冻结并登记） | 与现有仓库一致；升级窗口跟随官方 LTS 生命周期，过期版本不得进入生产 |
| OAuth/OIDC 授权服务器 | 复用经过审计的开源库自建服务，平台只实现身份语义层 | 落实 `CAP-OAP-003` 至 `CAP-OAP-013` 的复用要求；选型必须通过 `CAP-PLT-014` 的一致性测试与 `CAP-PLT-016` 的攻击测试 |
| 授权服务器选型门槛 | 必须支持 Authorization Code + PKCE S256、private_key_jwt/mTLS Client 认证、Refresh 轮换与重放检测、三种 Logout、Discovery/JWKS 双钥窗口、可注入自定义 Claim 与校验钩子；触发 `CAP-OAP-017` 时还必须原生支持 RFC 8628 Device Authorization Grant | 无法满足当前阶段适用门槛的组件不得选用；不得靠分叉组件的协议实现来补齐 |
| 主数据存储 | 关系型数据库，支持事务、表达式/函数唯一索引、行级锁 | `INV-G-002` 的规范化唯一索引与 `REQ-SESSION-002` 的原子 compare-and-set 依赖此能力 |
| 凭证与审计存储 | 凭证域与审计域独立于业务库（独立实例或独立安全域） | §9.1 与 `CAP-OBS-004` 的隔离要求；审计仅追加 |
| 缓存 | 分布式缓存，键必须含 `security epoch` 与 `policy version` | `REQ-AUTHZ-007` 的缓存键要求；缓存不可用时按 §15.4 降级 |
| 事件与 Outbox | 与主库同事务写 Outbox，再由投递器发布到消息中间件 | `INV-G-010` 禁止跨域双写；中间件选型需支持单主体顺序键与死信 |
| 密钥管理 | KMS/HSM 或等价受控边界；境内密评适用时改用合规密码模块 | `REQ-KEY-001` 禁止私钥明文导出；形态由 §13 问题 26 的结论决定 |
| 部署形态 | 起步为模块化单体，按 §4 域码划分模块边界并禁止跨模块直接引用数据访问层；协议数据面可独立部署 | 蓝图 §2.3 要求协议数据面高可用、最小依赖；域边界即未来的服务拆分线，先拆库表边界不拆进程 |
| 代码结构 | 一模块一域码，模块内分领域模型、应用服务、契约、基础设施四层 | 使 `CAP-*` 编号与代码目录可互相定位，支撑 §18.4 的追踪矩阵 |
| 本地开发环境 | 一条命令拉起依赖（数据库、缓存、消息、模拟身份源与模拟短信通道） | `CAP-API-013` 沙箱的前置条件；禁止使用生产个人数据 |
| 时钟 | 所有节点使用统一可信时间源，最大允许偏差登记并监控，超限时安全判定失败关闭 | JWT `exp/iat/auth_time`、TOTP、Challenge 过期、密钥轮换窗口与 epoch 单调性均依赖可信时钟 |

骨架交付物（阶段 0 出口的一部分）：

1. 可运行的服务骨架：健康检查、配置加载、结构化日志、追踪、错误契约中间件。
2. 一条打通的最小链路：授权码登录 → 签发 Token → 受保护接口校验 → 退出，全部走选定组件。
3. 数据库迁移工具链与可回滚的初始 Schema。
4. CI 流水线骨架：构建、单元测试、`CAP-PLT-014` 一致性测试与敏感信息扫描三条门禁先接入。
5. 选型评审记录：候选组件、门槛逐项比对结论、许可与成本、放弃项的理由。

## 12. 目标态分阶段验收清单

每条验收项必须可判定：引用能力编号、给出验证方法、说明证据形式并指定责任人。验证方法中的 `AT-*` 为蓝图定义的自动化验收编号，`SLO-*` 为 §9.0 引用的服务等级目标。验收时以蓝图的用例描述为准，本表只负责映射关系。

验收通则：

- 本节是**里程碑级关键验收映射**，只收录跨域、高风险与易退化的关键项，不是全量能力的逐条清单。全量覆盖由蓝图 §18.4 的追踪矩阵承载：每个 P0 能力必须在矩阵中有一行，包含 Owner、测试编号与证据位置，CI 校验缺行即阻断。本表未列出的 P0 能力不等于无需验收。
- 验收证据形式必须与能力的**载体**匹配（见 §4 开头）：代码类给自动化用例编号；设施类给声明式配置位置与配置扫描报告；流程类给台账、记录或报告，并标明执行周期。把流程类能力写成「自动化测试」或把代码类能力写成「定期评审」均视为验收项无效。
- 新 Client 上线统一通过 `CAP-PLT-019` 的应用上线认证执行 Profile 检查，本节不重复造一套人工断言。
- 责任人列必须以 §14 中该能力所属域的**第一责任方领衔**，协同方依次列在其后；一行跨多个域时逐域列出其第一责任方，不得只写协同方。
- 无自动化用例或无证据形式的验收项视为未完成，不得以“已评审通过”代替。
- 任一验收项失败且未在 `CAP-CTRL-006` 登记例外时，对应能力不得宣布交付。

## 13. 必须尽早决策的问题

1. 平台如何判断两个账号属于同一个自然人，哪些情况禁止自动合并？
2. 是否同时支持个人用户、企业员工、商家、开发者和服务账号？
3. 手机号、邮箱、用户名的唯一性是全局、租户内还是应用内？
4. 哪些业务允许共享同一个 Subject，哪些业务必须使用应用级 Subject？
5. 用户能否在没有加入任何业务线时独立存在？
6. 用户资料中哪些字段由平台负责，哪些由业务负责？
7. 一个业务线封禁用户是否只影响该 Membership？
8. 注销是全局注销还是退出某个业务，两种入口如何区分？
9. 统一权限中心负责到什么粒度，哪些权限由业务自行管理？
10. 是否需要企业 SSO、租户、组织、部门和委派管理员？
11. 旧系统存在多少套账号、重复账号和不兼容密码算法？
12. 身份中心不可用时，已有登录态和敏感操作分别如何降级？
13. 业务运营地区、数据驻留、未成年人和实名要求是什么？
14. 平台可用性、最大冻结生效时间和灾备目标是什么？
15. 谁是用户数据、身份安全、权限策略和隐私治理的最终负责人？
16. 平台采用哪些 IAL/AAL/FAL 等级，各敏感操作需要何种等级和认证新鲜度？
17. 各类客户端适用哪个 OAuth/OIDC 安全 Profile，是否存在高价值 FAPI 场景？
18. Client、API Resource、机器身份和工作负载身份的负责人及下线机制是什么？
19. 平台、应用、设备、租户和上游 IdP 的退出边界及传播 SLA 是什么？
20. 手机号回收、企业邮箱重分配和域名所有权变化如何防止账号接管？
21. 控制面首个管理员、根密钥、租户所有权转移和灾备恢复信任链如何建立？
22. Consent、OAuth Grant、营销订阅和协议接受如何分别建模并向下游传播？
23. 哪些不变量必须由数据库约束、属性测试、持续对账和发布门禁分别保证？
24. C 端用户与企业员工是否共用同一个 Global User，企业租户能否接管其成员的个人账号？若共用，离职回收、企业强制改密和个人数据可携带如何互不越界？
25. 手机号与邮箱在存储加密后如何支持登录查找、客服工单检索和风控聚合？确定性加密、HMAC 盲索引与明文索引三者如何选择，检索域如何隔离？
26. 平台适用的等保级别、是否纳入密码应用安全性评估、是否存在数据出境链路分别是什么？由此确定的算法清单（含是否必须支持 SM2/SM3/SM4）必须在阶段 0 冻结，因为它决定密码哈希、Token 签名与传输加密的选型。

以上问题的结论必须落到具体能力编号或 §9 的 `SLO-*` 引用上；只写会议结论不写编号视为未决策。

## 15. 参考标准方向

平台设计和实现可对齐以下标准或行业协议：

- OpenID Connect：统一身份认证和用户身份声明。
- OAuth 2.0：应用访问授权。
- RFC 9700 OAuth 2.0 Security Best Current Practice：OAuth 安全基线。
- RFC 8725 JWT Best Current Practices：JWT 算法、类型和密钥使用安全基线。
- RFC 7009、RFC 7662：Token 撤销与内省。
- RFC 8414、RFC 9207：Authorization Server Metadata 与授权响应 issuer 标识。
- RFC 7636 PKCE：授权码拦截防护，平台只允许 S256。
- RFC 8252：原生应用使用外部用户代理与 loopback/claimed HTTPS 回调。
- RFC 8628：输入受限设备的 Device Authorization Grant；仅在 `CAP-OAP-017` 触发时启用。
- RFC 9126 PAR、RFC 9101 JAR、RFC 9396 RAR：高安全授权请求。
- RFC 8705 OAuth mTLS、RFC 9449 DPoP：发送方约束 Token。
- RFC 8707 Resource Indicators：资源与 audience 约束。
- RFC 8693 Token Exchange：受控委托和代理调用。
- RFC 9068 JWT Access Token Profile：JWT Access Token 互操作约束。
- RFC 7591、RFC 7592：仅在启用动态 Client 注册和管理时适用，并必须叠加软件声明、初始访问令牌、配额与审批控制。
- OIDC RP-Initiated、Front-Channel、Back-Channel Logout：完整单点退出。
- FAPI 2.0 Security Profile：高价值 API 的安全 Profile。
- WebAuthn / FIDO2：Passkey 和抗钓鱼认证。
- SCIM 2.0：企业用户与组织目录同步。
- SAML 2.0：存量企业联合登录。
- JWT / JWK：令牌声明和签名密钥发布。
- NIST SP 800-63-4：身份核验、认证和联合保证等级参考。
- Shared Signals / CAEP / RISC：跨域持续安全状态与撤销信号。

标准协议解决的是互操作性，具体身份合并、租户隔离、业务状态、数据权限、隐私和运营流程仍需按本平台规则设计。

### 15.1 境内法规与密码合规

上面的清单只覆盖互操作协议。平台在境内运营时，下列要求会直接改变技术选型，必须在阶段 0 与阶段 1a 之前确认，而不是上线前补：

- 个人信息保护法：告知同意、单独同意、最小必要、个人权利响应与自动化决策说明，对应 `CAP-PRIV-001` 至 `CAP-PRIV-008`。敏感个人信息与人脸等生物特征需要单独同意，不能并入注册协议一次勾选。
- 网络安全法与数据安全法：日志留存、分类分级与重要数据识别，对应 `CAP-OBS-004`、`CAP-PRIV-004`、`CAP-PRIV-005`。
- 网络安全等级保护 2.0：适用等级决定身份鉴别、访问控制、安全审计与集中管控的具体条款，对应 `CAP-AUTH-*`、`CAP-AUTHZ-*`、`CAP-OBS-*`、`CAP-CTRL-*`。等级结论是 §13 问题 26 的输入。
- 密码应用安全性评估：若纳入密评，密码哈希、Token 签名、传输加密与密钥管理需要按商用密码要求选型，可能要求支持 SM2、SM3、SM4 与合规密码模块，对应 `CAP-KEY-006` 的算法合规基线。这一结论必须在阶段 0 冻结，因为它决定 `CAP-AUTH-004`、`CAP-AUTH-005` 的密码哈希方案与 `CAP-OAP-006` 的签名算法集合，事后更换等同一次全量凭证与 Token 迁移。SM3 等快速摘要不得直接作为密码哈希，密码存储仍必须使用经批准的加盐、自适应或内存困难口令派生方案。
- 个人信息出境：存在出境链路时需要标准合同、安全评估或认证之一，并登记接收方、用途与字段范围，对应 `CAP-PRIV-015`；未完成前不得开通跨境复制。
- 人脸识别与实名相关规定：人脸与活体核验必须有非生物特征的替代方式、单独同意与原始材料留存限制，对应 `CAP-PROFILE-011`、`CAP-PROFILE-012`；实名核验的数据源与留存期需单独登记，不得以 `CAP-AUTH-020` 的 Step-up 需求为由把人脸设为唯一可选项。
- 未成年人保护：年龄识别、监护人同意与功能限制对应 `CAP-PRIV-016`、`CAP-ASR-010` 至 `CAP-ASR-012`。
- 平台方规则：应用商店与小程序平台对账号删除入口、登录方式并列展示、授权范围最小化有各自要求，对应 `CAP-FED-014`、`CAP-SSC-009`；不满足会直接影响上架准入。

合规约束：

- 上述每项的适用性判定由法务、安全与隐私负责人签署，技术规则不能替代法律判断；判定结论必须落到具体能力编号，否则视为未落地。
- 判定结果若与已实现方案冲突，走 `CAP-CTRL-006` 的例外登记，并按 §10.1 设定到期收紧时间，不得长期挂起。

## 16. 术语表

本表统一本文档与配套蓝图中容易被各团队各自解释的术语。每个术语必须能落到一个承载对象与一种可观测形式，否则不写进设计。

| 术语 | 定义 | 承载对象 | 可观测形式 |
|---|---|---|---|
| Global User ID | 自然人在平台内的唯一稳定标识，与登录方式和业务无关 | Global User | 主档记录与事件中的 UID 字段 |
| Subject ID | 面向单个应用或受众的 pairwise 标识，用于避免跨应用关联 | Global User 与 Client 的映射 | ID Token 的 `sub`、Webhook 的 `subject_ref`、映射表 |
| Membership ID | 用户在某个业务线或租户内的成员关系标识 | Membership | 成员关系记录与业务成员状态 |
| External ID | 外部身份源中的稳定键，OIDC 为 issuer 加 sub；SAML 为 entityID、NameID 值、Format、适用的 NameQualifier、SPNameQualifier 与 SPProvidedID 语义组成的规范化元组 | Identity Binding | 绑定记录与身份源登记项 |
| Login Transaction | 服务端权威的登录事务，记录已完成的验证步骤、风险判定与保证等级 | 登录事务对象 | 事务状态、完成步骤列表、过期时间 |
| Operation | 跨同步事务边界的异步操作，统一表达进度、阻断、部分完成、失败、取消、人工接管和最终结果 | 异步操作对象 | `operation_id`、状态、步骤检查点、结果或安全收敛的原因码 |
| IAL / AAL / FAL | 身份核验强度、认证强度、联合断言强度三个互相独立的等级 | 用户主档、会话、断言 | 会话与 Token 中的等级 Claim、审计记录 |
| security epoch | 用户或 Client 安全状态的单调递增版本号，改密、冻结、吊销都会推进 | Global User、Client | Token Claim 与校验侧比对的水位值 |
| consent epoch | 某个主体、用途、数据类别与接收方 Consent 聚合的单调版本号，授权、取代、撤回或到期时推进 | Consent 聚合 | Token/内省字段、订阅与授权缓存键、撤回传播水位 |
| policy version | 授权策略的版本号，决策结果必须携带 | 策略包 | 决策日志中的版本字段 |
| revocation watermark | 校验侧已知的最新撤销状态位置，用于判断本地缓存是否过期 | 各消费方 | 消费方上报的水位与滞后时长 |
| 失败关闭 | 依赖不可判定时拒绝而不是放行，用于安全相关判定 | 各 PEP 与校验点 | 注入故障测试结果、拒绝原因码 |
| 墓碑（tombstone） | 标识或账号被释放、删除后保留的最小不可逆记录，用于防止历史归属被继承 | 标识记录、已删除主体 | 墓碑表、重新绑定拦截日志 |
| 隔离期 | 标识解绑后不可被新持有人立即使用的冷却窗口 | 标识记录 | 隔离到期时间、拦截计数 |
| PAP / PDP / PEP / PIP | 策略管理、决策、执行与信息提供四个职责 | 权限平台各组件 | 决策日志、执行点埋点、属性来源登记 |
| 盲索引 | 对加密字段做 HMAC 后建立的可等值查询索引，不可反解 | 加密字段的索引列 | 检索域登记、命中率与冲突率 |
| 确定性加密 | 相同明文产生相同密文的加密方式，可等值查询但泄露重复性 | 加密字段 | 算法登记、适用字段清单 |
| BFF | 与前端同站的后端会话层，替代跨站第三方 Cookie 承载会话与静默续期 | 应用接入形态 | Client 登记的接入形态、Cookie 属性 |
| 前通道 / 后通道退出 | 前者依赖浏览器加载 RP 端点，后者由服务端直连通知 RP | 退出编排 | 逐 RP 的确认记录与未确认原因分类 |
| 错误预算 | SLO 允许的失败额度，用于约束变更速度 | 每个 `SLO-*` 条目 | 预算消耗曲线、门禁联动记录 |
| 例外台账 | 偏离 P0 约束的登记记录，含风险接受人、补偿控制与到期日 | `CAP-CTRL-006` | 台账条目、到期自动收紧动作 |
| 双轨运行 | 新旧系统同时提供服务的迁移阶段，需明确权威侧与退役时间 | 迁移方案 | 权威侧标记、退役时间表 |
| 实现策略 | §4 能力表的实现归属列，取值为自建、复用、集成、暂缓，回答由谁完成 | 每个 `CAP-*` 条目 | 能力表字段与选型评审记录 |
| 载体 | §4 能力表的实施层次列，取值为代码、设施、流程，回答在哪一层完成 | 每个 `CAP-*` 条目 | 能力表字段；对应的测试、配置扫描或台账证据 |
| 启用触发 | P2 能力从暂缓转为必备的可判定条件 | 各小节的约束段 | 触发条件文本与触发时的变更单 |
